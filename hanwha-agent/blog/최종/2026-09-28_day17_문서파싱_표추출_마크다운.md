# [한화 내일 아카데미 ICT부문] 17일차 후기 — 문서 파싱, 표 추출과 마크다운

지난 포스팅에서는 LangChain 체인을 앱에 붙이고 비동기와 스트리밍까지 다뤘습니다. 그때 체인은 틀만 섰고 문서를 찾아오는 자리는 비어 있었습니다. 17일차에는 그 자리의 맨 앞을 만들었습니다.

RAG는 문서를 검색해서 가져온 근거로 답하게 하는 방식입니다. 전체가 열한 단계입니다.

```text
문서 준비 — 문서를 올릴 때 한 번 돈다
  ① 읽어 들이기 → ② 파싱 → ③ 청킹 → ④ 임베딩 → ⑤ 벡터DB 적재

질의 — 질문할 때마다 돈다
  ⑥ 질문 처리 → ⑦ 검색 → ⑧ 필터·재정렬 → ⑨ 프롬프트 구성 → ⑩ 모델 → ⑪ 답변+출처
```

**두 덩어리가 도는 시점이 다릅니다.** 이 경계를 놓치면 질문할 때마다 PDF를 다시 파싱하는 느리고 비싼 구조가 됩니다.

오늘 만든 것은 맨 앞 ①② 입니다. 문서를 읽어 들이고 군더더기를 걷어내는 파싱입니다. 글자를 꺼내는 것 자체는 어렵지 않았습니다. 원문의 구조를 지키는 것이 오늘의 전부였습니다.

한화 내일 아카데미 ICT부문 과정 17일차에 학습한 내용을 순서대로 정리해봅니다.

## 1. 파서 고르기 — 세 갈래

파일이 들어오면 세 갈래로 나뉩니다.

```text
파일이 들어온다
      │
      ▼
1. 못 읽는 형식인가?       .hwp .doc .ppt .xls  ──▶ "…로 변환해 주세요" 안내하고 막는다
      │ (아니면 통과)
      ▼
2. 로컬로만 읽는 형식인가?  .hwpx                ──▶ 로컬 파서
      │
      ▼
3. 그 밖                                          ──▶ 상용 API, 실패하면 로컬 파서로 대체
```

**1번에서 막는 편이 낫습니다.** 구형 형식을 억지로 읽으면 글자가 일부만 깨져서 들어옵니다. 그러면 문서는 정상 등록된 것처럼 보이고 검색에도 걸려서, 사용자는 몇 주 뒤에 "답이 좀 이상한데"로 겪게 됩니다. 원인이 업로드 시점에 있다는 것은 알 방법이 없습니다. 거절은 당장 불편하지만 무엇을 하면 되는지가 같이 나옵니다.

오늘 만든 것은 2번의 로컬 파서입니다. 실습 재료는 30개였습니다.

```text
파일 30개
 .docx 10개 , .pdf 11개 , .hwpx 3개 , 그 밖의 파일 6개
```

## 2. PDF — 페이지가 단위입니다

PDF 안에는 두 가지가 섞여 있습니다.

| | 꺼낼 수 있나 | 어떤 파일인가 |
| --- | --- | --- |
| 텍스트 레이어 | 됩니다 | 워드·한글에서 PDF로 내보낸 문서 |
| 이미지 | 안 됩니다 | 종이를 스캔해서 만든 PDF |

그리고 PDF에는 "몇 번째 줄"이라는 단위가 없습니다. 글자마다 좌표가 있을 뿐입니다. 그래서 페이지를 단위로 읽습니다. `p.6`처럼 근거를 대려면 어차피 페이지가 필요하기도 합니다.

```python
from pypdf import PdfReader

reader = PdfReader(str(PDF))
print("쪽수 : ", len(reader.pages))
```

```text
쪽수 :  16
```

페이지마다 글자 수를 세어보면 문서의 모양이 드러납니다.

```text
p.1  108자     p.5  1070자     p.9   961자     p.13  310자
p.2  231자     p.6   903자     p.10  222자     p.14  244자
p.3  443자     p.7  1005자     p.11  281자     p.15  211자
p.4  272자     p.8  1042자     p.12  282자     p.16  216자
---------------
16 페이지, 합계 약 7,800 자
```

앞뒤는 표지와 별표라 짧고, 본문인 5~9쪽이 1,000자 안팎입니다.

## 3. 스캔본 — 에러가 아니라 0자가 나옵니다

```text
쪽수 :  1
p.1  0자
---------------
1 페이지, 합계 약 0 자
```

**에러가 나지 않습니다.** 빈 문자열이 나옵니다. 그래서 모르고 지나가면 "문서는 넣었는데 검색에 안 걸리는" 상태가 됩니다.

로그로 남겼습니다.

```python
if not text:
    log.info("텍스트 없음 (스캔본으로 보임): %s p.%d", path.name, page_no)
    continue
```

```text
14:48:54 INFO  app.rag.local_parsers 텍스트 없음 (스캔본으로 보임): sample_scanned.pdf p.1
블록 0개
```

나중에 OCR을 붙일 자리이기도 합니다. 지금은 조용히 빠지지 않게 하는 것까지가 할 일입니다.

## 4. DOCX — 문단과 표가 따로 나옵니다

워드 파일은 압축 파일이었습니다.

```text
첫 4바이트 : b'PK\x03\x04'   ← ZIP 표식
엔트리 17개
  [Content_Types].xml
  _rels/.rels
  docProps/core.xml
  docProps/app.xml
  word/document.xml  ← 본문이 여기 있습니다
  word/_rels/document.xml.rels
```

`python-docx`가 이걸 대신 열어줍니다. 그런데 `doc.paragraphs`는 본문 바깥 층만 훑습니다. 표 안의 문단은 표에 속해 있어서 여기 안 나옵니다.

```text
본문
  문단      ← doc.paragraphs
  문단
  표        ← doc.tables
      행
        칸
          문단   ← doc.paragraphs 에 없다
  문단
```

그래서 "문단 먼저, 표는 나중에" 읽으면 이렇게 됩니다.

```text
총 블록 233개
표가 들어간 자리 : 227 ~ 233 번째  (전부 맨 끝)
```

원문 순서로 읽으면 표의 자리는 다릅니다.

```text
본문 자식 233개   종류 : p 226 · tbl 7
tbl 위치 : [10, 218, 221, 224, 227, 229, 232]
```

**첫 표는 원문에서 10번째인데 227번째로 밀립니다.** 그 자리를 찍어보면 무엇을 잃는지 분명해집니다.

```text
 9번째 항목 :  제·개정 이력
10번째 항목 :  [표1]
```

표 바로 앞이 그 표의 제목입니다. 둘을 떼어놓으면 표만 보고는 무엇의 이력인지 알 수 없습니다. 217칸을 건너뛰어 맨 뒤 별표들 사이에 끼는 셈입니다.

다음 단계인 청킹은 앞뒤 블록을 붙여 조각을 만듭니다. 자리가 틀리면 관계없는 글이 한 조각에 묶입니다.

표를 아예 빼먹으면 얼마나 잃는지도 재봤습니다.

```text
문단만 읽었을 때 : 6,230자
표까지 읽었을 때 : 7,358자
표 안 글자 1,128자 = 전체의 15.3%
```

규정 문서에서 표에 들어가는 것은 금액·기한·한도 같은 숫자입니다. 사람이 실제로 묻는 것이 거기 있습니다.

해결은 `python-docx`가 주는 목록 대신 XML 자식을 직접 도는 것이었습니다.

```python
body = doc.element.body
for child in body.iterchildren():
    tag = child.tag.split("}")[-1]      # "{긴 주소}p" → "p"
    if tag == "p":
        text = Paragraph(child, doc).text.strip()
    elif tag == "tbl":
        table = Table(child, doc)
```

라이브러리가 감춰둔 한 겹을 걷고 원문 순서를 되찾는 것입니다.

## 5. ParsedDoc — 형식이 달라도 같은 모양으로

형식마다 결과 타입이 다르면 쓰는 쪽이 매번 분기해야 합니다. 그래서 공통 모양을 정했습니다. 11일차에 만든 포트와 어댑터의 `LLMResult`와 같은 자리입니다.

```python
@dataclass
class ParsedBlock:
    kind: str        # 덩어리 종류 : 조항, 표
    locator: str     # 원본 어디서 나왔나 : p.6, 표2
    text: str        # 덩어리 글자들

@dataclass
class ParsedDoc:
    blocks: list[ParsedBlock] = field(default_factory=list)
    page_count: int = 0      # 페이지 개념이 없는 docx 는 1 로 둔다
    table_count: int = 0

@runtime_checkable
class ParserPort(Protocol):
    def parse(self, path: str) -> ParsedDoc: ...
```

`ParserPort`를 둔 이유는 상용 파싱 API로 갈아끼울 자리를 미리 잡아두기 위해서입니다. 로컬 파서든 API든 이 모양만 맞추면 쓰는 쪽 코드는 그대로입니다.

`locator`가 형식마다 다른 값을 담는 것이 이 설계의 요점입니다.

| | `page_count` | `locator` 예시 |
| --- | --- | --- |
| PDF | 실제 쪽수 | `p.6` |
| DOCX | 1 | 문서 이름, `표2` |

DOCX에 페이지 수가 없는 것은 페이지가 인쇄할 때 정해지기 때문입니다. 같은 파일도 용지와 글꼴에 따라 쪽수가 달라집니다.

## 6. 표 — 이어 붙이면 뜻이 사라집니다

표의 칸을 순서대로 이어 붙여봤습니다.

```text
표 크기 : 4행 7열

버전 구분 시행일 주요 내용 작성 검토 승인 v2.0 개정 2025-07-01 일비 인상(25,000→30,000)
· 광역시 숙박비 상한 신설 · 별표1 전면 개정 김지원 박성호 대표이사 v1.1 개정 2024-09-01 ...
```

**어떤 값이 어떤 제목에 속하는지가 사라졌습니다.** 사람 이름이 작성자인지 검토자인지, 날짜가 어느 버전의 시행일인지 글자만 봐서는 모릅니다. 모델도 모릅니다.

행과 열이 살아 있어야 하는데 `ParsedBlock.text`는 문자열 하나입니다. 문자열인데 구조가 남아 있는 형식이 필요했고, 그게 마크다운 표였습니다.

| 왜 마크다운인가 | |
| --- | --- |
| 문자열 하나 | `ParsedBlock.text`에 그대로 들어간다 |
| 행과 열이 산다 | 모델이 "작성=김지원"을 읽어낼 수 있다 |
| 토큰을 적게 먹는다 | HTML 표보다 훨씬 짧다 |
| 언어 모델이 잘 읽는다 | 학습 데이터에 흔한 형식이다 |

```python
def _table_to_markdown(headers: list[str], rows: list[list[str]]) -> str:
    head = "| " + " | ".join(headers) + " |"
    sep = "|" + "---|" * len(headers)
    body = ["| " + " | ".join(str(c) for c in r) + " |" for r in rows]
    return "\n".join([head, sep, *body])
```

```text
| 버전 | 구분 | 시행일 | 주요 내용 | 작성 | 검토 | 승인 |
|---|---|---|---|---|---|---|
| v2.0 | 개정 | 2025-07-01 | 일비 인상(25,000→30,000) · 광역시 숙박비 상한 신설 · 별표1 전면 개정 | 김지원 | 박성호 | 대표이사 |
```

첫 행을 무조건 머리로 씁니다. 머리 행이 없는 표도 마찬가지입니다. 첫 행이 제목인지 아닌지는 사람이 봐야 알 수 있는데 틀렸을 때의 손해가 작습니다.

## 7. pdfplumber — 선을 보고 표를 찾습니다

같은 문서의 PDF 판에서 그 표가 있는 쪽을 `pypdf`로 읽어봤습니다.

```text
 1 | 제·개정 이력
 2 | 버전
 3 | 구분
 4 | 시행일
 5 | 주요 내용
...
(문서 전체 434줄)
```

표가 세로로 풀려버렸습니다. `pypdf`는 글자를 꺼낼 뿐 선을 보지 않습니다.

`pdfplumber`는 선을 보고 표를 찾습니다.

```text
이 쪽의 표 : 1개
4행 7열
['버전', '구분', '시행일', '주요 내용', '작성', '검토', '승인']
```

문서 전체에서 찾은 표 개수를 DOCX와 맞춰보면 검산이 됩니다.

```text
PDF 표 합계 : 7   ·   DOCX 표 : 7   ·   같다 : True
```

같은 문서의 두 형식에서 같은 수가 나왔습니다. 둘 다 틀렸을 수도 있지만 서로 다른 방식으로 센 값이 맞는 것은 꽤 강한 신호입니다.

셀 안에 줄바꿈이 들어 있는 것이 함정이었습니다. 마크다운 표는 한 행이 한 줄이어야 하는데 `\n`이 행을 갈라버립니다.

```text
줄바꿈이 든 셀 : 8개 (전체 220개 중)
```

220칸 중 8칸뿐이라 눈으로 훑으면 놓치기 쉽습니다. 줄바꿈을 공백으로 바꿔서 넣었습니다.

그런데 `pdfplumber`는 무겁습니다. 설치된 용량을 재봤습니다.

```text
pypdf         3.7 MB
pdfplumber    0.3 MB   ← 자기 자신은 가볍다
pdfminer      9.3 MB   ┐ pdfplumber 가 끌고 오는 것
PIL          16.0 MB   ┘
```

**`pdfplumber` 자체는 0.3MB인데 딸려 오는 것이 25MB입니다.** 글자를 배치대로 읽으려면 `pdfminer`, 선을 찾으려면 이미지 처리가 필요하기 때문입니다. 그래서 앱에서는 나눠 씁니다. 글자 추출은 `pypdf`, 표가 필요한 자리에서만 `pdfplumber`입니다.

## 8. 21건 전부 — 한 건으로는 안 보이던 것

한 건을 뜯어보는 것과 재료 전부를 한꺼번에 돌리는 것은 보이는 게 다릅니다. 노트북을 하나 더 만들어 docx와 pdf 21건을 전부 파싱해봤습니다.

실패는 0건이었습니다. 그런데 짝지어보니 한쪽 칸이 전부 0이었습니다.

```text
문서                              docx 블록  pdf 블록    배수  docx 표  pdf 표
DOC-HR-014_국내출장_여비_규정_v2.0      233       16  14.6배       7      0
DOC-PU-007_구매·계약_규정_v4.0        119        9  13.2배       4      0
...
합계                                                        32      0
```

`parse_pdf`가 표를 찾지 않으니 당연한 결과인데, **당연한 것을 숫자로 본 값**이 있었습니다. 같은 규정을 pdf로 올리면 금액표·기한표가 전부 문장 사이에 녹아 들어간다는 뜻이고, 어느 형식으로 올렸느냐에 따라 답의 품질이 갈린다는 뜻입니다.

다음 단계인 청킹이 받게 될 조각의 크기도 재봤습니다.

```text
docx  1061개 · 평균  29자 · 중앙값  17자 · 최소  2자 · 최대  378자
pdf     81개 · 평균 360자 · 중앙값 224자 · 최소 38자 · 최대 1070자
```

docx는 평균 29자인데 중앙값이 17자입니다. 절반이 17자 이하고 큰 표 몇 개가 평균을 끌어올립니다. 실제로 찍어보면 이렇습니다.

```text
가장 짧은 블록
    2자  [조항]  '일반'
    2자  [조항]  '목차'
    2자  [조항]  '부칙'
```

어느 쪽도 그대로 쓰기엔 맞지 않습니다. 두 글자로는 답이 안 나오고, 1,070자는 한 페이지 통째라 질문과 상관없는 조항이 절반입니다.

마지막으로 지원하지 않는 형식을 일부러 넣어봤습니다.

```text
DOC-HR-014_..._v1.1.hwpx
   parse_docx  KeyError
   parse_pdf   PdfStreamError

sample_notice.pptx
   parse_docx  ValueError
   parse_pdf   PdfStreamError
```

어느 예외도 "형식이 틀렸다"고 말해주지 않습니다. `KeyError`를 보고 "한글 파일을 워드 파서에 넣었구나"를 알아내려면 라이브러리 속을 알아야 합니다. 그래서 파서에 닿기 전에 확장자로 가르는 함수를 만들었습니다.

```text
막음  a.hwp              .hwp 는 읽을 수 없습니다. HWPX 로 변환해 주세요.
막음  ..._v1.1.hwpx      .hwpx 파서는 아직 없습니다.
막음  sample_table.xlsx  .xlsx 는 다루지 않는 형식입니다.
통과  DOC-FI-009_법인카드_사용_지침_v1.4.docx
```

`.hwp`와 `.hwpx`의 메시지를 다르게 했습니다. 하나는 사용자가 할 일이 있고 하나는 우리가 할 일이 남은 것이라, 같은 "안 됨"으로 묶으면 둘 다 고쳐지지 않습니다.

## 이날의 소감

17일차는 **에러가 나지 않는 실패**를 계속 만난 날이었습니다.

스캔본은 예외 없이 0자로 통과했습니다. 표를 빼먹어도 아무 일도 일어나지 않았고, 표가 맨 뒤로 밀려도 블록 수는 233개 그대로였습니다. 확장자가 틀린 파일을 넣었을 때조차 예외 이름이 엉뚱한 곳을 가리켰습니다. 전부 프로그램은 정상 종료하는데 결과가 틀린 종류였습니다.

그래서 오늘은 숫자를 세는 것이 확인 방법이 됐습니다. 표가 7개인가, 15.3%를 잃는가, 첫 표가 10번째인가 227번째인가. 코드를 읽어서는 어느 쪽도 알 수 없었고 돌려서 세어봐야 보였습니다. 16일차에 스트리밍 조각 수를 세어보고 나서야 우리 체인이 스트리밍되지 않는다는 것을 알았던 것과 같은 방식이었습니다.

파싱이 "문서를 읽는 일"이라고 생각했습니다. 그런데 글자를 꺼내는 것 자체는 라이브러리 한 줄이었습니다. 실제로 시간을 쓴 것은 원문의 구조를 지키는 일이었습니다. 표가 몇 번째에 있었는지, 무슨 제목 밑에 있었는지, 행과 열이 어떻게 묶여 있었는지입니다. 그것들은 글자에 남지 않아서 의식적으로 옮겨 담지 않으면 사라집니다.

파싱 단계에서 미리 자르지 않기로 한 것도 같은 판단이었습니다. 국비지원교육 과정에서 배운 것 중에 **되돌릴 수 없는 결정은 뒤로 미룬다**는 것이 있는데 원문 구조를 버리는 것이 딱 그런 결정이었습니다. 한번 잃으면 다시 만들 수 없습니다.
