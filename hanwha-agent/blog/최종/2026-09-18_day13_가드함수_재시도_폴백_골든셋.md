## 1. 가드 함수 — 보내기 전에 거른다

질문이 비어 있거나 지나치게 길면 모델을 부를 이유가 없습니다. 호출 한 번이 곧 비용과 대기 시간이라, **보내기 전에 걸러야 할 것은 보내기 전에 거릅니다.**

```python
MIN_QUESTION_LEN = 2
ALLOWED_MODELS = {"claude-haiku-4-5"}

def check_question(text: str) -> str:
    settings = get_settings()
    q = (text or "").strip()
    if len(q) < MIN_QUESTION_LEN:
        raise GuardTripped("질문이 비어 있거나 너무 짧습니다.")
    if len(q) > settings.max_input_chars:
        raise GuardTripped(
            f"질문이 너무 깁니다. ({len(q)}자) "
            f"{settings.max_input_chars}자 이내로 줄여주세요."
        )
    return q

def check_model(model: str) -> str:
    if model not in ALLOWED_MODELS:
        raise GuardTripped(f"허용되지 않은 모델입니다. : {model}")
    return model

def check_daily_limit(used_today: int) -> None:
    settings = get_settings()
    if used_today >= settings.daily_call_limit:
        raise RateLimited(f"오늘 호출 한도({settings.daily_call_limit}회)를 모두 사용했습니다.")
```

노트북에서 다섯 가지를 넣어봤습니다.

```text
허용 모델      : {'claude-haiku-4-5'}

정상 질문      : 통과 → "부산 출장 숙박비 한도가 얼마인가요?"
공백 세 칸     : GuardTripped (400) 질문이 비어 있거나 너무 짧습니다.
아주 긴 질문   : GuardTripped (400) 질문이 너무 깁니다. (2001자) 2000자 이내로 줄여주세요.
허용 밖 모델   : GuardTripped (400) 허용되지 않은 모델입니다. : claude-opus-4-1
한도 초과      : RateLimited (429) 오늘 호출 한도(200회)를 모두 사용했습니다.
```

세 가지를 확인했습니다. 가드 함수는 통과한 값을 **정리해서 돌려준다**는 점, 상한값이 코드가 아니라 설정에서 온다는 점, 그리고 예외 종류에 따라 상태 코드가 갈린다는 점입니다. 길이 초과는 사용자가 고칠 수 있으니 400이고, 한도 초과는 사용자가 고칠 수 없으니 429입니다.

`check_model`의 화이트리스트도 안전장치입니다. 모델명을 잘못 적으면 더 비싼 모델을 부르게 되는데, 목록에 없는 이름은 호출 전에 막힙니다.

## 2. 스키마 검증 — 모델은 형식을 어긴다

JSON으로 답하라고 시켜도 모델은 가끔 필드를 빼먹거나, 타입을 틀리거나, 앞에 잡담을 붙입니다. 세 가지를 직접 넣어봤습니다.

```python
CASES = [
    ("ⓐ 필드 누락  ", '{"answer": "1박 70,000원 이내입니다.", "enough_evidence": true}'),
    ("ⓑ 타입 어긋남", '{"answer": "...", "sources": "DOC-HR-014", "enough_evidence": true}'),
    ("ⓒ 잡담이 앞에", '네, 알겠습니다!\n{"answer": "...", "sources": [], "enough_evidence": false}'),
]
for label, raw in CASES:
    try:
        AnswerOut.model_validate_json(raw)
    except ValidationError as e:
        first = e.errors(include_url=False)[0]
        print(f"{label} : loc={first['loc']} / type={first['type']} / {first['msg']}")
```

```text
ⓐ 필드 누락   : loc=('sources',) / type=missing      / Field required
ⓑ 타입 어긋남 : loc=('sources',) / type=list_type    / Input should be a valid array
ⓒ 잡담이 앞에 : loc=()           / type=json_invalid / Invalid JSON: expected value at line 1 column 1
```

`e.errors()`가 **어디가(`loc`) 어떤 종류로(`type`) 틀렸는지**를 구조로 준다는 점이 중요합니다. 사람이 읽을 메시지만 있는 게 아니라서, 재시도할 때 "무엇이 틀렸는지"를 그대로 프롬프트에 붙일 수 있습니다.

세 경우의 성격은 다릅니다.

| 경우 | 어디서 고치나 |
| --- | --- |
| ⓒ 잡담이 앞에 | 받는 쪽에서 고칠 수 있습니다. `_extract_json`으로 JSON 부분만 남기면 통과합니다 |
| ⓐ 필드 누락 / ⓑ 타입 어긋남 | 내용 자체가 틀렸습니다. 받는 쪽에서 채울 수 없으니 다시 받아야 합니다 |

## 3. 재시도 — 무엇이 틀렸는지 알려주고 다시 받는다

같은 요청을 그대로 다시 보내는 게 아니라, 검증 오류에서 뽑은 내용을 알려주고 다시 받습니다.

```python
prompt = q if not hint else f"{q}\n\n[직전 응답의 문제] {hint}\n출력 형식을 지켜 다시 답해 주세요."
```

| 정할 것 | 이 프로젝트 |
| --- | --- |
| 몇 번 | 최대 2회 — 첫 호출 포함 총 3회 |
| 무엇을 바꾸나 | 직전에 무엇이 틀렸는지를 프롬프트에 붙입니다 |
| 언제 포기 | 2회를 다 쓰면 폴백 |

**재시도하면 안 되는 실패**를 구분하는 것이 이 절의 핵심이었습니다.

| 실패 | 다시 부르면? | 판정 |
| --- | --- | --- |
| 스키마 위반 `ValidationError` | 다른 답이 올 수 있습니다 | 재시도 |
| 529 과부하, 타임아웃 | 잠시 뒤면 될 수도 있습니다 | 재시도 |
| 401 키가 틀렸다 | 백 번 불러도 안 됩니다 | 재시도 X |
| 429 한도를 다 썼다 | 부를수록 나빠집니다 | 재시도 X |
| 400 요청 자체가 틀렸다 | 똑같이 틀립니다 | 재시도 X |
| `GuardTripped` (우리가 막음) | 막으려고 만든 것입니다 | 재시도 X, 폴백 X |

기준은 **"다시 부르면 결과가 달라질 수 있는가"**입니다. 모델의 무작위성이나 일시적 장애는 달라질 수 있지만, 키·한도·요청 형식 문제는 몇 번을 불러도 같습니다. 429에서 재시도하면 한도를 더 소모해서 상황을 악화시킵니다.

`GuardTripped`는 폴백도 하지 않습니다. 일부러 막은 것이라 폴백 답변을 내주면 가드를 둔 의미가 없어집니다.

## 4. 폴백 — 에러가 아니라 유효한 응답으로

재시도까지 다 실패하면 모델에 더 매달리지 않고 미리 정해둔 답으로 갑니다.

```python
FALLBACK_ANSWER = "요청을 처리했지만 근거를 확인하지 못했습니다. 담당 부서에 문의해 주세요."

def _fallback(run_id: str, attempts: int) -> AskOut:
    return AskOut(
        answer=FALLBACK_ANSWER,
        sources=[],
        enough_evidence=False,
        run_id=run_id,
        attempts=attempts,
        fallback_used=True,
    )
```

중요한 점은 에러가 아니라 **유효한 응답 객체**로 돌려준다는 것입니다. 화면은 평소와 같은 모양의 데이터를 받으니 깨지지 않고, 대신 `fallback_used`를 보고 표시를 따로 붙일 수 있습니다.

```python
class AskOut(AnswerOut):
    run_id: str = Field(description="이 질문 한 건의 실행 번호. 예: RUN-1234")
    attempts: int = Field(default=1, description="스키마 검증에 성공하기까지 부른 횟수")
    fallback_used: bool = Field(default=False, description="세 번 모두 실패해 폴백 답변으로 대처한 여부")
```

```text
AskOut 필드 : ['answer', 'sources', 'enough_evidence', 'run_id', 'attempts', 'fallback_used']
기본값      : attempts=1 · fallback_used=False
```

`AnswerOut`을 상속해서 답변 필드 세 개는 그대로 쓰고, 실행 정보 세 개만 더했습니다. `attempts`가 잦아지면 프롬프트를 고쳐야 한다는 신호가 되고, `run_id`로 로그와 화면을 같은 번호로 찾아갈 수 있습니다.

## 5. 서비스 한 곳에 모으고 라우터 연결

가드·호출·검증·재시도·폴백을 흩어두면 순서가 어긋납니다. 서비스 함수 하나 안에 순서대로 넣었습니다.

```python
def ask(*, question: str, run_id: str = "RUN-0000") -> AskOut:
    q = check_question(question)          # 1. 가드
    llm = factory.get_llm()               # 2. 어댑터 한 개
    hint = ""
    for attempt in range(1, MAX_ATTEMPTS + 1):
        prompt = q if not hint else f"{q}\n\n[직전 응답의 문제] {hint}\n출력 형식을 지켜 다시 답해 주세요."
        result = llm.answer(question=prompt, contexts=NO_CONTEXTS, user=DEFAULT_USER)
        try:
            data = _extract_json(result.text)
            AnswerOut.model_validate(data)                  # 3. 규격 검사
        except ValidationError as e:
            hint = _hint_from(e.errors(include_url=False))
            log.warning("스키마 위반 %d/%d회 : %s", attempt, MAX_ATTEMPTS, hint)
            continue
        return AskOut(**data, run_id=run_id, attempts=attempt, fallback_used=False)
    return _fallback(run_id, MAX_ATTEMPTS)                  # 4. 폴백
```

읽을 점이 세 가지입니다.

**`GuardTripped`는 `try` 밖에 있습니다.** 가드는 일부러 막은 것이라 재시도도 폴백도 하지 않고 그대로 전역 핸들러까지 올라갑니다.

**`except`가 `ValidationError` 하나뿐입니다.** 형식 위반만 재시도 대상이고, 401·429 같은 실패는 잡지 않아 그대로 올라갑니다.

**성공은 `return`, 실패는 `continue`입니다.** `for`를 끝까지 돌았다는 것 자체가 "다 실패했다"는 뜻이라 별도 플래그가 필요 없습니다.

노트북에서 재시도 루프만 따로 돌려봤습니다.

```text
① 한 번에 성공  RUN-0000  attempts=1  fallback=False  근거 1건
② 한 번 실패    RUN-0000  attempts=2  fallback=False  근거 1건
③ 전부 실패     RUN-0000  attempts=3  fallback=True   근거 0건
   ⚠️ 폴백으로 응답합니다 (attempts=3)
```

라우터는 서비스가 다 하고 있으니 얇습니다.

```python
router = APIRouter(prefix="/chat", tags=["chat"])

@router.post("/messages", response_model=AskOut)
def create_message(payload: ChatRequest) -> AskOut:
    return chat_service.ask(question=payload.question)
```

`main.py`에 등록하면 `prefix`가 이어 붙어 최종 경로는 `/api/v1/chat/messages`가 됩니다. `include_router`는 라우터마다 한 번씩 부릅니다. 첫 인자가 router 하나이고 나머지는 옵션 자리라 여러 개를 한 번에 넘길 수는 없습니다.

길이 검사가 두 군데 있는 것은 중복이 아닙니다.

| 어디 | 무엇 | 왜 |
| --- | --- | --- |
| `ChatRequest` (`min_length=2`, `max_length=2000`) | 요청 형식 | 형식이 어긋난 요청은 서비스까지 들어오기 전에 422로 끊습니다 |
| `check_question` (`MAX_INPUT_CHARS`) | 운영 상한 | 화면을 거치지 않는 호출도 있고, 상한은 설정으로 바꿀 수 있어야 합니다 |

실제로 호출해 보면 한 글자 질문은 스키마에서 먼저 걸립니다.

```text
POST /api/v1/chat/messages -> 200
  {"answer": "...", "run_id": "RUN-0000", "attempts": 1, "fallback_used": false}
한 글자 질문 -> 422 {"code": "validation_failed", "message": "입력값을 확인하세요 — question"}
```

## 6. 골든셋 회귀 테스트

여기까지 오면 질문 한 건이 끝까지 흐릅니다. 남은 문제는 **그게 계속 맞는지 어떻게 아는가**였습니다.

`add(2, 3) == 5`는 언제 돌려도 5입니다. 그런데 모델은 같은 질문에 매번 다른 문장으로 답합니다. 답이 맞았어도 문자열은 다릅니다.

```python
assert out.answer == "부산 출장 숙박비는 1박 7만원 이내입니다."   # 거의 항상 실패합니다
```

그래서 정답 문장을 비교하지 않고 **지켜야 할 조건**을 검사합니다. 문항은 코드가 아니라 JSON 파일에 뒀습니다.

```json
{
  "id": "N-01",
  "question": "부산 출장 2박 3일인데 숙박비 한도가 얼마인가요?",
  "expect": {
    "contains": ["7만"],
    "min_sources": 1,
    "doc_ids": ["DOC-HR-014"]
  }
}
```

문항을 정상 질문으로만 채우면 "잘 될 때 잘 된다"만 확인하게 됩니다. 유형을 네 가지로 나눠 각 유형이 최소 한 건은 있게 맞췄습니다.

| 유형 | 무엇을 보는가 | 문항 수 |
| --- | --- | --- |
| N 정상 | 근거가 있는 질문에 숫자·버전을 제대로 옮기는가 | 3 |
| E 근거 없음 | 모르는 것을 모른다고 하는가 | 2 |
| F 스키마 위반 | 재시도하고, 끝내 안 되면 폴백으로 빠지는가 | 3 |
| G 가드 | 막아야 할 것을 막는가 (답이 아니라 예외가 나야 합니다) | 3 |

```text
문항 11개
  N (정상)        3
  E (근거 없음)   2
  F (스키마 위반) 3
  G (가드)        3
네 유형 모두 있는가 : True
```

한 유형이 0이면 그 상황은 **아예 검사되지 않고 있다**는 뜻입니다. 통과율 100%보다 이 줄이 먼저입니다.

E 유형이 특히 중요합니다. 근거 없는 질문에 그럴듯한 숫자를 붙여 답하는 것은 테스트가 없으면 통과처럼 보입니다. `not_contains: ["7만"]`은 "다른 지역 한도를 끌어다 쓰면 실패"를 코드로 적은 것입니다.

골든셋을 돌릴 때마다 실제 모델을 부르면 결과가 매번 달라지고 비용도 듭니다. 미리 정해둔 응답을 돌려주는 가짜 어댑터로 갈아끼웠습니다.

```python
stub = StubLLM(case["stub"])
monkeypatch.setattr(factory, "get_llm", lambda: stub)
```

**갈아끼우는 자리는 팩토리 한 곳이고, 서비스 코드는 한 줄도 손대지 않습니다.** 이게 되는 이유는 서비스가 팩토리 모듈을 통째로 쥐고 있기 때문입니다.

```python
import app.integrations.factory as factory     # 부를 때 찾아본다 → 교체가 먹는다
from app.integrations.factory import get_llm   # 자기 이름에 복사해둔다 → 교체가 안 먹는다
```

`from ... import`로 가져왔다면 팩토리를 바꿔도 테스트가 계속 진짜 어댑터를 부릅니다. 조용히 통과하는 대신 **실제 호출이 나가서 과금되는** 쪽이 더 위험합니다.

판정은 `assert`가 아니라 실패 사유 목록으로 돌려받습니다. `assert`면 첫 위반에서 멈추는데, 목록이면 어긋난 것을 한 번에 다 볼 수 있습니다.

```text
정상 응답        : []
숫자가 빠짐      : ["answer 에 '7만' 이 없습니다"]
없는 문서를 인용 : ["허용되지 않은 doc_id: DOC-HR-999"]
```

판정 함수를 먼저 시험해 본 이유가 있습니다. 잡아내야 할 것을 못 잡는 판정 함수는 문항을 몇 개 늘려도 전부 통과시킵니다.

pytest로 옮길 때는 `parametrize`로 문항 11개를 테스트 11건으로 만들었습니다.

```python
@pytest.mark.parametrize("case", GOLDEN, ids=[c["id"] for c in GOLDEN])
def test_golden(case: dict, monkeypatch) -> None:
```

`ids=`를 주면 실패했을 때 `test_golden[F-02]`처럼 어느 문항인지 바로 보입니다. 교체가 실제로 먹었는지도 한 줄로 확인합니다.

```python
assert stub.calls > 0, "가짜 어댑터가 한 번도 불리지 않았습니다"
```

```text
N-01 YES   N-02 YES   N-03 YES
E-01 YES   E-02 YES
F-01 YES   F-02 YES   F-03 YES
G-01 YES   G-02 YES   G-03 YES

통과율 : 11/11 = 100.0%
```

```bash
pytest -q
# 36 passed
```

## 7. 실습 중 만난 문제

**파일 이름이 두 개로 갈렸습니다.** 가드 파일을 `guard.py`로 만들었는데 테스트와 서비스는 `app.core.guards`로 import하고 있었습니다. 파일을 `guards.py`로 맞추면 테스트는 통과하지만, 오전에 만든 노트북이 여전히 `from app.core.guard import ...`라서 이번에는 노트북이 실패했습니다. 이름을 바꿀 때는 **그 이름을 부르는 곳을 전부** 찾아서 같이 바꿔야 합니다.

**테스트가 틀린 경우도 있었습니다.** 25건 중 1건이 실패했는데, 기대값에서 물음표가 빠져 있었습니다.

```text
E  AssertionError: assert '제주도 출장 숙박비 한도가 얼마인가요?' == '제주도 출장 숙박비 한도가 얼마인가요'
```

`.strip()`은 앞뒤 공백만 지우고 문장부호는 건드리지 않으니, 코드는 맞게 동작하고 테스트가 틀렸습니다. 테스트가 실패했다고 항상 코드가 틀린 것은 아닙니다. 여기서 코드를 "통과하게" 고치면 멀쩡한 동작을 망가뜨리게 됩니다.

**노트북에서 `No module named 'app'`이 났습니다.** 첫 셀이 `os.chdir`로 작업 폴더만 바꾸고 있었는데, `os.chdir`은 import 경로를 바꾸지 않습니다. `sys.path`에 `backend`를 넣어야 합니다.

```python
BACKEND = str(ROOT / "backend")
if BACKEND not in sys.path:
    sys.path.insert(0, BACKEND)
```

## 이날의 소감

13일차는 **모델을 믿지 않는 코드**를 만드는 날이었습니다. 프롬프트로 "JSON만 달라"고 부탁하는 것과, 안 지켰을 때 받아내는 장치를 만드는 것은 다른 일입니다.

특히 골든셋을 만들면서 테스트의 성격이 달라진다는 점을 알게 됐습니다. 기존 테스트는 "출력이 기대값과 같은가"를 봤지만, LLM 테스트는 "있어야 할 것이 있고 없어야 할 것이 없는가"를 봅니다. 그리고 **통과율보다 문항 구성이 먼저**입니다. 정상 질문만 11개면 100%가 쉽고, 그 숫자는 아무것도 보장하지 않습니다.

실습 중 만난 문제 세 가지는 공통점이 있었습니다. 파일명이 갈린 것, 기대값에 물음표가 빠진 것, `os.chdir`로 import가 될 거라 생각한 것 모두 **"당연히 되겠지" 하고 넘긴 자리**에서 났습니다. 이번에 만든 판정 함수와 `stub.calls > 0` 검사도 결국 "확인하는 장치가 정말 확인하고 있는지"를 한 번 더 보는 코드입니다.
