# [한화 내일 아카데미 ICT부문] 16일차 후기 — LangChain을 앱에 붙이기, 비동기와 스트리밍, 재시도·폴백

지난 포스팅에서는 RAG 전체 그림과 LangChain 기초, 체인 합성까지 다뤘습니다. 거기까지는 전부 노트북 안의 이야기였습니다. 16일차에는 그 체인을 **실제 앱 코드에 넣었습니다.**

붙이는 자리가 세 군데인데, 가운데 둘이 LangChain 부품이 아니라서 그대로는 파이프에 들어가지 않았습니다. 오후에는 비동기와 스트리밍, 그리고 Runnable이 기본으로 주는 재시도·폴백을 봤습니다. 한화 내일 아카데미 ICT부문 과정 16일차에 학습한 내용을 순서대로 정리해봅니다.

1. 프롬프트의 중괄호 — SystemMessage로 푼다
2. 우리 포트를 체인에 넣기
3. 파서 — LLMResult를 파서는 모른다
4. chain.py — 하지 않는 일을 먼저 적었습니다
5. 비동기 — ainvoke가 된다고 비동기인 것은 아닙니다
6. 스트리밍 — 조각 수를 세면 압니다
7. abatch와 gather, with_retry와 with_fallbacks
8. chat_service에 넣기

## 1. 프롬프트의 중괄호 — SystemMessage로 푼다

시스템 프롬프트는 `app/agent/prompts/answer_system.md` 파일에 따로 두고 있습니다. 파일 내용을 그대로 템플릿에 넣으면 문제가 생깁니다.

```python
ChatPromptTemplate.from_messages([
    ("system", raw),            # raw 안의 { } 를 변수로 읽습니다
    ("human", "{question}"),
])
```

지금은 통과합니다. 파일을 세어보니 이렇습니다.

```text
answer_system.md : 40줄, 중괄호 0개, 0개
```

중괄호가 하나도 없어서 통과한 것이지 안전해서가 아니었습니다. 출력 예시를 한 줄 넣어보면 바로 드러납니다.

```python
risky = raw + '\n\n예시: {"answer": "...", "sources": [{"doc_id": "DOC-HR-011"}]}'
```

```text
ValueError: Invalid format specifier in f-string template.
            Nested replacement fields are not allowed.
```

**"JSON으로 답하라"는 프롬프트에 JSON 예시를 넣는 것은 지극히 자연스러운 일입니다.** 그 순간 터진다는 게 이 문제의 고약한 점입니다.

`{{ }}`로 이스케이프하는 방법도 있지만 파일을 고쳐야 하고 사람이 계속 신경 써야 합니다. 더 나은 길이 있었습니다.

```python
from langchain_core.messages import SystemMessage

ChatPromptTemplate.from_messages([
    SystemMessage(content=risky),   # 템플릿이 아니라 "완성된 메시지"
    ("human", "{question}"),
])
```

```text
input_variables = ['question']
```

튜플 `("system", ...)`은 **템플릿**이라 포맷팅을 거치고, `SystemMessage`는 **이미 만들어진 메시지**라 그대로 실립니다. 변수 목록에 `question` 하나만 남은 것이 증거입니다.

생각해보면 시스템 메시지에는 애초에 채울 변수가 없습니다. **포맷팅이 필요 없는 자리를 템플릿으로 두었기 때문에 생긴 문제**였습니다.

## 2. 우리 포트를 체인에 넣기

11일차에 만든 `LLMPort`는 `invoke`가 없어서 파이프에 들어가지 않습니다. 15일차에 배운 `RunnableLambda`로 감싸면 됩니다.

```python
def call_port(value) -> LLMResult:
    messages = value.to_messages()                       # PromptValue → 메시지 목록
    question = "\n\n".join(str(m.content) for m in messages)
    return llm.answer(question=question, contexts=port_contexts, user=port_user)

llm_step = RunnableLambda(call_port).with_config(run_name="LLMPort")
```

```text
result.text  : 부산 출장 일비는 1일 4만원입니다.
result.model : mock
```

`with_config(run_name="LLMPort")`를 붙인 이유는 관측입니다. 안 붙이면 LangFuse 화면에 `RunnableLambda`라고만 찍힙니다. 람다가 여러 개면 어느 것이 터졌는지 구분되지 않습니다.

**이 함수가 경계선입니다.** 위로는 LangChain의 `PromptValue`, 아래로는 우리 포트의 `question: str`입니다. 한쪽 세상을 다른 쪽 말로 옮기는 자리라서, 프롬프트 구조가 바뀌어도 여기만 고치면 됩니다.

## 3. 파서 — LLMResult를 파서는 모른다

`StrOutputParser`를 바로 붙이면 안 됩니다.

```python
(prompt | llm_step | StrOutputParser()).invoke({"question": "부산 출장 일비는?"})
```

```text
ValidationError: 1 validation error for Generation
```

파서는 LangChain의 `AIMessage`나 문자열을 기대하는데 우리는 `LLMResult`를 넘깁니다. 중간에 한 칸을 더 둡니다.

```python
text_chain = prompt | llm_step | RunnableLambda(lambda r: r.text)
```

```text
부산 출장 일비는 1일 4만원입니다.
```

문자열 대신 검증된 객체를 받고 싶으면 `PydanticOutputParser`를 씁니다. 12일차에 손으로 짰던 JSON 추출과 스키마 검증을 파서 하나가 대신합니다.

```python
parser = PydanticOutputParser(pydantic_object=AnswerOut)
parsed_chain = prompt | llm_step | RunnableLambda(lambda r: r.text) | parser
```

```text
결과 타입        : AnswerOut
answer          : 부산 출장 일비는 1일 2만원입니다.
enough_evidence : True
```

형식을 안 지킨 답이 오면 이렇게 걸립니다.

```text
OutputParserException: Invalid json output: 죄송합니다. 잘 모르겠습니다.
```

**이 예외가 13일차에 만든 재시도 조건 자리에 들어갈 것입니다.** 지금은 `ValidationError`를 잡고 있는데, 체인으로 옮기면 잡을 예외가 바뀝니다.

그리고 파서만 붙이는 것으로는 부족합니다. 파서는 "이런 JSON을 달라"는 설명문을 만들어 줍니다.

```python
parser.get_format_instructions()
```

```text
The output should be formatted as a JSON instance that conforms to the JSON schema below. ...
```

이걸 프롬프트에 넣지 않으면 **모델은 JSON을 달라는 말을 들은 적이 없는 상태**가 됩니다. 운에 기대는 셈입니다. `answer_system.md`에 형식을 적어두긴 했지만, 파서가 만든 지시문을 덧붙이면 **스키마가 바뀔 때 프롬프트가 따라 바뀝니다.** 손으로 적은 설명은 따라오지 않습니다.

## 4. chain.py — 하지 않는 일을 먼저 적었습니다

실제 파일은 `backend/app/agent/chain.py`입니다. 함수 다섯 개가 작은 것에서 큰 것 순으로 쌓입니다.

| 함수 | 돌려주는 것 |
| --- | --- |
| `load_prompt(name)` | `prompts/<name>.md` 내용 |
| `build_prompt(*, system_prompt=None)` | `ChatPromptTemplate` (system + human) |
| `build_result_chain(llm, ...)` | 질문 → `LLMResult` |
| `build_answer_chain(llm, ...)` | 질문 → 답변 문자열 |
| `build_parsed_chain(llm, *, schema, ...)` | 질문 → 검증된 스키마 객체 |

파일 맨 위 주석에 **여기서 하지 않는 일**을 먼저 적어뒀습니다.

```text
mock / live 분기 처리 X
재시도, 폴백 처리 X
```

분기는 `factory.py` 한 곳에만 있고, 재시도·폴백은 `chat_service`에 있습니다. `chain.py`는 **어댑터를 받아서 체인을 만들어 주기만 합니다.** `llm`을 인자로 받는 것이 그 표시입니다. 스스로 `get_llm()`을 부르지 않습니다.

## 5. 비동기 — ainvoke가 된다고 비동기인 것은 아닙니다

Runnable은 같은 일을 네 가지 방식으로 합니다. 앞에 `a`가 붙은 것이 비동기입니다.

| 기본 | 비동기 | 쓰는 법 |
| --- | --- | --- |
| `chain.invoke(...)` | `chain.ainvoke(...)` | `result = await chain.ainvoke(...)` |
| `chain.batch([...])` | `chain.abatch([...])` | `result = await chain.abatch([...])` |
| `chain.stream(...)` | `chain.astream(...)` | `async for piece in chain.astream(...):` |

노트북에서는 `asyncio.run`을 쓸 수 없습니다.

```text
플랫폼 : win32
이벤트 루프 : _WindowsSelectorEventLoop
돌고 있는지 : True
```

```text
RuntimeError: asyncio.run() cannot be called from a running event loop
```

주피터는 이미 이벤트 루프를 돌리고 있어서, 그 위에서 또 돌리려 하면 막힙니다. 대신 `await`를 그냥 씁니다.

| 어디서 | 어떻게 |
| --- | --- |
| `.ipynb` | `result = await chain.ainvoke(...)` |
| `.py` 스크립트 | `result = asyncio.run(chain.ainvoke(...))` |
| FastAPI `async def` 라우터 | `result = await chain.ainvoke(...)` |

FastAPI 라우터가 노트북과 같은 모양인 것은 우연이 아닙니다. **둘 다 이미 누가 돌리고 있는 루프 안**입니다.

여기서 하나 걸렸습니다. 우리 `LLMPort.answer`는 평범한 동기 함수인데 `ainvoke`가 그냥 돕니다.

```text
invoke  : 부산 출장 일비는 1일 5만원입니다.
ainvoke : 부산 출장 일비는 1일 5만원입니다.
```

LangChain이 비동기 구현이 없는 부품은 동기 함수를 그대로 불러 줍니다. 덕분에 코드가 깨지지 않지만 대가가 있습니다. **그 자리는 진짜로 비동기가 아닙니다.** 기다리는 동안 다른 요청을 처리하지 못합니다. `await`를 붙였으니 됐겠지 하고 넘어가면 부하를 주기 전까지 아무도 모릅니다.

## 6. 스트리밍 — 조각 수를 세면 압니다

가짜 모델로 스트리밍을 확인했습니다.

```text
조각 개수 : 9
조각 목록 : ['일비', ' ', '5만원', ' ', '-', ' ', '숙박', ' ', '실비']
```

그런데 체인 끝에 람다를 하나 붙이고 다시 세어보면 달라집니다.

```python
decorated = prompt | fake_stream_llm() | StrOutputParser() | RunnableLambda(lambda s: f"[일반] {s}")
```

```text
llm | parser                      : 9
llm | parser | RunnableLambda     : 1
우리 앱 chain.py                   : 1
```

**9개가 1개가 됐습니다.** 평범한 함수를 감싼 `RunnableLambda`는 입력이 다 모일 때까지 기다렸다가 한 번에 처리합니다. 앞에서 아무리 조각으로 흘려보내도 여기서 막힙니다.

그리고 우리 앱 체인도 1입니다. `build_answer_chain` 끝에 `RunnableLambda(lambda r: r.text)`가 있기 때문입니다. 즉 **지금 우리 체인은 `stream()`을 불러도 스트리밍되지 않습니다.** 메서드가 있다고 되는 게 아니었습니다.

함수가 조각을 받아 조각을 내놓으면 흐름이 이어집니다.

```python
def 꾸미기(조각들: Iterator[str]) -> Iterator[str]:
    for s in 조각들:
        yield f"[{s}]"
```

```text
+ RunnableLambda(보통 함수)        : 1
+ RunnableLambda(제너레이터 함수)  : 14
```

`return`이냐 `yield`냐가 스트리밍 여부를 가릅니다. 겉모양은 거의 같은데 동작이 다릅니다.

다만 이걸 고쳐도 지금은 소용없습니다. `LLMPort.answer`가 완성된 `LLMResult` 하나를 돌려주기 때문에 **흘려보낼 조각이 애초에 없습니다.** 스트리밍을 하려면 화면이 아니라 포트부터 손대야 합니다.

## 7. abatch와 gather, with_retry와 with_fallbacks

0.3초 걸리는 가짜 조회를 세 건 돌려봤습니다.

```text
순차 (for + await) : 0.92초
asyncio.gather     : 0.31초
abatch             : 0.31초
```

`for` 안에서 `await`하면 하나씩 끝나기를 기다립니다. **`await`를 썼다고 동시에 도는 게 아닙니다.**

| 방법 | 누가 동시 실행을 맡나 | 언제 쓰나 |
| --- | --- | --- |
| `await chain.abatch([...])` | LangChain이 대신 해준다 | 같은 체인에 입력 여러 개 |
| `await asyncio.gather(*[...])` | 코루틴을 직접 모은다 | 서로 다른 일을 동시에 |

둘 다 0.31초로 같으니 고르는 기준은 속도가 아니라 **입력 모양**입니다.

```text
순차 : 0.61초
동시 : 0.30초
```

답변 체인은 `{"question": ...}`을, 메타 조회는 `{"doc_id": ...}`를 받아서 `abatch`로 묶을 수 없었습니다. 그래서 `gather`입니다.

재시도는 Runnable에 붙이면 됩니다.

```python
ok = RunnableLambda(flaky).with_retry(stop_after_attempt=3, wait_exponential_jitter=False)
```

```text
1. stop_after_attempt=3 : 부산 출장 일비는? 성공   (실제 호출 3회)
2. stop_after_attempt=2 : RuntimeError: 일시 오류 2   (실제 호출 2회)
```

`stop_after_attempt`는 **재시도 횟수가 아니라 총 호출 횟수**입니다. 2를 주면 한 번 더 해보고 끝입니다.

13일차에 손으로 짠 재시도와는 맡는 일이 다릅니다.

| | `chat_service`의 for문 | `with_retry` |
| --- | --- | --- |
| 무엇에 반응하나 | **스키마 위반** (응답은 왔는데 모양이 틀림) | **예외** (응답 자체가 안 옴) |
| 다시 부를 때 | 힌트를 붙여 프롬프트를 바꾼다 | 똑같이 다시 부른다 |

형식 위반은 예외가 아니라 정상 응답이라 `with_retry`가 볼 수 없습니다. **둘은 대체재가 아닙니다.**

폴백도 붙일 수 있습니다.

```python
safe = RunnableLambda(always_fail).with_fallbacks([RunnableLambda(fallback_notice)])
```

```text
폴백 결과 : 지금은 답변할 수 없습니다. 총무팀 담당자에게 문의해 주세요.
   타입      : RunnableWithFallbacks
```

`invoke`에서는 깔끔합니다. **스트리밍에서는 다릅니다.**

```text
error_on_chunk_number=0 : 폴백 성공 → '지금은 답변할 수 없습니다.'
error_on_chunk_number=2 : 폴백 실패 → FakeListChatModelError
                          이미 나간 조각 2개 : '부산'
```

첫 조각이 나가기 전에 터져야 폴백이 듣습니다. 중간에 터지면 사용자는 이미 `부산`까지 읽은 상태이고, 폴백 문장으로 바꿔 치울 수가 없습니다. `invoke`는 다 만든 다음에 넘기니 갈아 끼울 여지가 있지만 **스트리밍은 내보내면서 만듭니다.**

## 8. chat_service에 넣기

`ask()`에서 어댑터를 직접 부르던 줄이 체인 호출로 바뀌었습니다.

```python
chain = build_result_chain(llm, contexts=NO_CONTEXTS, user=DEFAULT_USER).with_retry(
    stop_after_attempt=2
)
...
# result = llm.answer(question=prompt, contexts=NO_CONTEXTS, user=DEFAULT_USER)
result = chain.invoke({"question": prompt})
```

바깥 구조는 그대로입니다. 가드 → 실행 기록 생성 → 트레이스 → 재시도 → 사용량 기록 → 검증 → 폴백 → 기록 마무리입니다.

체인을 **for문 밖에서 한 번만 만드는 것**이 맞습니다. 프롬프트는 매번 달라지지만 체인 구조는 같아서, 안에서 만들면 같은 객체를 세 번 조립하게 됩니다.

테스트는 그대로 통과했습니다.

```text
backend/tests/test_chat_golden.py    11 passed
backend/tests/test_layers.py          5 passed
전체                                 36 passed
```

13일차에 만든 골든셋이 이 교체의 안전망이었습니다. 어댑터를 팩토리에서 갈아 끼우는 방식이라, 안에서 체인을 쓰든 포트를 직접 쓰든 테스트는 상관하지 않습니다. **경계를 잡아두면 안쪽을 바꿀 수 있다**는 것이 여기서 값으로 돌아왔습니다.

## 이날의 소감

16일차는 **새 기능을 만든 날이 아니라 이미 있는 것을 다른 방식으로 부른 날**이었습니다. 사용자가 받는 답은 하나도 바뀌지 않았고, 테스트 36건도 그대로 통과했습니다.

그런데도 이 교체가 안전했던 이유가 분명했습니다. 11일차에 포트와 어댑터로 경계를 그어두고, 13일차에 골든셋으로 그 경계를 지켰기 때문입니다. **그때는 왜 이렇게까지 하나 싶었던 것들이 오늘 한 번에 값을 했습니다.** 경계가 없었으면 체인으로 바꾸는 동안 무엇이 깨졌는지 알 방법이 없었을 것입니다.

확인하는 방법에 대해서도 배운 게 있습니다. `ainvoke`가 도는 것과 진짜 비동기인 것은 다르고, `stream()`이 있는 것과 실제로 조각이 나오는 것은 다릅니다. 둘 다 **에러 없이 통과하기 때문에** 그냥 보면 알 수 없습니다. 조각 수를 세어보고 나서야 우리 체인이 스트리밍되지 않는다는 것을 알았습니다. 돌아간다는 것과 의도대로 돌아간다는 것은 다른 이야기였습니다.

재시도를 두 겹으로 쌓으면서 걸리는 점도 생겼습니다. 지금 한 번의 질문이 최대 3회 × 2회, 여섯 번까지 모델을 부를 수 있습니다. 게다가 `with_retry`가 예외로 재시도한 호출은 사용량 표에 남지 않습니다. 15일차에 "버려진 응답도 이미 과금됐으니 검증 전에 기록한다"고 정했는데, 그 구멍이 다른 모양으로 다시 생긴 셈입니다. 더 정확히는 **과금됐는지조차 알 수 없습니다.** 연결이 안 닿았으면 과금이 없고, 답을 다 만든 뒤 오류였으면 과금이 있는데 지금 코드로는 구분되지 않습니다.

국비지원교육 과정이 3분의 1을 지나면서, 편해지는 도구를 붙일 때마다 **무엇을 잃는지 같이 보는 습관**이 생기고 있습니다. `with_retry` 한 줄이 코드를 줄여주지만 장부에는 구멍을 냅니다.
