## 1. 글자로 찾으면 질문이 안 걸립니다

같은 문서에 네 번 물어봤습니다.

```text
'숙박'                         → 17줄
'숙박비'                        → 17줄
'출장 갈 때 숙박비 얼마?'             → 0줄
'출장 숙박비'                     → 0줄
```

단어를 정확히 치면 찾고 문장으로 물으면 못 찾습니다. `출장 숙박비`조차 0줄인데, 띄어쓰기 하나로 연속된 글자가 아니게 되기 때문입니다.

사용자는 단어가 아니라 문장으로 묻습니다. 이 간극이 임베딩을 넣는 이유였습니다. 비슷한 자료를 찾는 기능이 멋있어서가 아니라, 글자 검색이 실제로 이렇게 못 찾습니다.

## 2. 확장과 패키지는 다릅니다

PostgreSQL에는 `vector`라는 자료형이 없습니다. 두 가지를 따로 깔아야 하는데 이름이 비슷해서 하나로 착각하기 쉬웠습니다.

| | 무엇을 하나 | 어디에 |
| --- | --- | --- |
| 확장 `vector` | DB가 `vector` 자료형을 알게 합니다 | PostgreSQL 안 |
| 패키지 `pgvector` | SQLAlchemy가 그 타입을 파이썬에서 다루게 합니다 | 가상환경 안 |

```bash
docker compose exec postgres psql -U agent -d agent -c "CREATE EXTENSION IF NOT EXISTS vector;"
python -m pip install "pgvector==0.5.0"
```

확장은 DB에 붙는 것이라 컨테이너를 지우고 다시 만들면 다시 켜야 합니다. 그리고 이게 마이그레이션에 없습니다. 저장소를 새로 받아 `alembic upgrade head`만 해서는 안 생깁니다.

## 3. 차원은 한 곳에서 정합니다

```python
# models/base.py
EMBED_DIM = 1024
```

칼럼은 `Vector(1024)`로 굳어 있는데 설정이 768이면 적재할 때 터집니다. 그래서 설정의 기본값을 이 상수에서 가져옵니다.

로컬 어댑터는 한 걸음 더 갑니다. 설정에 적힌 1,024를 믿지 않고 모델에게 직접 묻습니다.

```python
self.dim: int = int(self._model.get_embedding_dimension())
```

모델을 바꿨는데 설정을 안 고치면 그 차이가 여기서 드러납니다.

칼럼은 `nullable=True`로 더했습니다. 이미 행이 들어 있는 테이블에 칼럼을 붙이는 마이그레이션이라 기존 행은 비어 있어야 합니다. 이 결정이 뒤에서 `embedding IS NOT NULL` 조건으로 돌아옵니다.

## 4. 거리 연산자 셋은 같은 정보였습니다

벡터가 얼마나 가까운지를 재는 연산자가 셋입니다.

| 연산자 | 이름 | 무엇을 재나 |
| --- | --- | --- |
| `<=>` | 코사인 거리 | 두 벡터가 이루는 각도 |
| `<->` | L2 거리 | 두 점 사이의 직선 거리 |
| `<#>` | 내적의 음수 | 곱해 더한 값에 마이너스 |

내적만 부호가 뒤집혀 있습니다. 내적은 클수록 가까운데 그대로 두면 정렬 방향이 혼자 반대가 됩니다. 마이너스를 붙여 셋을 "작을수록 가깝다"로 맞추면 `ORDER BY ... ASC` 하나로 전부 쓸 수 있습니다.

셋으로 각각 정렬해 보니 순서가 똑같이 나왔습니다. 값만 다르고 순위는 같았습니다. 왜 그런지 각도를 제가 정한 벡터를 넣어 확인해 봤습니다.

```text
청크                 cos |    <=> 예측        실측 |    <-> 예측        실측 |    <#> 예측        실측
합성-같은 방향           1.0 |    0.0000    0.0000 |    0.0000    0.0000 |   -1.0000   -1.0000
합성-가까움             0.8 |    0.2000    0.2000 |    0.6325    0.6325 |   -0.8000   -0.8000
합성-중간              0.5 |    0.5000    0.5000 |    1.0000    1.0000 |   -0.5000   -0.5000
합성-직각              0.0 |    1.0000    1.0000 |    1.4142    1.4142 |   -0.0000   -0.0000
```

크기가 1인 벡터끼리는 셋이 한 값에서 나옵니다.

```text
<=>  =  1 - cos
<->  =  sqrt(2 - 2cos)  =  sqrt(2 × <=>)
<#>  =  -cos            =  -(1 - <=>)
```

수업에서 나온 실제 값으로도 맞춰 봤습니다. 코사인 거리 0.3074가 나온 청크의 L2 거리가 0.7841이었는데 `sqrt(2 × 0.3074)`가 0.7841입니다. 내적은 -0.6926이었고 `-(1 - 0.3074)`가 -0.6926입니다.

이건 모델이 벡터를 정규화해 준다는 전제에서 성립합니다. 정규화를 끄면 길이가 제각각이 되고 그때는 긴 문서의 벡터가 길어져서 "내용이 비슷해서"가 아니라 "길어서" 위로 올라옵니다.

DB가 주는 거리는 작을수록 가까우니 화면에는 `1.0 - 거리`로 뒤집어 내보냅니다. 단조 변환이라 순서는 바뀌지 않습니다.

## 5. 색인이 테이블보다 큽니다

벡터 검색을 빠르게 하려고 HNSW 색인을 만들었습니다.

```sql
CREATE INDEX chunks_embedding_hnsw ON chunks USING hnsw (embedding vector_cosine_ops);
```

연산자 클래스를 골라서 만듭니다. `vector_cosine_ops`로 만든 색인은 `<=>`로 정렬할 때만 쓰입니다. `<->`로 질의하면 같은 색인이 있어도 안 탑니다.

만들고 크기를 봤더니 뜻밖이었습니다.

```text
chunks_embedding_hnsw      40 kB
테이블 본체                8192 bytes
```

본문 8kB에 색인이 40kB입니다. HNSW는 벡터 사이의 이웃 관계를 그래프로 따로 쌓기 때문에 행이 적을 때는 배보다 배꼽이 큽니다.

게다가 안 탑니다.

```text
[enable_seqscan=off]
  ->  Index Scan using chunks_embedding_hnsw on chunks  (cost=20.03..24.08 ...
[enable_seqscan=on]
  ->  Seq Scan on chunks  (cost=0.00..1.05 rows=4 width=12)
```

전부 훑는 쪽을 막아야 색인을 씁니다. 비용 추정이 24.08 대 1.10이고 네 줄짜리 테이블에서는 그냥 읽는 게 싸니 판단이 맞습니다.

그런데도 미리 만드는 이유는 수만 건이 쌓인 뒤에 만들면 그동안 모든 질의가 전부 훑기 때문입니다. 데이터가 적을 때 티가 안 나고 쌓인 뒤에 오는 종류의 느려짐입니다. 차원 한계를 미리 확인했던 것과 같은 모양입니다.

## 6. 질문으로 근거를 찾았습니다

검색 결과 한 줄을 사용자에게 보여주려면 테이블 셋을 붙여야 합니다. 본문과 출처는 `chunks`에, 몇 판인지는 `document_versions`에, 제목과 부서와 보안등급은 `documents`에 있습니다. 한 번의 조인으로 가져옵니다. 청크를 먼저 찾고 문서를 하나씩 조회하면 결과 12건에 질의가 25번 나갑니다.

1번에서 0줄이던 그 문장으로 물어봤습니다. 숙박비가 실제로 적힌 여비 규정을 올린 상태입니다.

```text
1. score 0.6795  DOC-HR-014 (현행) · 제3장 제2절 제14조(숙박비) · 별표1
     제14조(숙박비) ① 숙박비는 실제 지출한 금액으로 지급하되, [별표1]의 상한을 …
2. score 0.6507  DOC-HR-014 (현행) · 표3
3. score 0.649   DOC-HR-014 (현행) · 표2
     | 직급 | 일비 | 숙박비(광역시) | 숙박비(그 밖의 지역) | 식비 | …
4. score 0.6423  DOC-HR-014 (현행) · 제3장 제1절 제12조(식비) · 별표1
```

1위가 숙박비 조문이고 3위가 금액이 적힌 표입니다. 글자로는 0줄이던 문장이 조문과 금액표를 같이 집어 옵니다. 출처가 `제3장 제2절 제14조(숙박비)`로 나와 그대로 근거로 쓸 수 있습니다. 조 단위로 묶고 장·절을 붙여 둔 청킹 규칙이 여기서 값을 합니다.

시간을 재 보니 느린 쪽이 예상과 달랐습니다.

```text
회차           질문 임베딩       벡터 조회
1           11.145초      0.171초  ← 모델 여는 값 포함
2            0.096초      0.051초
3            0.095초      0.049초
```

질문을 벡터로 바꾸는 데 0.09초, 가까운 것을 찾는 데 0.05초입니다. 첫 회차의 11초는 임베딩이 아니라 모델을 처음 메모리에 올리는 값이고 프로세스당 한 번만 듭니다. 서버를 재시작한 뒤 첫 사용자만 그걸 기다립니다. 뜰 때 미리 한 번 불러 두면 없앨 수 있는 비용입니다.

그런데 이 출력이 문제 두 가지를 같이 보여줍니다.

**같은 내용이 여러 번 나옵니다.** 위 결과는 한 판만 올려서 깨끗한데, 수업에서는 같은 문서의 세 판을 다 올려 1·2·3위가 전부 같은 조항으로 나왔습니다. v1.4·v2.0·v2.1 을 다 올렸고 그 조항 본문이 세 판에서 같습니다. 점수까지 0.557로 같습니다. 상위 3건만 쓰면 사용자가 받는 근거 세 건이 같은 문장의 세 판본입니다. 수업에서 개수를 3에서 12로 늘렸는데, 늘려도 4·5·6위가 또 같은 표의 세 판본이었습니다. 개수를 늘리는 건 증상을 미루는 쪽이고, 검색에서는 현행 판만 봐야 합니다. 작업 단계의 마지막 빈 칸이 이것이었습니다.

**근거가 없어도 답을 돌려줍니다.** 수업에서는 법인카드 지침만 올린 상태로 숙박비를 물었는데 열두 건이 모두 돌아왔습니다. 숙박비가 적힌 문서는 올리지 않았는데도 그렇습니다. 없는데도 빈손으로 돌아오지 않습니다. 그때 1위 점수가 0.557이었고 맞는 문서를 올렸을 때가 0.6795입니다. 이 차이로 "답이 있다"와 "없다"를 가를 수 있을지는 모르겠습니다. 경계가 좁고 문서가 바뀌면 또 달라집니다.

벡터 검색은 "가장 가까운 몇 개"를 돌려주는 기능이지 "맞는 답이 있는지"를 가려 주는 기능이 아니었습니다.

지난 포스팅에서 적어 둔 것이 하나 걸렸습니다. "파싱은 0.1초지만 10초를 넘기면 업로드는 성공했는데 화면에는 실패로 뜬다"고 써 뒀는데 임베딩을 붙이자 그게 실제 문제가 됐습니다. 19청크에 9초가 걸렸습니다. 화면 쪽 제한시간을 10초에서 60초로 올렸습니다.

올린 건 임시 대응입니다. 작업 번호를 받아 1초마다 물어보는 구조를 이미 만들어 뒀으니 업로드 요청 자체가 길어질 이유는 없는데, 지금은 업로드와 작업 조회가 같은 제한시간을 씁니다. 둘을 나누면 올리지 않아도 되는 값입니다.

## 7. import 두 줄을 빠뜨렸습니다

코드를 받아 붙이다 `embedder.py`에서 import 두 줄을 빠뜨렸습니다. 함수 하나가 `get_settings()`와 `Path`를 쓰는데 파일 맨 위에 그 둘이 없었습니다.

```text
터진다 → NameError : name 'get_settings' is not defined
```

함수 안에서만 쓰는 이름이라 import가 없어도 모듈은 뜹니다. 서버도 정상으로 올라옵니다. 부를 때까지 조용합니다.

터지는 자리가 나빴습니다. 이 함수를 부르는 곳이 적재 함수 안이고 그건 배경에서 돕니다. 업로드는 201로 끝나고 화면은 정상으로 보입니다. 작업 상태를 물어봐야 비로소 에러가 나옵니다.

문법 오류였다면 서버가 뜨지 않아 바로 알았을 겁니다. 이름 오류는 그 줄을 지나갈 때만 납니다. 코드를 받아 붙일 때 import부터 맞추는 쪽이 쌉니다.

## 이날의 소감

임베딩 모델이 2.29GB씩 둘이라 정리를 쓰는 동안은 받아 두지 않았습니다. 그래서 질문을 벡터로 바꾸는 부분은 수업에서 나온 값으로 먼저 썼고 나중에 받아서 같은 것을 다시 돌려 제 수치로 바꿨습니다.

그 사이에 모델 없이 확인할 수 있는 게 있다는 걸 알았습니다. 각도를 제가 정한 벡터를 만들어 넣으면 칼럼이 제대로 왕복하는지, 거리 연산자 셋의 관계가 맞는지, 색인이 타는지, 조인이 도는지를 전부 눌러 볼 수 있었습니다. 4번의 예측과 실측을 맞춘 표가 그렇게 나온 것입니다.

"모델이 좋은가"와 "배선이 맞는가"는 다른 질문입니다. 섞어서 보면 결과가 이상할 때 어느 쪽이 틀렸는지 알 수 없습니다. 모델이 없어서 어쩔 수 없이 둘을 나눴는데, 나누고 보니 나누는 쪽이 원래 맞았습니다.

23일차도 기능을 늘린 것보다 늘린 기능이 어디서 틀리는지 찾은 쪽이 더 남았습니다. 상위 3건이 같은 문장의 세 판본이라는 것, 근거가 없어도 그럴듯한 점수가 붙어 나온다는 것. 둘 다 돌려 보고 출력을 읽어야 보이는 것들이었습니다.
