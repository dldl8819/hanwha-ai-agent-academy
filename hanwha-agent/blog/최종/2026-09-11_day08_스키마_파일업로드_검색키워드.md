# [한화 내일 아카데미 ICT부문] 8일차 후기 — 스키마, 파일 업로드, 검색 키워드 확장

지난 포스팅에서는 리포지토리·서비스 계층으로 DB 접근과 트랜잭션 경계를 나누는 내용을 정리했었는데, 그다음 시간엔 그 위에서 실제로 화면과 주고받을 데이터 형태(스키마)를 정리하고 파일 업로드 API를 처음부터 만들어봤습니다. 한화 내일 아카데미 ICT부문 과정 8일차 내용으로, 문서 하나를 실제로 서버에 올려서 DB에 기록까지 남기는 흐름을 끝까지 따라가 봤습니다.

8일차에 학습한 내용을 순서대로 정리해봅니다.

1. 모델과 스키마의 차이
2. 요청 단위 의존성 확장
3. 파일 업로드(멀티파트)
4. 검색 키워드 확장

## 1. 모델과 스키마의 차이

| | 모델(`app/models/document.py`) | 스키마(`app/schemas/document.py`) |
| --- | --- | --- |
| 개념 | DB 테이블의 한 행을 담는 객체 | 데이터를 외부로 전달할 때 쓰는 객체 |
| 구성 요소 | `Mapped`, `mapped_column` | `BaseModel` |
| 읽는 주체 | 데이터베이스(내부) | 브라우저 등 외부(화면) |
| 값 구성 | 옵션 없음, 테이블에 저장되는 모든 데이터 | 화면에 안 띄울 정보는 제외 가능 |

가장 중요한 규칙은 **모델은 절대로 화면에 그대로 전달하지 않는다**는 것입니다. 브라우저 개발자 도구에 그대로 노출되면 보안에 취약해지기 때문입니다. 그래서 응답용 스키마를 따로 만들었습니다.

```python
class DocumentOut(BaseModel):
    doc_id: str
    title: str
    dept: str
    version: str
    security_level: Literal["일반", "3급", "대외비"]
    file_format: Literal["docx", "pdf"]
    status: Literal["현행", "만료"]
    effective_from: date
    expires_at: date | None = None
    index_status: Literal["대기", "재임베딩", "완료", "보관"] = "대기"
    index_progress: int = Field(default=0, ge=0, le=100)

class DocumentCreateOut(BaseModel):
    doc_id: str = Field(examples=["DOC-HR-014"])
    title: str
    version: str = Field(examples=["v2.0"])
    file_format: Literal["docx", "pdf"]
    file_path: str = Field(examples=["uploads/DOC-HR-014_v2.0.docx"])
    created: bool = Field(description="문서가 새로 생겼으면 True, 버전만 더했으면 False")
```

## 2. 요청 단위 의존성 확장

`deps.py`에 요청마다 새로 만들어야 하는 것들을 의존성으로 추가했습니다.

```python
def get_request_id(request: Request) -> str:
    return request.headers.get("X-Request-ID") or uuid.uuid4().hex[:8]

RequestIdDep = Annotated[str, Depends(get_request_id)]

def get_request_logger(request_id: RequestIdDep) -> logging.Logger:
    return get_logger(f"api.req.{request_id}")

LoggerDep = Annotated[logging.Logger, Depends(get_request_logger)]
```

`get_request_logger`가 `RequestIdDep`을 또 요구하는 중첩 의존성 구조입니다. 클라이언트가 `X-Request-ID` 헤더를 보내면 그걸 쓰고, 없으면 새로 만들어서 요청 하나를 로그에서 끝까지 추적할 수 있게 했습니다.

## 3. 파일 업로드(멀티파트)

파일은 JSON에 담을 수 없어서, 브라우저는 파일을 보낼 때 텍스트 칸과 파일 칸을 나눠서 보내는 **멀티파트(multipart/form-data)** 형식을 씁니다. FastAPI에서 이걸 파싱하려면 라이브러리 설치가 필요합니다.

```bash
python -m pip install python-multipart==0.0.32
```

업로드 라우터는 텍스트 필드를 `Form()`으로, 파일을 `File()`/`UploadFile`로 받습니다.

```python
@router.post("", response_model=DocumentCreateOut, status_code=201)
async def upload_document(
    doc_id: Annotated[str, Form()],
    title: Annotated[str, Form()],
    dept_id: Annotated[str, Form()],
    security_level: Annotated[str, Form()],
    version: Annotated[str, Form()],
    effective_from: Annotated[date, Form()],
    file: Annotated[UploadFile, File()],
    logger: LoggerDep,
) -> dict:
    safe_name = Path(file.filename or "").name
    ext = Path(safe_name).suffix.lower()

    if ext not in ALLOWED_EXTS:
        raise ValidationFailed(
            f"{ext or '확장자 없는'} 파일은 등록할 수 없습니다. "
            "DOCX 또는 PDF 로 변환해 다시 올려 주세요."
        )

    UPLOAD_DIR.mkdir(parents=True, exist_ok=True)
    dest = UPLOAD_DIR / f"{doc_id}_{version}{ext}"
    with dest.open("wb") as out:
        shutil.copyfileobj(file.file, out)

    return document_service.create_document(
        doc_id=doc_id, title=title, dept_id=dept_id, security_level=security_level,
        version=version, effective_from=effective_from,
        file_path=dest.as_posix(), file_format=ext.lstrip("."),
    )
```

허용 확장자를 집합(`ALLOWED_EXTS`)으로 관리하고, 여기 없는 확장자는 `ValidationFailed`를 던져서 전역 예외 핸들러가 422로 응답하게 만들었습니다. 실습 삼아 `.txt`를 임시로 허용 목록에 넣고 업로드가 되는지, 뺐을 때 거부되는지 서버를 직접 띄워서 확인했는데 둘 다 의도대로 동작했습니다. 업로드된 실제 파일이 쌓이는 `uploads/` 폴더는 `.gitignore`에 추가해서 저장소에는 안 올라가게 했습니다.

## 4. 검색 키워드 확장

문서 목록 조회에 조건을 하나씩 늘려갔습니다 — 전체 조회, 부서별 조회, 보안 등급별 조회, 상태별 조회, 키워드 검색까지 다섯 가지 방식을 파라미터 하나로 다 처리합니다.

```python
@router.get("", response_model=list[DocumentOut])
def list_documents(
    dept_id: str | None = None,
    security_level: str | None = None,
    status: str | None = None,
    q: str | None = None,
    limit: Annotated[int, Query(ge=1, le=100)] = 20,
) -> list[dict]:
    return document_service.list_documents(
        dept_id=dept_id, security_level=security_level, status=status, q=q, limit=limit
    )
```

라우터는 파라미터를 그대로 서비스에 넘기기만 하고, 실제로 조건을 SQL로 바꾸는 건 리포지토리(`document_repo.list_documents`)가 맡습니다. 계층별로 역할이 딱 나뉘어 있으니, 검색 조건이 하나 더 늘어도 라우터 시그니처에 매개변수 하나 추가하는 정도로 끝났습니다.

## 이날의 소감

지금까지 만든 레이어드 구조(라우터-서비스-리포지토리-모델)가 실제 기능을 하나 추가할 때 얼마나 수월해지는지 체감한 하루였습니다. 파일 업로드처럼 완전히 새로운 기능도 스키마 하나, 라우터 함수 하나만 추가하면 나머지(트랜잭션, 쿼리, 예외 처리)는 이미 만들어둔 계층이 그대로 받아줬습니다. 확장자 검증 실습을 서버를 직접 띄워서 curl로 재현해보면서, 코드를 눈으로만 보는 것과 실제로 요청을 보내서 확인하는 것의 차이도 다시 느꼈습니다.
