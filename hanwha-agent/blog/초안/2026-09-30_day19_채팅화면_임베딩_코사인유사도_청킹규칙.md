## 1. 채팅 화면 — Streamlit 재실행 모델

백엔드는 13일차에 이미 질문을 받고 있었습니다. 그동안 `/docs`나 노트북으로만 불렀는데, 이날 사람이 쓸 화면을 붙였습니다.

서버가 둘입니다.

```bash
uvicorn app.main:app --app-dir backend     # 8000
streamlit run frontend/app.py              # 8501
```

따로 도는 프로세스 둘이고 화면이 HTTP로 백엔드를 부릅니다. 대화 이력은 딕셔너리 목록입니다.

```python
chat: list[dict[str, str]] = []

def append_turn(history: list[dict[str, str]], role: str, content: str) -> None:
    history.append({"role": role, "content": content})
```

`role`과 `content` 두 칸짜리 모양이 낯익습니다. Anthropic SDK의 `messages`가 같은 모양이고 LangChain의 `SystemMessage`도 이걸 객체로 감싼 것입니다. 나중에 이력을 모델에 넘겨 이어 대화하게 할 때 변환이 거의 없습니다.

여기서 Streamlit의 재실행 모델이 그대로 걸립니다.

```python
if 'chat' not in st.session_state:
    st.session_state['chat'] = []
```

입력이 들어올 때마다 스크립트가 처음부터 다시 돕니다. `chat = []`을 그냥 두면 매번 빈 목록으로 초기화되어 대화가 한 마디도 안 쌓입니다. `if ... not in`으로 감싸서 없을 때만 만드는 것이 요점입니다.

화면 함수는 순서가 곧 설계입니다.

```python
def render() -> None:
    # ① 쌓여 있던 대화를 먼저 다 그린다
    for message in st.session_state['chat']:
        with st.chat_message(message['role']):
            st.markdown(message['content'])

    # ② 입력창. 입력이 없으면 여기서 끝난다
    question = st.chat_input('무엇을 도와드릴까요?')
    if not question:
        return

    # ③ 질문을 이력에 넣고 바로 그린다
    st.session_state['chat'].append({'role': 'user', 'content': question})
    ...
```

재실행마다 화면이 비므로 ①에서 이력을 다시 그려야 대화가 이어져 보입니다. ②의 `if not question: return`은 입력이 없는 재실행에서 아무 일도 하지 않게 막습니다. 메뉴를 클릭하기만 해도 스크립트는 다시 돌기 때문입니다.

## 2. 화면이 안 보여 주는 것

백엔드가 돌려주는 `AskOut`에는 다섯 가지가 들어 있는데 화면은 `answer` 하나만 씁니다.

| 필드 | 화면에서 | |
| --- | --- | --- |
| `answer` | 씁니다 | |
| `sources` | 안 씁니다 | 근거 문서·조항·버전 |
| `fallback_used` | 안 씁니다 | 폴백으로 답한 것인지 |
| `attempts` | 안 씁니다 | 몇 번 만에 성공했는지 |
| `run_id` | 안 씁니다 | 이 질문의 실행 번호 |

`sources`를 안 보여주는 것이 제일 큽니다. RAG 11단계의 ⑪ Citation 자리인데 비어 있습니다. 출처 없이 답만 보여주면 사용자가 답을 확인할 방법이 없습니다. 규정 답변에서는 그게 전부입니다.

실패했을 때도 문제가 남습니다. 질문은 이력에 쌓였는데 답을 받아오다 실패하면 `return`으로 빠져나가서 assistant 메시지가 안 들어갑니다. `st.error`는 그 실행에서만 그려지고 `session_state`에 남지 않으므로, 다음 재실행에서는 **답이 안 온 질문 하나**만 보이고 이유는 사라집니다.

## 3. 블록과 청크는 다릅니다

오후 진도입니다. 파서가 이미 문서를 잘라 놓았는데 그걸 그대로 쓰지 않는 이유부터 봤습니다.

```python
doc = parse_local(TARGET)
print(f'블록 {len(doc.blocks)} · 표 {doc.table_count} · 쪽 {doc.page_count}')
```

```text
블록 233 · 표 7 · 쪽 1
```

233개를 통째로 프롬프트에 넣으면 숙박비를 묻는데 항공기 조항까지 실려 갑니다. 그렇다고 블록 하나만 넣으면 다른 것이 빠집니다. "광역시 숙박비가 얼마까지 되나요"에 답하는 블록을 골라 보면 이렇습니다.

```text
고른 블록 : ② 광역시 지역의 숙박비는 1박당 70,000원을 상한으로 한다.
  이 블록 안에 조 표시가 있나 : False
  30자도 안 되는 블록 : 131개 / 233개
```

답은 맞는데 어느 조항인지가 블록 안에 없습니다. "제14조(숙박비)"는 30번 블록에 9자짜리로 따로 떨어져 있습니다. 이 블록만 검색해서 넘기면 앞에서 본 ⑪ Citation에 적을 것이 여전히 없습니다.

233개 중 131개가 30자도 안 됩니다. 절 제목, 조 제목, 문서번호 같은 것들입니다. 그래서 둘을 나눕니다.

| | 무엇 | 누가 정하나 |
| --- | --- | --- |
| 블록 | 파서가 보는 단위 — 문단 하나, 표 하나 | 문서와 파서 |
| 청크 | 검색이 쓸 단위 — 조 하나, 표 하나 | 우리 |

블록은 주어진 것이고 청크는 정하는 것입니다. 파서를 고쳐서 블록을 크게 만드는 방법도 있지만 그렇게 하지 않습니다. 파서는 문서 구조를 그대로 옮기는 일만 하게 두어야 같은 파서 출력으로 청킹 방식을 여러 개 시험할 수 있기 때문입니다.

## 4. 낱말이 겹쳐야 찾는 검색의 한계

지금까지 문서를 찾는 방법은 글자가 겹치는지 보는 것이었습니다. 두 문구의 글자 겹침을 0에서 1 사이로 재봤습니다.

```python
def jaccard(x: str, y: str) -> float:
    sx, sy = (set(x.replace(' ', '')), set(y.replace(' ', '')))
    return len(sx & sy) / len(sx | sy)
```

```text
'광역시 숙박비 상한' vs '잠자리 비용 한도'      겹치는 글자 ['비', '한'] · 자카드 0.154
'광역시 숙박비 상한' vs '광역시 숙박비 상한액'  겹치는 글자 8개       · 자카드 0.889
```

뒤쪽은 글자 하나 차이라 0.889가 나옵니다. 앞쪽은 뜻이 거의 같은데 0.154입니다. 실제 문서에 SQL `LIKE`를 걸어 보면 더 분명합니다.

```text
LIKE '%숙박비%' → 27건
LIKE '%잠자리%' → 0건
LIKE '%잠자리 비용%' → 0건
```

블록 233개 안에 숙박 규정이 분명히 있는데 "잠자리 비용"으로는 0건입니다. 낱말 비교는 쓴 사람과 찾는 사람이 같은 단어를 쓸 때만 맞습니다.

여기서 벡터가 나옵니다. 글자 대신 뜻을 숫자 배열로 바꾸면 겹치는 글자가 없어도 가까울 수 있습니다.

## 5. 코사인 유사도 — 거리가 아니라 각도

벡터를 이루는 실수의 개수가 차원입니다. 받아 둔 두 모델은 `config.json`에 이렇게 적혀 있었습니다.

```text
KURE-v1    hidden_size=1024 · max_position=8194 · xlm-roberta
bge-m3     hidden_size=1024 · max_position=8194 · xlm-roberta
```

둘 다 1024차원이고 구조도 같습니다. KURE-v1이 bge-m3를 한국어로 미세조정한 것이라는 설명이 파일에서 확인됩니다.

차원이 크면 좋을 것 같지만 값이 붙습니다. 실수 하나를 4바이트로 보고 재봤습니다.

```text
1024차원 × 8000청크 × 4바이트 =  31.25 MB
4096차원 × 8000청크 × 4바이트 = 125.00 MB     ← 4배
```

저장을 맡을 `pgvector`에는 한계가 둘 있습니다. 벡터 열에 담을 수 있는 차원은 16,000인데 빠른 검색용 색인을 만들 수 있는 차원은 2,000입니다. 2,000을 넘기면 저장은 되는데 색인이 안 걸려서 검색할 때마다 전부 훑습니다. 데이터가 적을 때는 티가 안 나고 쌓인 뒤에 느려지므로 차원은 적재를 시작하기 전에 정해야 합니다.

본론인 코사인 유사도는 내적을 두 크기로 나눈 값입니다.

```python
def dot(u, v):    return sum((a * b for a, b in zip(u, v)))   # 같은 자리끼리 곱해 더한다
def norm(u):      return math.sqrt(dot(u, u))                 # 제곱합의 제곱근
def cosine(u, v): return dot(u, v) / (norm(u) * norm(v))      # 내적을 두 크기로 나눈다
```

```text
cos(u, u) = +1.0000    똑같다
cos(u, v) = +0.8000    닮았다
cos(u, ⊥) = +0.0000    아무 상관 없다
cos(u, w) = -1.0000    정반대
```

왜 크기를 나누는지는 안 나눠 보면 압니다. 질문 `q`에 대해 뜻이 가깝지만 짧은 문서 `d1`과, 뜻은 덜 가깝지만 긴 문서 `d2`를 비교했습니다.

```text
# 나쁜 예 — 내적만
  d1 0.900  vs  d2 3.000   → 이기는 쪽 = d2
# 좋은 예 — 코사인
  d1 0.994  vs  d2 0.707   → 이기는 쪽 = d1
```

문장이 길면 벡터가 커집니다. 내적만 쓰면 긴 문서가 이기고, 그 결과가 프롬프트에 실리면 관계없는 긴 글에 토큰을 쓰게 됩니다. 각도만 보면 방향이 맞는 짧은 쪽이 이깁니다.

크기를 1로 맞춰 두면 나눌 것이 아예 없어집니다.

```text
dot(û, v̂) = 0.960000   cosine(u, v) = 0.960000   차이 0.0
```

같은 값입니다. 적재할 때 정규화해 두면 검색은 내적만으로 끝납니다.

## 6. 임베딩 모델 두 개를 재봤습니다

18일차에 받아 둔 모델을 이날 처음 열었습니다. 인터넷을 타지 않게 환경변수로 막습니다.

```python
import os
os.environ["HF_HUB_OFFLINE"] = "1"
...
def main() -> None:
    from sentence_transformers import SentenceTransformer   # 함수 안에서 import
```

`import`보다 먼저 설정해야 먹습니다. 라이브러리가 불려 올 때 이 값을 읽기 때문에, 파일 맨 위에 `import`를 두면 환경변수를 설정하는 줄보다 먼저 실행될 수 있습니다.

재는 방법을 먼저 정했습니다. 문장쌍 6개에 사람이 미리 답을 적어 둡니다. 점수만 보면 잘한 것처럼 보이므로 무엇이 나와야 하는지를 고정하고 나서 모델을 돌립니다.

```text
[KURE-v1] 차원 1024 - 모양 (12, 1024)
 +0.6585  같은 뜻 광역시 숙박비 상한 / 잠자리 비용 한도
 +0.7380  같은 뜻 출장 전에 신청서를 낸다 / 출장은 사전 신청이 원칙이다
 +0.8239  가까움  법인카드로 결제한다 / 법인카드 사용 지침을 따른다
 +0.7484  가까움  일비는 하루 단위로 준다 / 숙박비는 1박 단위로 준다
 +0.7216  다름   출장 신청서를 낸다 / 재택근무를 신청한다
 +0.3898  남남   숙박비 상한액 / 정보보안 지침 위반
```

첫 줄이 이 실습의 목적이었습니다. 자카드 0.154에 `LIKE`로는 0건이던 짝이 **0.6585로 올라왔습니다.** 글자가 안 겹쳐도 뜻으로 찾는다는 것이 확인됩니다.

그런데 제대로 안 된 것도 나왔습니다.

| | 가까운 쌍 최저 | 먼 쌍 최고 |
| --- | --- | --- |
| KURE-v1 | 0.6585 | 0.7216 |
| bge-m3 | 0.6573 | 0.7626 |

먼 쌍이 가까운 쌍보다 높습니다. 두 모델 모두 그렇습니다. "0.7 이상이면 관련 있다"처럼 임계값 하나를 걸면 틀린 쌍이 통과하고 맞는 쌍이 걸러집니다. 순서가 뒤집혀 있으니 임계값을 어디에 두어도 이 여섯 쌍을 옳게 가를 수 없습니다.

다만 이걸 모델의 실패로 보기는 어렵습니다. 문제가 된 쌍이 `출장 신청서를 낸다 / 재택근무를 신청한다`인데 둘 다 사내 절차를 신청하는 문장입니다. 모델이 0.72를 준 것이 틀렸다고 하기 어렵고, 거르는 일은 RAG 11단계의 ⑧ 필터·리랭킹이 할 몫이지 ④ 임베딩이 할 몫이 아닙니다. 즉 이 결과는 **문장쌍 6개로는 모델을 평가할 수 없다**는 뜻으로 읽는 쪽이 맞습니다. 라벨을 정하는 것 자체가 판단이고, 그 판단이 틀리면 점수가 아무것도 말해 주지 않습니다.

모델 선택은 점수보다 조건이 먼저 자릅니다. 문서가 회사 밖으로 나가면 안 된다는 조건이 API 모델을 자르고, 라이선스와 차원이 더 자른 뒤에 남은 둘을 재는 순서입니다. 반대로 하면 쓸 수 없는 모델을 재느라 시간을 씁니다.

## 7. 청킹 규칙 — 표는 자르지 않습니다

마지막으로 어디서 자를지를 정했습니다. 문서를 통째로 이어 붙이고 1,200자마다 끊어 봤습니다.

```text
8,505자 → 8 청크
  표4: 원문 위치 7035~7413 → 청크 #5~#6  두 조각으로 갈린다
  표7: 원문 위치 8191~8487 → 청크 #6~#7  두 조각으로 갈린다
```

일곱 개 중 둘이 갈립니다. 갈린 자리를 펴 보면 왜 문제인지가 보입니다.

```text
앞 조각에 머리행이 있나 : True
뒤 조각에 머리행이 있나 : False
```

뒤 조각에는 열 이름이 없습니다. `| 국내선 항공 | 일반석 | 실비 | 본부장 |`만 검색되면 이 값들이 무엇을 뜻하는지 알 수 없습니다.

`RecursiveCharacterTextSplitter`를 쓰면 될까 싶어 넣어 봤는데 같은 둘이 갈립니다. 이 도구는 줄 경계는 알아도 표라는 것은 모르기 때문입니다. 한도를 넘으면 줄 사이 어디든 끊습니다. 문서 구조를 아는 쪽이 먼저 갈라 주어야 합니다.

그래서 규칙을 둘 세웠습니다. 첫째, 표는 자르지 않습니다. 표 하나가 청크 하나이고 길이를 따지지 않습니다.

```text
가장 긴 표 = 378자 · LIMIT 을 넘는 표 = 0개
```

가장 긴 표가 한도의 3분의 1이라 규칙을 지키는 비용이 0입니다.

둘째, 조는 통째로 묶습니다. `제14조(숙박비)` 제목부터 다음 조 직전까지가 한 청크입니다. 정규식으로 자르는데, 괄호를 어떻게 씌우는지에 따라 결과가 달라집니다.

```text
캡처 그룹 ()      ← 우리가 쓸 형태
['', '제1조(목적)', ' 이 규정은 여비를 정한다. ', '제8조(일비)', ' 일비는 30,000원으로 한다.']

비캡처 (?:)      ← 조 제목이 통째로 사라진다
['', ' 이 규정은 여비를 정한다. ', ' 일비는 30,000원으로 한다.']
```

바깥 괄호 하나만 씌웁니다. 안 씌우면 조 제목이 결과에서 사라져 출처를 못 적습니다.

돌려 보니 걸리는 것이 하나 더 나왔습니다.

```text
('제9조', '제9조 에 따라 관리한다.\n목차\n제1장 총칙')
```

이건 조 제목이 아니라 문장 안에서 다른 조를 가리키는 말입니다. 세어 보니 `제N조`가 100번 나오는데 줄 맨 앞은 73번이고 나머지 27번이 상호참조였습니다. 목차에 적힌 조 제목도 28개가 잡혔습니다. 실제 조가 73개인데 조각이 101개 나온 이유입니다.

## 이날의 소감

이날 배운 것 중 가장 오래 남는 건 **재보기 전에 재는 방법부터 정한다**는 순서입니다. 임베딩 모델을 돌리기 전에 문장쌍 6개에 답을 먼저 적어 뒀기 때문에 "먼 쌍이 가까운 쌍보다 높다"는 결과를 알아볼 수 있었습니다. 점수만 봤다면 0.72와 0.74를 구분하지 못하고 넘어갔을 것입니다.

그리고 그 결과를 모델 탓으로 돌리지 않고 문항 설계를 의심하게 된 것도 이날 배운 부분입니다. 6쌍으로는 아무것도 결론 낼 수 없다는 것을 숫자로 확인했습니다.

청킹은 규칙을 정하는 일이 대부분이었습니다. 코드는 짧은데 "표를 자르지 않는다", "조를 통째로 묶는다"를 정하기까지 실패 사례를 여러 번 만들어 봐야 했습니다. 도구가 알아서 해 줄 것이라고 기대했던 `RecursiveCharacterTextSplitter`가 표를 그대로 갈라 버린 것이 그 차이를 분명히 보여줬습니다. 라이브러리 사용법을 아는 것과 왜 그렇게 쓰는지를 아는 것의 차이가 여기에 있습니다.

`chunker.py`는 아직 절반입니다. 조 단위로 자르는 함수가 목록을 만들다 말고 끝나서 부르면 `TypeError`가 납니다. 다음 수업에서 이어 씁니다.
