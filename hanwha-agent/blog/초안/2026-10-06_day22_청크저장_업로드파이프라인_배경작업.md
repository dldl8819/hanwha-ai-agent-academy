한화 내일 아카데미 ICT부문 22일차입니다. 21일차까지 만든 것은 문서를 조각내는 기능이었습니다. 조각은 변수에 담겼다가 셀이 끝나면 사라졌습니다. 이날 진도는 그 조각을 테이블에 남기고, 업로드 요청 한 번으로 파싱부터 저장까지 이어 붙이는 것이었습니다.

## 1. 담을 자리가 없었습니다

21일차까지의 결과를 다시 찍어 봤습니다.

```text
블록 81 · 표 2 · 쪽 1
조항 단위 17 + 표 단위 2 = 19 청크
  [표] ord=1  locator=표1  글자 수=264
  [표] ord=18  locator=표2  글자 수=283
```

81블록을 19청크로 줄였는데 그 19개를 쓸 데가 없습니다. 질문이 들어올 때마다 문서를 다시 파싱할 수는 없습니다. 그래서 `chunks` 테이블을 만들었습니다.

## 2. 청크는 문서가 아니라 버전에 매답니다

`Chunk.version_id` 가 가리키는 것은 `documents` 가 아니라 `document_versions` 입니다. 처음에는 왜 한 단계 더 들어가는지 몰랐습니다.

```python
class Chunk(Base):
    __tablename__ = "chunks"

    id: Mapped[int] = mapped_column(primary_key=True)
    version_id: Mapped[int] = mapped_column(ForeignKey("document_versions.id"), index=True)
    ord: Mapped[int] = mapped_column(default=0)        # 문서 안에서의 순서
    kind: Mapped[str] = mapped_column(String(16))      # "조항" | "표"
    locator: Mapped[str] = mapped_column(String(200))  # "제3장 제2절 제14조(숙박비)"
    text: Mapped[str] = mapped_column(Text)
```

같은 문서라도 판이 다르면 본문이 다릅니다. 숙박비 상한이 7만원에서 8만원으로 바뀐 판이 있으면, 두 조각은 같은 조항 번호를 달고도 다른 답을 내놓습니다. 문서에 매달면 **그 둘이 한 통에 섞여 어느 쪽이 맞는지 가릴 수 없습니다.**

`text` 를 `String` 이 아니라 `Text` 로 둔 이유도 눌러 봤습니다. 위 재료의 표2가 283자입니다. `VARCHAR(200)` 에 283자를 넣어 보니 조용히 잘리는 게 아니었습니다.

```text
거부됐다 → DataError
   (psycopg.errors.StringDataRightTruncation) value too long for type character varying(200)
```

잘린 채로 저장되는 것보다는 낫습니다. 다만 터지는 자리가 업로드가 아니라 배경 작업 안이라, 사용자에게는 성공 응답이 먼저 갑니다.

## 3. 모델을 써도 마이그레이션이 비어서 나올 수 있습니다

모델 클래스를 쓰고 Alembic 을 돌리면 끝인 줄 알았습니다. `models/__init__.py` 에 import 하는 한 줄이 더 필요했습니다.

```python
from app.models.document import Chunk, Document, DocumentVersion
```

Alembic 의 autogenerate 는 `Base.metadata` 에 등록된 테이블만 봅니다. import 하지 않으면 등록이 안 되고, 리비전 파일이 빈 `upgrade()` 로 나옵니다. 에러가 아니라 빈 파일이라 알아채기 어려운 자리입니다.

```text
Base.metadata 에 등록된 표:
  chunks ←
  departments
  document_versions
  documents
  run_steps
  runs
  usage_logs
  users
```

## 4. 같은 판을 다시 올리면 갈아끼웁니다

파싱부터 저장까지 잇는 함수를 만들었습니다. 이 안에 생각하지 못한 처리가 하나 있었습니다.

```python
drafts = chunker.chunk(parsed)

for old in list(dv.chunks):   # 기존 청크를 먼저 지운다
    s.delete(old)
s.flush()                     # DELETE 를 먼저 내보낸다

for i, d in enumerate(drafts):
    s.add(Chunk(version_id=dv.id, ord=i, kind=d.kind, locator=d.locator, text=d.text))
```

지우지 않고 `add` 만 하면 같은 조항이 두 벌 남습니다. 검색이 같은 근거를 중복으로 집어 오고, 어느 것이 최신인지 가릴 방법이 없습니다. **더하는 게 아니라 갈아끼워야 합니다.**

```text
재적재 결과: {'chunks': 19, 'tables': 2, 'summary': '조항 단위 17 + 표 단위 2 = 19 청크'}
chunks 전체 행 수 : 19 → 19
늘지 않았다. 더한 게 아니라 갈아끼웠다.
```

`s.flush()` 가 없으면 SQLAlchemy 가 INSERT 를 먼저 보낼 수 있습니다. 지금은 유일 제약이 없어 티가 안 나지만 제약을 거는 순간 충돌합니다.

## 5. 왜 배경으로 돌리는지 시간을 재 봤습니다

파싱과 청킹을 업로드 요청 안에서 다 돌리면 요청이 그만큼 매달립니다. 그래서 먼저 쟀습니다.

```text
파일                                         청크      1회차      2회차
DOC-FI-009_법인카드_사용_지침_v1.4.docx            19   0.014초   0.014초
DOC-FI-009_법인카드_사용_지침_v1.4.pdf             17   0.107초   0.027초
DOC-HR-014_국내출장_여비_규정_v2.0.docx            53   0.026초   0.028초
DOC-HR-014_국내출장_여비_규정_v2.0.pdf             45   0.096초   0.099초
```

두 번 잰 것은 첫 번째 값에 파서 라이브러리를 처음 올리는 비용이 섞이기 때문입니다. PDF 가 0.107초에서 0.027초로 떨어지는데 그 차이가 라이브러리 import 값입니다. **파싱이 느린 것과 import 가 느린 것은 다른 문제입니다.** 섞어 재면 엉뚱한 곳을 고치게 됩니다.

재료는 전부 0.1초 아래라 동기로 불러도 아무 일 없습니다. 문제는 지금 재료가 기준이 아니라는 점입니다. 20쪽이 0.1초면 수백 쪽은 몇 초입니다. 화면 쪽 요청 제한이 10초인데 그걸 넘기면 업로드는 성공했는데 화면에는 실패로 뜹니다.

## 6. 작업 번호를 배부합니다

FastAPI 가 응답을 보낸 뒤 호출할 함수를 담아 두는 상자를 줍니다.

```python
job_id = document_service.start_ingest_job(doc_id=doc_id, version=version, path=dest.as_posix())
background.add_task(document_service.run_ingest_job, job_id)

return {**result, "job_id": job_id}
```

업로드 응답에는 결과가 없고 "어느 작업을 보면 되는지" 만 들어갑니다.

`add_task` 에 괄호를 붙여 쓰면 어떻게 되는지 확인해 봤습니다.

```text
add_task(작업(1)) 를 호출:
   (작업이 지금 실행됨: 1 )
등록 끝. 이제 배경 작업을 돌려 본다:
   터졌다 → TypeError : the first argument must be callable
```

작업은 동기로 이미 끝나고, 그 뒤 배경에서 `None()` 을 부르다 터집니다. 응답은 그 전에 나가므로 화면은 정상이고 로그에만 남습니다. 괄호 하나로 비동기가 사라지는데 결과만 보면 잘 돌아간 것처럼 보입니다.

배경 작업의 예외를 전부 받아 작업에 적어 두는 것도 같은 이유였습니다. 응답은 이미 나갔으니 예외가 요청 쪽으로 돌아갈 길이 없습니다. 잡아서 적지 않으면 화면은 진행 중에 영원히 머물고 원인은 아무 데도 남지 않습니다.

실제로 한 번 걸렸습니다. 서버를 `backend/` 폴더에서 띄웠더니 설정 파일을 못 찾고 다른 DB 로 붙었습니다.

```text
작업 상태: 실패 / 0 % / 0 청크
메시지: (sqlite3.OperationalError) no such table: chunks
```

설정을 읽는 경로가 현재 작업 폴더 기준이라서 그렇습니다. 예외를 적어 두는 코드를 넣어 둔 덕에 원인이 화면에 그대로 나왔습니다.

## 7. 업로드 화면과 폴링

지금까지의 요청은 전부 JSON 이었습니다. 파일은 JSON 으로 못 보냅니다. 멀티파트로 나가야 하고, 그 형식에서는 텍스트 칸과 파일 칸이 따로 실립니다.

```python
return _request("POST", "/api/v1/documents",
                data={"doc_id": doc_id, "title": title, ...},
                files={"file": (filename, content)})
```

`files` 의 값이 튜플인 것에 이유가 있었습니다. 바이트만 주면 서버가 파일 이름을 몰라 확장자 검사에서 걸립니다.

화면은 한 자리에서 두 가지를 그립니다. 세션에 작업 번호가 없으면 등록 폼, 있으면 진행 상태입니다.

```python
if job["status"] not in ("완료", "실패"):
    time.sleep(1)
    st.rerun()
```

1초에 한 번 묻고 다시 그립니다. 이 조건을 빼면 끝난 뒤에도 계속 서버를 두드립니다. `time.sleep(1)` 이 화면 그리는 쪽을 멈추기 때문에 그 1초 동안은 다른 입력을 받지 못합니다. 몇 분 걸리는 작업이라면 서버가 밀어 주는 방식으로 바꿔야 합니다.

## 8. 완료인데 66% 입니다

```text
완료 · 66% · 19청크
조항 단위 17 + 표 단위 2 = 19 청크

  [  ok] 파일 검증
  [  ok] 문서 파싱                      표 2개 인식
  [  ok] 표 -> 마크다운 변환               표 2개
  [  ok] 청킹                         19청크
  [todo] 임베딩
  [todo] 검색 반영 및 현행 버전 지정
```

여섯 단계 중 넷만 돌아갑니다. 뒤 둘은 아직 구현이 없습니다. 목록에서 지우지 않고 남겨 둔 것이 좋았습니다. 무엇이 빠졌는지가 화면에 그대로 보입니다. 진행률도 4/6 으로 계산해서 완료인데 66% 에서 멈춥니다. 100% 로 적으면 임베딩이 끝난 것처럼 보이니 덜 된 것을 덜 됐다고 두는 쪽입니다.

## 이날의 소감

AI 에이전트를 만든다고 하면 모델을 부르는 코드가 전부일 것 같았습니다. 22일차까지 와서 보니 모델을 부르기 전에 쌓아야 하는 것이 훨씬 많습니다. 이날 쓴 코드 중에 모델을 부르는 줄은 한 줄도 없었습니다.

눌러 보고 알게 된 것이 둘 있습니다. `VARCHAR(200)` 이 조용히 자르는 줄 알았는데 거부했습니다. `add_task` 에 괄호를 붙이면 아무 일 없이 동기로 돌아가는 줄 알았는데 배경에서 터지고 로그에만 남았습니다. 둘 다 **코드만 읽었으면 반대로 외웠을 자리**입니다.

같은 날 짚어 두고 고치지 않은 것도 셋 적어 뒀습니다. 임베딩을 하지 않았는데 색인 상태가 완료로 적혀서 벡터 없는 판이 검색 대상으로 판정됩니다. 작업 상태를 담아 둔 곳이 프로세스 메모리라 서버가 다시 뜨면 사라집니다. 그리고 지난 포스팅의 출처 문제가 모양을 바꿔 돌아왔습니다.

조 제목이 없는 조각은 출처 자리에 파일 이름이 들어갑니다. 업로드는 파일명을 문서번호와 판 번호로 갈아치웁니다.

```text
원본 파일명        DOC-FI-009_법인카드_사용_지침_v1.4.docx  → ['DOC-FI-009_법인카드_사용_지침_v1.4']
업로드가 바꾼 이름   DOC-FI-009_v9.9.docx               → ['DOC-FI-009_v9.9']
```

21일차까지는 화면에 찍고 지나가는 값이라 넘겼습니다. 이날부터는 그 값이 DB 에 저장되고, 나중에 근거 인용으로 사용자에게 보입니다. 사용자에게 "이 답은 DOC-FI-009_v9.9 에서 나왔습니다" 라고 하면 아무것도 알려 주지 않습니다. 미루면 뒤에서 더 비싸집니다.

과정의 절반을 넘겼습니다. 돌아보면 기능을 늘린 날보다 이미 만든 것이 어디서 틀리는지 찾은 날이 더 많았습니다.
