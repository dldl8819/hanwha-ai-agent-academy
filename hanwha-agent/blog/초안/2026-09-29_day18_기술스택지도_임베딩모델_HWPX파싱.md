## 1. 기술 스택 지도 — 도구를 먼저 고르지 않는다

앱은 층으로 쌓여 있고 층마다 선택지가 많습니다. 화면만 해도 Streamlit·Gradio·React·NiceGUI가 있고 저장소는 PostgreSQL·Chroma·Qdrant·Pinecone이 있습니다.

지도 맨 아래에 기준이 한 줄 적혀 있었습니다.

```text
「어느 게 빠른가」보다 「스택에 무엇이 하나 더 늘어나는가」
```

늘어난 것 하나마다 배워야 할 것, 버전을 맞춰야 할 것, 터졌을 때 봐야 할 곳이 같이 늘어납니다. 성능은 대체로 나중에 문제가 되고 개수는 처음부터 문제가 됩니다.

그 앞에 더 중요한 기준이 있었습니다. **도구를 먼저 고르지 않는다**입니다. 필요한 것을 한 줄로 적는 쪽이 먼저입니다. 우리가 적은 한 줄은 이것이었습니다.

```text
「문서의 판과 보안등급으로 거른 뒤에 비슷한 것을 찾는다」
```

이 한 줄이 저장소를 정했습니다. 풀어 보면 이렇습니다.

| 요구의 조각 | 필요한 것 |
| --- | --- |
| 문서의 판(버전)으로 거른다 | 관계형 조건 검색 |
| 보안등급으로 거른다 | 사용자 등급과 대조 — 조인 |
| 비슷한 것을 찾는다 | 벡터 유사도 검색 |

전용 벡터 DB는 세 번째를 더 잘합니다. 그런데 앞의 둘은 이미 쓰고 있는 PostgreSQL에 있는 것입니다. 벡터를 따로 두면 두 곳을 오가며 맞춰야 하고 스택에 하나가 더 늘어납니다. `pgvector`는 쓰던 DB에 확장을 하나 켜는 것이라 늘어나는 게 없습니다.

"더 잘하는 것"과 "우리 요구에 맞는 것"이 다르다는 게 요점이었습니다.

지금까지 만든 것이 지도의 어디인지도 짚어봤습니다. 열여섯 칸 중 열 칸이 찼고 남은 게 청킹·검색·도구 연동·외부 실행·배포·CI입니다.

## 2. 임베딩 모델 — 4.3GB를 저장소 밖에 둔다

RAG의 네 번째 단계인 임베딩은 글자를 숫자 배열로 바꾸는 일입니다. 그 일을 할 모델을 내 컴퓨터에 받았습니다.

API로 부를 수도 있는데 로컬을 골랐습니다.

| | API | 로컬 |
| --- | --- | --- |
| 문서가 나가는가 | 나간다 | 안 나간다 |
| 비용 | 문서 수에 비례 | 0 |
| 준비 | 키 하나 | 4.3GB 내려받기 |

사내 규정 문서가 대상이고 대외비 등급이 섞여 있습니다. 그걸 바깥으로 보내는 것은 기술 선택이 아니라 보안 결정입니다. 그리고 임베딩은 문서를 올릴 때 전부 한 번씩 돕니다. 질문당 한 번인 LLM 호출과 다릅니다.

두 개를 받았습니다. 고려대에서 만든 `KURE-v1`과 다국어 모델 `bge-m3`입니다. 비교하려고 둘 다 받았습니다.

받는 스크립트에 판단이 몇 개 들어 있었습니다.

```python
"files": ["pytorch_model.bin", "config.json", "tokenizer.json", ...],
"sizes": {"pytorch_model.bin": 2_271_145_830},
```

저장소 전체를 받지 않습니다. `bge-m3`는 `onnx/`에 같은 가중치 사본이 또 있어서(2.27GB) 전체를 받으면 쓰지도 않는 걸 더 받습니다.

크기를 바이트까지 대조합니다. 받다가 끊겨도 파일은 남습니다. 이름만 보면 다 있는 것처럼 보이는데 내용이 잘려 있습니다. 어제 정리한 "에러가 나지 않는 실패"와 같은 종류라 크기를 재는 것이 유일한 확인 방법입니다.

받은 것은 저장소 밖에 둡니다.

```text
workspace/
├── hanwha-agent/        ← 저장소
└── models/              ← 저장소 밖, 같은 층
    ├── KURE-v1/   2.2GB
    └── bge-m3/    2.2GB
```

4.3GB를 커밋하면 clone이 불가능해지고 한 번 들어가면 히스토리에서 빼기도 어렵습니다. `.gitignore`에 넣었습니다. 저장소에는 받는 법만 있고 받은 것은 없습니다.

## 3. HWPX — ZIP 안의 XML이다

`.hwp`와 `.hwpx`는 다른 형식이고 한쪽만 읽을 수 있었습니다.

| | HWPX | HWP |
| --- | --- | --- |
| 무엇인가 | ZIP 안의 XML | 한컴 독자 바이너리 |
| 표준 | KS 국가 표준 | 공개 표준이 아니다 |
| 파이썬 | 표준 라이브러리만으로 읽는다 | 유일한 파서가 5년 넘게 릴리즈 없음 |

`.hwpx`는 라이브러리를 새로 들이지 않아도 됩니다. `zipfile`과 `xml.etree`가 표준 라이브러리라 오전에 본 "무엇이 하나 더 늘어나는가" 기준에서 0입니다.

열어보니 워드와 같은 ZIP 표식이었습니다.

```text
항목 수 : 10
  mimetype                   application/hwp+zip (19바이트)
  Contents/section0.xml      ← 본문
  Contents/header.xml        서식
  settings.xml               커서 위치
  Preview/PrvText.txt        미리보기용 짧은 글자
```

```text
열 개 전체의 압축 방식 : {0}    (0 = 압축한 것이 아니라 그대로 넣었다)
```

열 개 전부 압축되어 있지 않습니다. ZIP은 담는 그릇으로만 쓰고 내용은 그대로 뒀습니다.

XML을 읽다가 두 번 걸렸습니다. 먼저 네임스페이스입니다.

```python
root.findall('p')
```

```text
findall('p') 결과 : []
찾은 개수         : 0

에러가 났습니까?  → 아니요. 조용히 빈 목록이 돌아왔습니다.
```

HWPX의 태그는 이름 앞에 주소가 붙어 있습니다. 주소를 붙이니 237개가 나왔습니다. 0과 237 사이에 예외가 없습니다.

두 번째는 `.text`가 `None`일 수 있다는 것이었습니다.

```text
TypeError: sequence item 0: expected str instance, NoneType found
```

```text
글자 태그     : 450 개
.text 가 None : 41 개
```

빈 태그의 `.text`는 빈 문자열이 아니라 `None`입니다. 450개 중 41개인데 한 개만 있어도 전체가 멈춥니다. 237개 문단을 훑다 중간에서 끊기면 그 뒤는 시도조차 못 합니다. `or ""` 한 조각으로 끝났습니다.

## 4. findall과 iter — 같은 글이 두 번 들어온다

XML을 훑는 방법이 둘인데 결과가 크게 갈렸습니다.

| | 어디를 보나 |
| --- | --- |
| `findall("태그")` | 바로 아래 자식 전부 |
| `iter("태그")` | 자기 아래 모든 깊이 |

```text
findall 로 모은 블록 : 233
iter    로 모은 블록 : 416
차이                 : +183
```

늘어난 183개가 무엇인지 확인했습니다.

```text
늘어난 블록 : 183 개
표 안에 있던 문단 : 133 종류
늘어난 것이 전부 표 안 문장인가 : True
```

표 안의 문단이 두 번씩 들어온 것이었습니다. 표를 담은 문단을 한 번 세고 그 안의 문단을 또 셉니다.

중복은 에러로 걸리지 않고 그대로 지나갑니다. 그런데 이 블록들이 검색에 들어가면 같은 내용이 여러 조각으로 앉습니다. 검색 결과 상위가 같은 말로 채워지고 프롬프트에 중복이 실려 토큰만 늘어납니다.

규칙 하나로 정리했습니다. **구조를 훑을 때는 `findall`(직계), 글자를 긁을 때는 `iter`(모든 깊이).** 구조에 `iter`를 쓰면 중복되고 글자에 `findall`을 쓰면 빠집니다.

## 5. 표 — DOCX와 완전히 같은 결과가 나온다

표가 들어 있는 자리는 이렇게 생겼습니다.

```text
hp:p                          ← 표를 "담은" 문단
└── hp:run
    └── hp:tbl  rowCnt="4" colCnt="7"
        └── hp:tr                             행
            └── hp:tc  header="1"             칸
                └── hp:subList
                    └── hp:p → hp:run → hp:t  ← 실제 글자
```

어제 만든 `_table_to_markdown`을 그대로 썼습니다. 형식이 달라도 표를 담는 모양은 하나라 함수를 다시 만들지 않았습니다.

코드에서 `continue` 한 줄이 중요했습니다.

```text
continue 있음 : 233
continue 없음 : 240
차이           : 7
```

`continue`가 없으면 표 하나가 블록 두 개가 됩니다. 마크다운 표 하나와, 같은 내용을 이어 붙인 문단 하나입니다. 표가 7개라 정확히 7이 늘었습니다.

같은 문서를 세 형식으로 읽어 견주면 이렇습니다.

```text
형식        블록    표    쪽수
HWPX     233    7     1
DOCX     233    7     1
PDF       16    0    16
```

**HWPX와 DOCX가 완전히 같습니다.** 둘 다 ZIP + XML이고 문단과 표가 구조로 남아 있어서 원문 순서대로 훑으면 같은 결과가 나옵니다.

이 일치를 테스트로 박았습니다. 숫자를 따로 적어두는 것보다 두 파서가 서로를 검산하게 하는 쪽이 낫습니다. 한쪽을 고쳐서 결과가 달라지면 바로 걸립니다.

## 6. parse_local — 결말이 셋이다

파서가 셋이 됐으니 어느 파일을 어느 파서로 보낼지 정하는 자리가 필요했습니다. 없을 때 어떻게 되는지부터 봤습니다.

```text
훑은 파일   : 24건
읽힘        : 20건
조용히 빠짐 : 4건
```

`.hwpx` 세 건이 아무 말 없이 빠졌습니다. `continue`가 정상 흐름이라 로그도 예외도 없습니다. 문서를 올린 사람은 성공한 줄 압니다.

진입점을 만들면서 결말을 셋으로 뒀습니다.

| 결말 | 언제 | 왜 |
| --- | --- | --- |
| 예외 | 형식이 안 맞는다 | 사용자가 고칠 수 있다 |
| `None` + 로그 | 파서가 터졌다 | 사용자가 할 수 있는 게 없다 |
| 예외 | 읽었는데 글자가 0 | 스캔본일 수 있다 — 안내가 있다 |

읽을 수 없는 형식도 두 종류로 나눴습니다.

```text
[.hwp] 읽을 수 없는 형식입니다: .hwp
      안내 → 한글에서 열고 [다른 이름으로 저장] → HWPX 또는 PDF 로 내보내세요…
[.rtf] 지원하지 않는 형식입니다: .rtf
      안내 → 핸들러를 추가하면 지원할 수 있습니다
```

하나는 사용자가 할 일이 있고 하나는 우리가 할 일이 남은 것입니다. 같은 "안 됨"으로 묶으면 둘 다 고쳐지지 않습니다.

## 7. 받아온 문서로 — 표가 있던 곳은 PDF였다

연습 재료는 수업에 맞춰 만든 것이라 표가 반듯하고 글자도 빠짐없이 박혀 있습니다. 실제로 공개된 문서를 받아 같은 파서에 넣어봤습니다. 법령 두 건(hwpx)과 보고서 세 건(pdf)입니다.

```text
개인정보 보호법(법률)(제21445호).hwpx
  ParsedDoc(blocks=1151, page_count=1, table_count=1)
  문단 1150개 · 표 1개 · 파싱 0.0초

글로벌 AI 보안 동향 조사·분석 보고서(2026)_6호.pdf
  ParsedDoc(blocks=13, page_count=13, table_count=0)
  문단 13개 · 표 0개 · 파싱 0.5초
```

다섯 건 전부 읽혔습니다. 그런데 표를 세어보니 둘뿐이었고 그 둘이 이랬습니다.

```text
문서                                   표    행   열   첫 줄
개인정보 보호법(...).hwpx               표1    0   1   | 개인정보 보호법 |
도로교통법(...).hwpx                    표1    0   1   | 도로교통법 |
```

**본문 행이 0**입니다. 법령 맨 위의 제목 상자를 표로 그려둔 것뿐이었습니다. 법령은 조문이 전부 글이라 표를 거의 쓰지 않습니다.

표가 정말로 있던 곳은 PDF 보고서였는데 `parse_pdf`는 표를 찾지 않습니다. 어제 배운 `pdfplumber`로 따로 꺼냈습니다.

```text
GNSM_..._정보보안전문가.pdf          표   3개    0.2초
TTPs_2_스피어_피싱....pdf            표  13개   13.8초
글로벌 AI 보안 동향....pdf           표  17개    1.3초

PDF 표 합계 33개
```

그런데 33개가 다 표는 아니었습니다.

```text
── p.1  1행 2열
    | 수업 지도안 | 정보보안전문가 |     ← 머리글 영역이 선으로 그려져 표로 잡힘
```

머리글·바닥글 영역이 선으로 그려져 있으면 표로 잡힙니다. 행이 셋 이상, 열이 둘 이상, 빈 칸이 40% 이하인 것만 남기니 9개가 됐습니다.

```text
문서                            전체   남김   버림
GNSM_..._정보보안전문가.pdf          3    1    2
TTPs_2_스피어_피싱....pdf           13    3   10
글로벌 AI 보안 동향....pdf          17    5   12
```

남은 것들은 머리 행만 봐도 무슨 표인지 압니다.

```text
p.1    단계 | 학습 과정 | 교수 - 학습 활동 | 학습자료 및 유의점
p.3    시점 | 핵심 조치 | 세부 실행 내용
p.9    통제 대상 | 관리·통제 초점 | 강제·대응 방식
```

어제 배운 두 가지도 그대로 나왔습니다.

```text
칸 339개
  None 인 칸          57개   ← 병합된 자리
  줄바꿈이 든 칸      56개   ← 마크다운 행을 갈라버린다
```

처리하지 않았으면 모아둔 파일이 통째로 깨집니다. 최종적으로 표 11개를 마크다운 파일 하나에 담았습니다.

## 이날의 소감

18일차는 **오전에 배운 기준을 오후에 써먹은 날**이었습니다.

오전에 도구를 먼저 고르지 말라고 배웠습니다. 그런데 그 "필요한 것"이 어디서 나오는지는 오후에 알았습니다. 문서에서 나옵니다. 사내 규정은 표에 금액과 기한이 들어 있어 표 추출이 핵심이었습니다. 법령은 조문이 전부 글이고 표는 장식이었습니다. 같은 파서로 둘 다 읽히지만 쓸 만한 결과인지는 다른 문제였습니다.

국비지원교육 과정에서 받은 연습 재료만 썼다면 "우리 파서는 표를 잘 잡는다"로 끝났을 것입니다. 받아온 문서를 넣고 나서야 표가 둘뿐이고 그 둘도 빈 상자라는 것을 봤습니다. 파서가 쓸 만한지는 코드만 봐서는 모르고 읽힐 문서를 넣어봐야 알게 됩니다.

`pdfplumber`가 33개를 찾았을 때도 같은 일이 있었습니다. 숫자만 보면 성공인데 열어보니 4분의 3이 머리글이었습니다. 표를 33개 뽑았다고 보고하면 24개가 빈 상자라는 것은 아무도 모릅니다. 세어보는 것으로는 부족하고 몇 개는 열어봐야 합니다.

중복도 같은 종류였습니다. `iter`로 모으면 183개가 더 나오는데 에러가 아닙니다. 데이터가 늘어난 것처럼 보이지만 검색에서는 같은 말이 상위를 채웁니다. 우리가 만드는 것이 검색해서 답하는 시스템이라 **조용히 늘어나는 것이 조용히 빠지는 것만큼 위험하다**고 배웠습니다.

파서는 이제 세 형식을 읽습니다. 그런데 오늘 확인한 것들을 보면 읽는 것과 쓸 수 있게 만드는 것 사이가 아직 멉니다. 다음 포스팅에서는 이어서 배운 내용을 정리해보겠습니다.
