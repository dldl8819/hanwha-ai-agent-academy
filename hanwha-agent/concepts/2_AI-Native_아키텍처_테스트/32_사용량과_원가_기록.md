# 사용량과 원가 기록

[[31_관측과_실행_기록]]에서 질문 한 건을 `runs`에 남겼다. 여기서는 **호출 한 번**을 `usage_logs`에 남긴다. 둘은 다른 단위다.

| 표 | 단위 | 재시도가 2회 돌면 |
| --- | --- | --- |
| `runs` | 질문 한 건 | 1행 |
| `usage_logs` | 모델 호출 한 번 | **2행** |

## 테이블

### `backend/app/models/usage.py`

```python
class UsageLog(Base, TimestampMixin):
    __tablename__ = "usage_logs"

    id: Mapped[int] = mapped_column(primary_key=True)
    run_id: Mapped[str] = mapped_column(ForeignKey("runs.id"), nullable=False)
    model: Mapped[str] = mapped_column(String(64))

    input_tok: Mapped[int] = mapped_column(Integer, default=0)
    cache_tok: Mapped[int] = mapped_column(Integer, default=0)
    output_tok: Mapped[int] = mapped_column(Integer, default=0)

    cost_krw: Mapped[float] = mapped_column(Float, default=0.0)
    occurred_at: Mapped[datetime] = mapped_column(default=datetime.now)
```

| 컬럼 | 왜 남기는가 |
| --- | --- |
| `run_id` | `runs.id`를 가리키는 FK. 질문 한 건에 호출 여러 건을 묶는다 |
| `model` | 모델마다 단가가 다르다. 나중에 모델을 바꿨을 때 비용이 어떻게 변했는지 이 컬럼이 없으면 알 수 없다 |
| `input_tok` / `output_tok` | 출력이 입력보다 5배 비싸서([[24_API_토큰과_과금]]) 합계만으로는 원가를 설명할 수 없다 |
| `cache_tok` | 캐시 읽기는 단가가 따로 있다. 지금은 원가 계산에 반영하지 않지만 값은 미리 남겨 둔다 |
| `cost_krw` | 계산해서 저장한다. 나중에 단가표가 바뀌어도 **그때의 원가**가 보존된다 |

`cost_krw`를 조회할 때마다 계산하지 않고 저장해 두는 이유가 중요하다. 단가와 환율은 바뀐다. 저장해 두지 않으면 작년 사용량을 올해 단가로 다시 계산하게 된다. `sources`를 JSON으로 통째로 남긴 것과 같은 판단이다 — **그때 이렇게 됐다는 스냅샷**이다.

`TimestampMixin`이 `created_at`을 이미 주는데 `occurred_at`을 따로 둔 것은, 기록을 나중에 몰아서 적재하는 경우 "행이 만들어진 시각"과 "호출이 일어난 시각"이 달라질 수 있어서다.

### 리비전

```bash
alembic -c backend/alembic.ini revision --autogenerate -m "add usage_logs"
alembic -c backend/alembic.ini upgrade head
```

`models/__init__.py`에 `UsageLog`를 import 해야 autogenerate가 이 표를 본다. 빠뜨리면 에러 없이 **빈 리비전 파일**이 나온다([[21_Alembic_마이그레이션]]).

## 기록하는 자리 — 검증 전이다

### `backend/app/services/chat_service.py`

```python
def _record_usage(run_id: str, result) -> None:
    try:
        with session_scope() as session:
            session.add(
                UsageLog(
                    run_id=run_id, model=result.model,
                    input_tok=result.input_tok, cache_tok=result.cache_tok,
                    output_tok=result.output_tok, cost_krw=result.cost_krw,
                )
            )
    except Exception as e:
        log.warning("사용 기록 실패(무시하고 계속): %s", e)
```

```python
result = llm.answer(question=prompt, contexts=NO_CONTEXTS, user=DEFAULT_USER)

_record_usage(run_id, result)      # ← 검증하기 전에 기록한다

try:
    data = _extract_json(result.text)
    AnswerOut.model_validate(data)
except ValidationError as e:
    ...
    continue
```

**이 순서가 전부다.** 응답이 형식을 어겨 버려지더라도 그 호출의 토큰은 이미 과금됐다. 통과한 호출만 기록하면 재시도로 나간 비용이 장부에서 통째로 빠진다.

확인해 보면 `attempts`와 행 수가 정확히 같다.

```text
① 한 번에 성공        RUN-8860  attempts=1  usage_logs 1건
   WARNING  스키마 위반 1/3회 : sources: Field required
② 한 번 실패 후 성공  RUN-8861  attempts=2  usage_logs 2건
```

`try/except Exception`으로 삼키는 것도 [[31_관측과_실행_기록]]의 `langfuse_client`와 같은 판단이다. **기록에 실패해도 답변은 나가야 한다.** 대신 조용히 넘어가므로 대가가 있다 — 실제로 `usage_logs` 리비전을 적용하기 전에는 이 경고만 찍히고 테스트가 전부 통과했다. 통과하는데 행이 안 쌓이면 이 자리를 먼저 본다.

## 집계

`runs`와 `users`까지 조인하면 사람별로 얼마를 썼는지 나온다.

```python
per_person = session.execute(
    select(User.name, User.emp_no, func.count(UsageLog.id), func.sum(UsageLog.cost_krw))
    .join(Run, UsageLog.run_id == Run.id)
    .join(User, Run.user_id == User.id)
    .group_by(User.name, User.emp_no)
).all()
```

```text
***사람별 결과***
 김민준 (2019-0412) : 19건 52.7원
***토큰 비중***
 입력 22800, 출력 5700
 출력 비중 : 20.0 %
```

조인이 두 단계인 이유는 **`usage_logs`에 `user_id`가 없기 때문**이다. 호출은 질문에 속하고 질문이 사람에 속한다. 사용량 표에 사람을 직접 달아두면 빨라지지만, 같은 사실이 두 곳에 적혀 어긋날 수 있다. 지금 규모에서는 조인이 맞다.

출력 비중을 따로 보는 이유는 단가 때문이다. 토큰 수로는 출력이 20%지만 단가가 5배라, **비용으로는 절반 이상**이 출력에서 나온다. 비용을 줄이려면 `max_tokens`를 조이거나 "짧게 답하라"를 프롬프트에 넣는 쪽이 입력을 줄이는 것보다 효과가 크다.

## 컬럼 이름 바꾸기 — autogenerate 를 쓰면 안 되는 경우

처음에는 컬럼 이름을 `occured_at`(r 한 개)으로 잘못 적었다. 동작에는 문제가 없었다. 모델·리비전·실제 테이블이 **모두 같은 철자로 틀려 있었기 때문**이다. 이런 오타는 에러로 드러나지 않고, 나중에 쿼리를 짜는 사람이 바른 철자로 적었다가 걸린다.

고칠 때 `--autogenerate`를 쓰면 안 된다.

```python
# autogenerate 가 적어주는 것 — 이름이 바뀐 줄 모른다
op.drop_column("usage_logs", "occured_at")
op.add_column("usage_logs", sa.Column("occurred_at", sa.DateTime(), nullable=False))
```

없어진 컬럼 하나와 새로 생긴 컬럼 하나로 볼 뿐이라, 그대로 실행하면 **기존 행의 값이 전부 사라진다.** 이름만 바꾸려면 손으로 적는다.

```python
def upgrade() -> None:
    op.alter_column(
        "usage_logs", "occured_at",
        new_column_name="occurred_at",
        existing_type=sa.DateTime(),
        existing_nullable=False,
    )
```

`existing_type`과 `existing_nullable`은 바꾸려는 값이 아니라 **지금 그대로인 값**을 알려주는 인자다. 일부 DB는 컬럼을 고칠 때 전체 정의를 다시 써야 해서, Alembic 이 문장을 만들려면 이 정보가 필요하다.

```text
INFO  [alembic.runtime.migration] Running upgrade cbd68bb8e46d -> 9f2a041f60ca,
      rename usage_logs.occured_at to occurred_at
```

```text
 occurred_at | timestamp without time zone |  | not null |
```

적용 전후로 행 수가 35건 그대로였다. 이름만 바뀌고 값은 남았다.

**먼저 만든 리비전(`cbd68bb8e46d`)의 `occured_at`은 고치지 않는다.** 이미 적용한 사람의 DB 는 그 이름으로 만들어져 있어서, 과거 리비전을 고쳐 쓰면 기록과 실제가 어긋난다. 마이그레이션 이력은 **무엇이 있었는지를 남기는 기록**이지 현재 상태를 적는 문서가 아니다.

고친 뒤에는 모델과 DB 가 맞는지 확인한다.

```bash
alembic -c backend/alembic.ini check
# No new upgrade operations detected.
```

## 짚어둘 것

**테스트가 개발 DB에 쓴다.** `ask()`가 DB에 기록하게 되면서, 골든셋 테스트([[29_골든셋_회귀테스트]])를 한 번 돌릴 때마다 `runs`와 `usage_logs`에 행이 쌓인다. `attempts`가 2·3인 문항이 있어 사용량 행은 더 빨리 는다. 뒤에 `conftest.py` 에 fixture 를 넣어 테스트가 임시 SQLite 를 쓰게 고쳤다 — [[29_골든셋_회귀테스트]].
