# 가드와 재시도·폴백

[[27_구조화_출력]]까지는 모델에게 요청하고 응답을 검증하는 흐름을 만들었다. 여기서는 그 앞뒤를 감싼다. **요청 전에는 가드로 거르고, 응답이 규칙을 어기면 재시도하고, 끝내 안 되면 폴백으로 빠진다.**

```text
질문 ──▶ 가드 ──▶ 모델 호출 ──▶ 스키마 검증 ──▶ 응답
          │                         │
       막음(400/429)           실패 → 재시도(최대 2회) → 끝내 실패 → 폴백
```

## 가드 함수 — 모델로 보내기 전에 거른다

질문이 비어 있거나 지나치게 길면 모델을 부를 이유가 없다. 호출 한 번이 돈과 시간이라서([[24_API_토큰과_과금]]), **보내기 전에 걸러야 할 것은 보내기 전에 거른다.** [[22_AI_Native_애플리케이션]]의 "상한과 계측은 처음부터"를 코드로 옮긴 자리다.

### `backend/app/core/guards.py`

```python
MIN_QUESTION_LEN = 2
ALLOWED_MODELS = {"claude-haiku-4-5"}

def check_question(text: str) -> str:
    settings = get_settings()
    q = (text or "").strip()
    if len(q) < MIN_QUESTION_LEN:
        raise GuardTripped("질문이 비어 있거나 너무 짧습니다.")
    if len(q) > settings.max_input_chars:
        raise GuardTripped(
            f"질문이 너무 깁니다. ({len(q)}자)"
            f"{settings.max_input_chars}자 이내로 줄여주세요."
        )
    return q

def check_model(model: str) -> str:
    if model not in ALLOWED_MODELS:
        raise GuardTripped(f"허용되지 않은 모델입니다. : {model}")
    return model

def check_daily_limit(used_today: int) -> None:
    settings = get_settings()
    if used_today >= settings.daily_call_limit:
        raise RateLimited(f"오늘 호출 한도({settings.daily_call_limit}회)를 모두 사용했습니다.")
```

- **`check_question`은 검사만 하지 않고 정리된 문자열을 돌려준다.** `(text or "")`로 `None`도 받아내고, `.strip()`으로 앞뒤 공백을 지운 값을 넘긴다. 공백 세 칸짜리 질문은 정리하고 나면 0자라서 걸린다
- 길이 상한은 코드에 숫자로 박지 않고 설정(`MAX_INPUT_CHARS`)에서 읽는다
- 모델은 **허용 목록** 방식이다. 막을 것을 나열하는 대신 쓸 수 있는 것만 적어둔다. 목록에 없는 비싼 모델로 실수로 바뀌어도 여기서 멈춘다. 다만 `.env`의 `LLM_MODEL`을 바꾸면 이 목록도 같이 고쳐야 한다
- `check_daily_limit`은 `>=`로 비교한다. 이미 200회를 썼으면 201번째가 아니라 **지금 이 호출부터** 막는다

예외도 두 가지로 나눴다([[05_예외_계층_설계]]).

| 예외 | 상태 코드 | 뜻 |
| --- | --- | --- |
| `GuardTripped` | 400 | 요청 자체가 규칙에 안 맞는다 (질문 길이, 모델) |
| `RateLimited` | 429 | 요청은 맞는데 한도를 다 썼다 |

실행 결과다.

```text
허용 모델      : {'claude-haiku-4-5'}

정상 질문      : 통과 → "부산 출장 숙박비 한도가 얼마인가요?"
공백 세 칸     : GuardTripped (400) 질문이 비어 있거나 너무 짧습니다.
아주 긴 질문   : GuardTripped (400) 질문이 너무 깁니다. (2001자)2000자 이내로 줄여주세요.
허용 밖 모델   : GuardTripped (400) 허용되지 않은 모델입니다. : claude-opus-4-1
한도 초과      : RateLimited (429) 오늘 호출 한도(200회)를 모두 사용했습니다.
```

`(2001자)2000자`처럼 붙은 것은 괄호 안에서 f-string 두 개를 나란히 이어 쓸 때 사이에 공백이 없어서다. 파이썬은 나란히 놓인 문자열을 **그대로 이어 붙인다.** 앞 문자열 끝에 공백을 하나 두면 된다([[23_포트와_어댑터]]의 factory 에러 메시지와 같은 문제).

### 테스트 — `backend/tests/test_guards.py`

```python
def test_check_question_rejects_blank() -> None:
    with pytest.raises(GuardTripped):
        check_question("   ")

def test_check_daily_limit_raises_when_exhausted() -> None:
    limit = get_settings().daily_call_limit
    check_daily_limit(limit - 1)            # 한 번 남았을 때는 통과
    with pytest.raises(RateLimited):
        check_daily_limit(limit)            # 다 썼을 때부터 막는다
```

- `pytest.raises(예외)` — 블록 안에서 **그 예외가 나야 통과**한다. 안 나면 실패다
- 한도 테스트는 **경계값 양쪽**을 모두 찍는다. `limit - 1`은 통과, `limit`은 실패. `>`와 `>=`를 헷갈리면 정확히 이 경계에서 드러난다
- 길이 상한은 `limit + 1`로 테스트한다. 설정값이 바뀌어도 테스트를 고칠 필요가 없다

#### 실습 중 만난 이슈: 테스트가 틀려서 실패했다

```python
def test_check_question_passed_and_strips() -> None:
    assert check_question("  제주도 출장 숙박비 한도가 얼마인가요?  ") == "제주도 출장 숙박비 한도가 얼마인가요"
```

```text
AssertionError: assert '제주도 출장 숙박비 한도가 얼마인가요?' == '제주도 출장 숙박비 한도가 얼마인가요'
1 failed, 24 passed
```

기대값에서 물음표가 빠져 있다. `.strip()`은 **앞뒤 공백만** 지우고 문장부호는 건드리지 않으니, 코드는 맞게 동작했고 테스트가 틀렸다.

테스트가 실패했다고 항상 코드가 틀린 것은 아니다. 실패 메시지의 `-`(기대)와 `+`(실제)를 비교해서 **어느 쪽이 의도와 다른지** 먼저 판단해야 한다. 여기서 코드를 "통과하게" 고치면(물음표까지 지우게 하면) 멀쩡한 동작을 망가뜨리게 된다.

#### 실습 중 만난 이슈: 파일 이름이 두 개로 갈렸다

교안에서는 파일을 `guard.py`로 만들고, 테스트와 서비스는 `app.core.guards`로 import 했다. 파일을 `guards.py`로 맞추면 테스트는 통과하지만, 오전에 만든 노트북은 여전히 `from app.core.guard import ...`라서 이번에는 노트북이 `No module named 'app.core.guard'`로 실패한다. 이름을 바꿀 때는 **그 이름을 부르는 곳을 전부** 찾아서 같이 바꿔야 한다.

## 스키마 검증 — 모델은 형식을 어긴다

JSON 으로 답하라고 시켜도 모델은 가끔 필드를 빼먹거나, 타입을 틀리거나, 앞에 잡담을 붙인다. 세 가지를 직접 넣어봤다.

```python
CASES = [
    ("ⓐ 필드 누락  ", '{"answer": "1박 70,000원 이내입니다.", "enough_evidence": true}'),
    ("ⓑ 타입 어긋남", '{"answer": "...", "sources": "DOC-HR-014", "enough_evidence": true}'),
    ("ⓒ 잡담이 앞에", '네, 알겠습니다!\n{"answer": "...", "sources": [], "enough_evidence": false}'),
]
for label, raw in CASES:
    try:
        AnswerOut.model_validate_json(raw)
    except ValidationError as e:
        first = e.errors(include_url=False)[0]
        print(f"{label} : loc={first['loc']} / type={first['type']} / {first['msg']}")
```

```text
ⓐ 필드 누락   : loc=('sources',) / type=missing   / Field required
ⓑ 타입 어긋남 : loc=('sources',) / type=list_type / Input should be a valid array
ⓒ 잡담이 앞에 : loc=()           / type=json_invalid / Invalid JSON: expected value at line 1 column 1
```

`e.errors()`는 **어디가(`loc`) 어떤 종류로(`type`) 틀렸는지**를 구조로 준다. 사람이 읽을 메시지(`msg`)만 있는 게 아니라서 재시도할 때 "무엇이 틀렸는지"를 그대로 프롬프트에 붙일 수 있다. `include_url=False`는 오류마다 붙는 Pydantic 문서 링크를 뺀다.

세 경우는 성격이 다르다.

- **ⓒ는 받는 쪽에서 고칠 수 있다.** [[27_구조화_출력]]의 `_extract_json`을 거치면 JSON 부분만 남아 정상 통과한다
- **ⓐ ⓑ는 내용 자체가 틀렸다.** 받는 쪽에서 채울 수 없으니 모델에게 다시 받아야 한다 → 재시도

## 재시도

| 정할 것 | 이 프로젝트 |
| --- | --- |
| 몇 번 | 최대 2회 — 첫 호출 포함 총 3회 |
| 무엇을 바꾸나 | **직전에 무엇이 틀렸는지를 프롬프트에 붙인다** |
| 언제 포기 | 2회를 다 쓰면 폴백 |

같은 요청을 그대로 다시 보내는 게 아니라, `e.errors()`에서 뽑은 오류(예: `sources` 필드 누락)를 알려주고 다시 받는다. 모델이 어디를 고쳐야 하는지 알고 답하게 된다.

재시도에는 상한이 반드시 있어야 한다. **재시도 한 번이 곧 호출 한 번**이라, 3회까지 가면 비용과 대기 시간도 최대 3배가 된다.

### 재시도하면 안 되는 실패

| 실패 | 다시 부르면? | 판정 |
| --- | --- | --- |
| 스키마 위반 `ValidationError` | 다른 답이 올 수 있다 | 재시도 |
| 529 과부하, 타임아웃 | 잠시 뒤면 될 수도 있다 | 재시도 |
| 401 키가 틀렸다 | 백 번 불러도 안 된다 | 재시도 X |
| 429 한도를 다 썼다 | **부를수록 나빠진다** | 재시도 X |
| 400 요청 자체가 틀렸다 | 똑같이 틀린다 | 재시도 X |
| `GuardTripped` (우리가 막음) | 막으려고 만든 것 | 재시도 X, 폴백 X |

기준은 **"다시 부르면 결과가 달라질 수 있는가"**다. 모델의 무작위성이나 일시적 장애는 달라질 수 있지만, 키·한도·요청 형식 문제는 몇 번을 불러도 같다. 429에서 재시도하면 한도를 더 소모해서 오히려 상황을 악화시킨다([[25_Claude_API_호출]]의 실패 유형 표와 같은 판단).

`GuardTripped`는 폴백도 하지 않는다. 우리가 **일부러 막은 것**이라, 폴백 답변을 내주면 가드를 둔 의미가 없어진다. 사용자에게 "질문이 너무 깁니다"를 그대로 알려주는 게 맞다.

## 폴백

재시도까지 다 실패하면 더 이상 모델에 매달리지 않고 **미리 정해둔 안전한 길**로 간다.

| 흔한 폴백 | 예 |
| --- | --- |
| 안전한 기본 응답 | "근거를 확인하지 못했습니다" |
| 다른 모델로 교체 | 더 큰 모델로 한 번 더 |
| 기능 축소 | 요약 없이 검색 결과만 보여주기 |

이 프로젝트는 **안전한 기본 응답**을 쓴다.

```python
answer = "요청을 처리했지만 근거를 확인하지 못했습니다. 담당부서에 문의해 주세요"
sources = []
enough_evidence = False
fallback_used = True
```

중요한 점은 에러가 아니라 **유효한 응답 객체**로 돌려준다는 것이다. 화면은 평소와 같은 모양의 데이터를 받으니 깨지지 않고, 대신 `fallback_used`를 보고 "폴백 답변입니다" 같은 표시를 따로 붙일 수 있다.

### `AskOut` — 폴백인지 구분하는 필드

```python
class AskOut(AnswerOut):
    run_id: str = Field(description="이 질문 한 건의 실행 번호. 예: RUN-1234")
    attempts: int = Field(default=1, description="스키마 검증에 성공하기까지 부른 횟수")
    fallback_used: bool = Field(default=False, description="세 번 모두 실패해 폴백 답변으로 대처한 여부")
```

`AnswerOut`을 **상속**해서 `answer`·`sources`·`enough_evidence`는 그대로 쓰고, 실행 정보 세 개만 더했다.

```text
AskOut 필드 : ['answer', 'sources', 'enough_evidence', 'run_id', 'attempts', 'fallback_used']
기본값      : attempts=1 · fallback_used=False
```

| 필드 | 왜 필요한가 |
| --- | --- |
| `run_id` | 질문 한 건을 로그와 화면에서 같은 번호로 찾아가기 위해 |
| `attempts` | 몇 번 만에 성공했는지. 재시도가 잦으면 프롬프트를 고쳐야 한다는 신호 |
| `fallback_used` | 이 답이 모델의 답인지 폴백인지 |

재현할 수 없는 LLM 호출에서는 기록이 유일한 증거라([[22_AI_Native_애플리케이션]]) `run_id`로 이 세 가지를 묶어두는 게 운영에서 중요해진다.

## 한 곳에 모으기 — `chat_service.ask()`

가드·호출·검증·재시도·폴백은 흩어두면 순서가 어긋난다. **서비스 함수 하나 안에 순서대로** 넣는다.

### `backend/app/services/chat_service.py`

```python
def ask(*, question: str, run_id: str = "RUN-0000") -> AskOut:
    q = check_question(question)          # 1. 가드 — 여기서 난 예외는 그대로 위로 올라간다
    llm = factory.get_llm()               # 2. 어댑터 한 개
    hint = ""
    for attempt in range(1, MAX_ATTEMPTS + 1):
        prompt = q if not hint else f"{q}\n\n[직전 응답의 문제] {hint}\n출력 형식을 지켜 다시 답해 주세요."
        result = llm.answer(question=prompt, contexts=NO_CONTEXTS, user=DEFAULT_USER)
        try:
            data = _extract_json(result.text)
            AnswerOut.model_validate(data)                 # 3. 규격 검사
        except ValidationError as e:
            hint = _hint_from(e.errors(include_url=False))  # 무엇이 틀렸는지를 다음 프롬프트로
            log.warning("스키마 위반 %d/%d회 : %s", attempt, MAX_ATTEMPTS, hint)
            continue
        return AskOut(**data, run_id=run_id, attempts=attempt, fallback_used=False)
    return _fallback(run_id, MAX_ATTEMPTS)                  # 4. 세 번 다 실패 → 폴백
```

읽을 점 세 가지.

- **`GuardTripped`는 `try` 밖에 있다.** 가드는 우리가 일부러 막은 것이라 재시도도 폴백도 하지 않고 그대로 전역 핸들러까지 올라간다
- **`except`가 `ValidationError` 하나뿐이다.** 지어낸 형식만 재시도 대상이고, 401·429 같은 실패는 잡지 않아 그대로 올라간다
- **성공은 `return`, 실패는 `continue`.** `for`를 끝까지 돌았다는 것 자체가 "다 실패했다"는 뜻이라 별도 플래그가 필요 없다

로그는 `log.warning(f"...{hint}")`가 아니라 `log.warning("... %s", hint)`로 쓴다. `%s` 자리를 남겨두면 로그 레벨이 올라가 안 찍힐 때 문자열을 조립하는 비용조차 들지 않고, 로그 수집 도구가 "같은 메시지의 다른 값"으로 묶어 셀 수 있다([[06_로깅]]).

## 라우터 연결 — `/api/v1/chat/messages`

붙일 자리를 먼저 정한다.

| | |
| --- | --- |
| 메서드 + 경로 | `POST /api/v1/chat/messages` |
| 요청 본문 | `ChatRequest` |
| 응답 | `AskOut` |
| 실패 | 전역 핸들러가 번역한다 |

질문을 보내는데 `POST`인 것은 조회가 아니라서다. 같은 질문을 두 번 보내면 모델을 두 번 부르고 기록도 두 건 남으니 `GET`으로 둘 수 없다([[09_HTTP와_URI]]).

서비스가 다 하고 있으니 라우터는 얇다.

### `backend/app/api/v1/chat.py`

```python
router = APIRouter(prefix="/chat", tags=["chat"])

@router.post("/messages", response_model=AskOut)
def create_message(payload: ChatRequest) -> AskOut:
    return chat_service.ask(question=payload.question)
```

`main.py`에 등록하면 `prefix`가 이어 붙어 최종 경로는 `/api/v1` + `/chat` + `/messages`가 된다.

```python
from app.api.v1 import auth, chat, documents

app.include_router(chat.router, prefix="/api/v1")
```

`include_router`는 **라우터마다 한 번씩** 부른다. 첫 인자가 router 하나이고 나머지는 `prefix` 같은 옵션 자리라, `include_router(documents.router, auth.router, ...)`처럼 한 번에 넘길 수는 없다.

길이 검사가 두 군데 있는 것은 중복이 아니다.

| 어디 | 무엇 | 왜 |
| --- | --- | --- |
| `ChatRequest` (`min_length=2`, `max_length=2000`) | 요청 형식 | 형식이 어긋난 요청은 서비스까지 들어오기 전에 422로 끊는다 |
| `check_question` (`MAX_INPUT_CHARS`) | 운영 상한 | 화면을 거치지 않는 호출도 있고, 상한은 `.env`로 바꿀 수 있어야 한다 |

실제로 한 글자 질문을 보내면 스키마에서 먼저 걸려 `422 validation_failed`가 나오고, 2001자는 서비스 안 가드에서 `GuardTripped`로 걸린다. 두 값은 따로 관리되니 **바꿀 때 둘 다 맞춰야** 한다.
