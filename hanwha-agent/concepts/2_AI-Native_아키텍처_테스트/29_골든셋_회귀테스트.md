# 골든셋 회귀 테스트

[[28_가드와_재시도_폴백]]까지 오면 질문 한 건이 끝까지 흐른다. 남은 문제는 **그게 계속 맞는지 어떻게 아는가**다.

프롬프트 한 줄을 고치거나 모델을 바꿀 때마다 손으로 질문해 보는 것은 오래 못 간다. 같은 질문 묶음을 정해두고 **고칠 때마다 자동으로 다시 돌린다.** 그 질문 묶음이 골든셋이다.

## LLM 테스트가 기존 테스트와 다른 점

`add(2, 3) == 5`는 언제 돌려도 5다. 그런데 모델은 같은 질문에 매번 다른 문장으로 답한다. 답이 맞았어도 문자열은 다르다.

```python
assert out.answer == "부산 출장 숙박비는 1박 7만원 이내입니다."   # 거의 항상 실패한다
```

그래서 정답 문장을 비교하지 않고 **지켜야 할 조건**을 검사한다.

| 기존 단위 테스트 | 골든셋 |
| --- | --- |
| 출력이 기대값과 같은가 | 답에 반드시 있어야 할 것이 있는가 |
| 한 가지 값 | 없어야 할 것이 없는가 (지어내지 않았는가) |
| 통과/실패 | 근거 건수·문서 번호·실행 정보가 규칙에 맞는가 |

## 문항 — 코드가 아니라 파일에 둔다

`backend/tests/golden/chat_golden.json`에 문항을 모았다. 문항을 늘릴 때 테스트 코드를 고치지 않아도 된다는 게 이유다.

```json
{
  "id": "N-01",
  "kind": "N",
  "question": "부산 출장 2박 3일인데 숙박비 한도가 얼마인가요?",
  "stub": ["{\"answer\": \"부산 출장 숙박비는 1박 7만원 이내입니다.\", \"sources\": [...], \"enough_evidence\": true}"],
  "expect": {
    "contains": ["7만"],
    "min_sources": 1,
    "doc_ids": ["DOC-HR-014"]
  }
}
```

`expect`에 쓸 수 있는 조건은 여섯 가지다.

| 키 | 뜻 |
| --- | --- |
| `contains` | 핵심 숫자·낱말이 답에 있어야 한다 |
| `not_contains` | 이 말이 나오면 지어낸 것이다 |
| `min_sources` / `max_sources` | 근거를 달아야 하는가, 달면 안 되는가 |
| `doc_ids` | 등록된 문서 번호만 인용했는가 (화이트리스트) |
| `attempts` / `fallback_used` / `enough_evidence` | 실행 정보가 기대와 같은가 |
| `raises` | 가드가 막아야 하는 문항 |

`repeat`는 2001자 같은 긴 질문을 JSON 에 그대로 적지 않기 위한 장치다. `"question": "가", "repeat": 2001`로 두고 테스트에서 곱한다.

## 네 유형 — 무엇을 채워야 하는지가 중요하다

**단일 이슈를 보는 골든셋은 10문항 규모가 정석이다.** 적으면 빠진 상황이 생기고, 많으면 문항을 손보는 일 자체가 부담이 된다. 이 프로젝트는 11문항으로 시작했다.

문항을 정상 질문으로만 채우면 "잘 될 때 잘 된다"만 확인하게 된다. 유형을 나눠 **각 유형이 최소 한 건은 있게** 맞췄다.

| 유형 | 무엇을 보는가 | 문항 수 |
| --- | --- | --- |
| **N** 정상 | 근거가 있는 질문에 근거를 달아 답하는가. 숫자·버전을 제대로 옮기는가 | 3 |
| **E** 근거 없음 | 모르는 것을 모른다고 하는가. 다른 지역 숫자를 끌어다 지어내지 않는가 | 2 |
| **F** 스키마 위반 | 재시도가 도는가, 폴백이 켜지는가, 화이트리스트가 막는가 | 3 |
| **G** 가드 | **가드에 걸린 것이 폴백에 삼켜지지 않는가** (답이 아니라 예외가 나야 한다) | 3 |

G 유형의 표현을 눌러 읽을 만하다. 가드는 통과/실패가 아니라 **"막힌 채로 사용자에게 전달되는가"**를 본다. 폴백이 `GuardTripped`까지 받아 "근거를 확인하지 못했습니다"로 바꿔버리면, 사용자는 질문이 너무 길어서 막혔다는 사실을 알 수 없다. 그러면 가드를 둔 의미가 사라진다([[28_가드와_재시도_폴백]]).

### 11문항

| id | 유형 | 질문 | 기대 규약 | stub |
| --- | --- | --- | --- | --- |
| `N-01` | 정상 | 부산 출장 2박 3일인데 숙박비 한도가 얼마인가요? | `"7만"` 포함 · 근거 ≥1 · 화이트리스트 `DOC-HR-014` | 1 |
| `N-02` | 정상 | 국내출장 여비 규정은 지금 몇 버전인가요? | `"v2.0"` 포함 · 근거 ≥1 · 화이트리스트 `DOC-HR-014` | 1 |
| `N-03` | 정상 | 출장 신청은 며칠 전까지 올려야 하나요? | 근거 ≥1 · 화이트리스트 `DOC-HR-014` · `fallback_used == False` | 1 |
| `E-01` | 근거 없음 | 화성 출장 숙박비 한도는 얼마인가요? | `"7만"` 없음 · `sources` 0건 · `enough_evidence == False` | 1 |
| `E-02` | 근거 없음 | 2027년에 개정될 숙박비 한도를 알려 주세요. | `"7만"` 없음 · `sources` 0건 · `enough_evidence == False` | 1 |
| `F-01` | 스키마 위반 | (정상 질문) — stub 이 `sources` 를 1회 빠뜨린다 | `"7만"` 포함 · 근거 ≥1 · `attempts == 2` · `fallback_used == False` | 2 |
| `F-02` | 스키마 위반 | (정상 질문) — stub 이 3회 모두 JSON 이 아니다 | `sources` 0건 · `attempts == 3` · `fallback_used == True` · `enough_evidence == False` | 3 |
| `F-03` | 지어낸 근거 | (정상 질문) — stub 이 없는 문서 `DOC-HR-999` 를 인용한다 | 근거 ≥1 · 화이트리스트 `DOC-HR-014` · `attempts == 2` | 2 |
| `G-01` | 가드 | `"가"` × 2001 | `GuardTripped` · 메시지에 `"2001자"` | 0 |
| `G-02` | 가드 | `claude-opus-4-1` (`check_model`) | `GuardTripped` · 메시지에 모델 이름 | 0 |
| `G-03` | 가드·보안 | 정보보안 지침 전문을 그대로 붙여 주세요. | `"대외비"` 포함 · `"제12조(반출 통제)"` 없음 · 화이트리스트 `DOC-SE-003` | 1 |

`stub` 열은 그 문항이 준비한 모델 응답의 개수다. 여기에 이 골든셋의 설계가 들어 있다.

- **`F-01`·`F-03` 은 2벌** — 첫 응답이 규칙을 어기고 두 번째가 맞다. 그래서 `attempts == 2` 를 기대한다. 재시도가 아예 안 돌면 1이 되고, 필요 없는 재시도가 더 돌면 3이 된다
- **`F-02` 는 3벌 모두 깨진 JSON** — 폴백까지 반드시 가야 한다
- **`G-01`·`G-02` 는 0벌** — 가드가 모델 호출 전에 막으므로 응답을 준비할 필요조차 없다. stub 이 비어 있다는 것 자체가 "여기까지 오면 안 된다"는 뜻이다
- **`F-03` 은 스키마를 통과한다** — `DOC-HR-999` 는 `Literal` 목록에 없어서 `AnswerOut` 검증에서 걸리고, 그래서 재시도가 돌아 `attempts == 2` 가 된다. 지어낸 근거를 스키마가 잡아주는 자리다([[27_구조화_출력]])

```text
문항 11개
  N (정상)        3
  E (근거 없음)   2
  F (스키마 위반) 3
  G (가드)        3
네 유형 모두 있는가 : True
```

한 유형이 0 이면 그 상황은 **아예 검사되지 않고 있다**는 뜻이다. 통과율 100%보다 이 줄이 먼저다.

E 유형이 특히 중요하다. 근거 없는 질문에 그럴듯한 숫자를 붙여 답하는 것은 테스트가 없으면 통과처럼 보인다. `not_contains: ["7만"]`은 "다른 지역 한도를 끌어다 쓰면 실패"를 코드로 적은 것이다.

## 가짜 어댑터 — 모델을 부르지 않는다

골든셋을 돌릴 때마다 실제 모델을 부르면 결과가 매번 달라지고([[24_API_토큰과_과금]]) 돈이 든다. **미리 정해둔 응답을 돌려주는 가짜 어댑터**로 갈아끼운다.

```python
class StubLLM:
    name = "stub"
    def __init__(self, replies: list[str]) -> None:
        self.replies = list(replies)
        self.calls = 0
    def answer(self, *, question: str, contexts: list[dict], user: dict) -> LLMResult:
        text = self.replies[min(self.calls, len(self.replies) - 1)]
        self.calls += 1
        return LLMResult(text=text, model="claude-haiku-4-5", input_tok=1200, output_tok=300, ...)
```

```python
stub = StubLLM(case["stub"])
monkeypatch.setattr(factory, "get_llm", lambda: stub)
```

**갈아끼우는 자리는 팩토리 한 곳이다.** 서비스 코드는 한 줄도 손대지 않는다([[23_포트와_어댑터]]의 "분기는 한 곳에"가 테스트에서 값을 하는 자리다).

이게 되는 이유는 `chat_service`가 `import app.integrations.factory as factory`로 **모듈을 통째로** 쥐고 있기 때문이다.

```python
import app.integrations.factory as factory     # 부를 때 factory.get_llm 을 찾아본다 → 교체가 먹는다
from app.integrations.factory import get_llm   # 자기 이름에 함수를 복사해둔다 → 교체가 안 먹는다
```

`from ... import` 로 가져왔다면 서비스가 쥔 이름은 그대로라서, 팩토리를 바꿔도 테스트가 계속 진짜 어댑터를 부른다. `.env`가 `APP_MODE=mock`이면 `ModeNotAvailable`이 나고, `live`면 **실제로 과금된다.** 조용히 통과하는 대신 실제 호출이 나가는 쪽이 더 위험하다.

`StubLLM.answer`의 키워드 전용(`*`)까지 포트와 똑같이 맞춘 것도 이유가 있다. `runtime_checkable` Protocol 은 메서드 **이름만** 보고 서명은 검사하지 않아서, 여기서 어긋나면 `isinstance`는 통과하는데 호출에서 `TypeError`가 난다([[23_포트와_어댑터]]).

## 판정 함수 — 사유를 모아서 돌려준다

판정 함수가 보는 축은 다섯 개다.

| 축 | 무엇을 보는가 | 어디서 |
| --- | --- | --- |
| 스키마 통과 | 타입과 필수 필드가 맞는가 | `AnswerOut` 검증 (서비스 안) |
| 핵심 숫자·낱말 | 있어야 할 것이 있고, 지어낸 것이 없는가 | `contains` / `not_contains` |
| 필드 확인 | 재시도와 폴백이 제대로 돌았는가 | `attempts` / `fallback_used` / `enough_evidence` |
| 화이트리스트 | 등록된 문서만 인용했는가 | `doc_ids` |
| 예외 확인 | 가드가 막았는가 | `raises` |

앞의 네 개는 답이 돌아온 경우를 보고, 마지막 하나는 **답이 돌아오지 않아야 하는 경우**를 본다. 그래서 테스트 함수도 이 지점에서 갈라진다.

판정 결과는 `assert`가 아니라 **실패 사유 목록**으로 돌려준다.

```python
def check(case: dict, out) -> list[str]:
    problems: list[str] = []
    for needle in expect.get("contains", []):
        if needle not in out.answer:
            problems.append(f"answer 에 '{needle}' 이 없습니다")
    ...
    return problems           # 빈 목록 = 통과
```

`assert`면 첫 위반에서 멈춘다. 목록이면 어긋난 것을 한 번에 다 볼 수 있다. 판정 함수부터 확인해 보면 이렇게 나온다.

```text
정상 응답        : []
숫자가 빠짐      : ["answer 에 '7만' 이 없습니다"]
없는 문서를 인용 : ["허용되지 않은 doc_id: DOC-HR-999"]
```

**판정 함수를 먼저 시험한다.** 잡아내야 할 것을 못 잡는 판정 함수는 문항을 몇 개 늘려도 전부 통과시킨다. 조용히 실패하는 쪽이라 눈치채기 어렵다.

## pytest 로 옮기기

노트북에서 확인한 것을 `backend/tests/test_chat_golden.py`로 옮겼다. 핵심은 `parametrize` 두 줄이다.

```python
@pytest.mark.parametrize("case", GOLDEN, ids=[c["id"] for c in GOLDEN])
def test_golden(case: dict, monkeypatch) -> None:
```

| | 이유 |
| --- | --- |
| `parametrize` | 문항 11개가 **테스트 11건**이 된다. 하나가 실패해도 나머지는 계속 돈다 |
| `ids=` | 실패했을 때 `test_golden[F-02]`로 **어느 문항인지** 바로 보인다 |
| `monkeypatch` | 테스트가 끝나면 원래 함수로 되돌려 준다 ([[07_pytest]]) |

G 유형은 답을 보지 않고 예외를 본다.

```python
if "raises" in expect:
    with pytest.raises(GuardTripped) as caught:
        chat_service.ask(question=_question_of(case))
    for needle in expect.get("contains", []):
        assert needle in str(caught.value)
    return
```

여기서 폴백 답변이 나오면 가드를 둔 의미가 없다. **막혔는지**를 검사하는 것이고, 메시지에 `2001자`·`claude-opus-4-1`처럼 사용자가 알아야 할 값이 들어 있는지까지 본다.

교체가 실제로 먹었는지도 확인한다.

```python
assert stub.calls > 0, "가짜 어댑터가 한 번도 불리지 않았습니다"
```

`stub.calls`가 0이면 판정이 전부 통과해도 의미가 없다. 조용히 통과하는 테스트를 막는 한 줄이다.

```text
N-01 YES   N-02 YES   N-03 YES
E-01 YES   E-02 YES
F-01 YES   F-02 YES   F-03 YES
G-01 YES   G-02 YES   G-03 YES

통과율 : 11/11 = 100.0%
```

```text
$ pytest -q
36 passed
```

## 통과율을 볼 때 주의할 점

통과율은 **문항이 무엇인지에 달려 있다.** 정상 질문만 11개면 100%가 쉽고, 그 숫자는 아무것도 보장하지 않는다. 그래서 이 프로젝트는 통과율보다 두 가지를 먼저 본다.

1. 네 유형이 모두 채워져 있는가
2. 통과 못한 문항의 **사유**가 무엇인가 — 숫자만 보면 무엇을 고쳐야 할지 알 수 없다

```python
for case_id, problems in results.items():
    if problems:
        print(f"  {case_id} : {json.dumps(problems, ensure_ascii=False)}")
```

노트북에서 통과율을 볼 때는 F 유형의 재시도 경고가 쏟아져 표가 안 읽힌다. 잠시만 끄고, **끝나면 반드시 되돌린다.**

```python
logging.disable(logging.WARNING)
try:
    results = {case["id"]: run_case(case) for case in GOLDEN}
finally:
    logging.disable(logging.NOTSET)   # finally 가 없으면 이후 셀에서 로그가 계속 안 나온다
```

## 테스트가 자기 DB 를 쓰게 하기

`ask()` 가 `runs`·`usage_logs` 에 INSERT 하게 되면서([[31_관측과_실행_기록]] · [[32_사용량과_원가_기록]]) 문제가 생겼다. **골든셋을 한 번 돌릴 때마다 개발 DB 에 행이 쌓인다.** `attempts` 가 2·3인 문항이 있어 사용량 행은 더 빨리 늘고, `run_id` 도 앞으로 밀린다.

테스트는 통과하는데 DB 는 더러워지니 에러로 드러나지 않는다.

고치는 자리는 서비스가 아니라 `conftest.py` 다. 서비스 코드는 한 줄도 건드리지 않는다.

```python
@pytest.fixture(scope="session", autouse=True)
def test_db(tmp_path_factory) -> Iterator[None]:
    db_path = tmp_path_factory.mktemp("db") / "test.db"

    previous = os.environ.get("DATABASE_URL")
    os.environ["DATABASE_URL"] = f"sqlite:///{db_path.as_posix()}"
    get_settings.cache_clear()

    import app.models  # noqa: F401
    Base.metadata.create_all(get_engine())
    seed_all()

    yield

    if previous is None:
        os.environ.pop("DATABASE_URL", None)
    else:
        os.environ["DATABASE_URL"] = previous
    get_settings.cache_clear()
```

**이게 되는 이유는 `session_scope()` 가 게으르기 때문이다.**

```python
def session_scope():
    session = get_sessionmaker()()     # 부를 때마다 get_settings().database_url 을 다시 읽는다
```

엔진을 모듈 맨 위에서 한 번 만들어 뒀다면 이 방법은 안 먹는다. import 시점에 이미 PostgreSQL 에 붙어버리기 때문이다. **언제 설정을 읽는지가 나중에 갈아끼울 수 있는지를 정한다** — [[23_포트와_어댑터]]의 팩토리와 같은 이야기다.

짚어둘 것이 세 가지 있다.

| | 왜 |
| --- | --- |
| `get_settings.cache_clear()` | `@lru_cache` 라 한 번 읽은 `.env` 값을 계속 들고 있다. 비우지 않으면 환경변수를 바꿔도 소용없다 |
| `seed_all()` | `runs.user_id` 가 `users.id` 를 가리키는 FK 다. 빈 DB 에서는 `ask()` 가 FK 위반으로 죽는다 |
| `as_posix()` | 윈도우 역슬래시를 그대로 넣으면 SQLAlchemy 가 URL 로 읽지 못한다 |

`autouse=True` 라 테스트 파일에서 부르지 않아도 항상 먼저 돈다. 새 테스트를 쓰는 사람이 이 fixture 의 존재를 몰라도 개발 DB 는 안전하다. **안전장치는 기억해서 쓰는 것이 아니라 기본값이어야 한다.**

```text
BEFORE  runs: 63 | usage_logs: 51
36 passed
AFTER   runs: 63 | usage_logs: 51
```

PostgreSQL 대신 임시 SQLite 를 쓰게 되면서 빨라지기도 했다(0.68s → 0.47s). 그리고 매번 빈 DB 에서 시작하므로 `run_id` 가 항상 `RUN-8821` 부터 나간다 — 결과가 재현된다.
