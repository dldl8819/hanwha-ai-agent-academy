# 청크 저장

[[50_청킹_규칙]]까지 만들어 둔 것은 조각내는 기능이었다. 조각은 변수에 담겼다가
셀이 끝나면 사라졌다. 질문이 들어올 때마다 문서를 다시 파싱할 수는 없으니
어딘가 적어 둬야 한다. 그 자리를 만든다.

## 담을 자리가 없었다

```text
블록 81 · 표 2 · 쪽 1
조항 단위 17 + 표 단위 2 = 19 청크
  [표] ord=1  locator=표1  글자 수=264
  [표] ord=18  locator=표2  글자 수=283

이 drafts 는 셀이 끝나면 사라진다. 질문이 들어올 때 다시 파싱할 수는 없다.
```

81블록을 19청크로 줄였는데 그 19개를 쓸 데가 없다.

## 청크는 문서가 아니라 버전에 딸린다

`Chunk.version_id` 가 가리키는 것은 `documents` 가 아니라 `document_versions` 다.

| | |
| --- | --- |
| 문서에 달면 | v1.4 와 v2.0 이 청크를 공유한다. 개정된 조문과 옛 조문이 한 통에 섞인다 |
| 버전에 달면 | 판마다 따로 쌓인다. 만료된 판의 청크를 검색에서 빼는 것도 버전 단위로 된다 |

같은 문서라도 판이 다르면 본문이 다르다. 숙박비 상한이 7만원에서 8만원으로
바뀐 판이 있으면, 그 둘은 같은 조항 번호를 달고도 다른 답을 내놓는다.
섞이면 어느 쪽이 맞는지 가릴 수 없다.

## 칼럼

```text
  id           INTEGER
  version_id   INTEGER        FK -> document_versions.id
  ord          INTEGER
  kind         VARCHAR(16)
  locator      VARCHAR(200)
  text         TEXT
```

`chunker.ChunkDraft` 의 `kind`·`locator`·`text` 를 그대로 받고 두 칸을 더했다.

- **`ord`** — 문서 안에서의 순서. 검색 결과를 원문 순서로 되돌리거나 앞뒤 조각을
  붙여 볼 때 쓴다.
- **`version_id` 에 `index=True`** — 청크는 늘 "이 버전의 청크 전부" 형태로 조회된다.
  색인이 없으면 버전 하나 읽을 때마다 `chunks` 전체를 훑는다.

### `text` 는 `String` 이 아니라 `Text` 다

```text
가장 긴 조각 283자 — locator 칼럼이 String(200) 이라서
본문은 Text 로 뒀다. String 이면 이 조각이 잘린다.
```

`String(n)` 은 길이 상한이 있다. `locator` 는 출처 문자열이라 200자로 충분하지만
본문은 조항 하나가 길어지면 넘는다. 표는 마크다운으로 변환해 넣으므로 더 길다.
위 재료의 표2가 283자다.

`VARCHAR(200)` 에 283자를 넣어 보면 조용히 잘리지 않는다. 거부한다.

```text
거부됐다 → DataError
   (psycopg.errors.StringDataRightTruncation) value too long for type character varying(200)
```

잘린 채로 저장되는 것보다 낫다. 다만 터지는 자리가 업로드가 아니라 배경 작업
안이라([[56_배경_작업과_작업_번호]]) 사용자에게는 201 이 먼저 가고, 실패는
작업 상태를 물었을 때야 드러난다.

## `__init__.py` 에 import 하지 않으면 마이그레이션에 안 나온다

```text
Base.metadata 에 등록된 표:
  chunks ←
  departments
  document_versions
  documents
  run_steps
  runs
  usage_logs
  users
```

Alembic 의 autogenerate 는 `Base.metadata` 에 등록된 테이블만 본다.
모델 파일에 클래스를 써 두기만 하고 `models/__init__.py` 에서 import 하지 않으면
`Base.metadata` 에 안 올라가고, 리비전 파일이 빈 `upgrade()` 로 나온다.
에러가 아니라 빈 파일이라 알아채기 어렵다.

```text
Running upgrade 9f2a041f60ca -> 8dd7b4e2751d, add chunks
```

## 파싱에서 저장까지 — `ingest_document()`

```text
document_versions : id=10 chunk_count=19 index_status=완료 progress=100 indexed_at=2026-10-06
chunks 실제 행 수   : 19

  ord=0  조항  DOC-FI-009_v9.9         114자  '일반\n법인카드 사용 지침\nv1.4\n문서번호  DOC-FI-00'
  ord=1  표  표1                      264자  '| 버전 | 구분 | 시행일 | 주요 내용 | 작성 | 검토 '
  ord=2  조항  DOC-FI-009_v9.9         205자  '이 표는 문서관리규정 제9조에 따라 관리한다.\n목차\n제1조(목'
  ord=3  조항  제1장 제1조(목적)              73자  '제1조(목적) 이 지침은 법인카드의 발급·사용·관리 및 증빙에'
```

순서는 ① 어느 판에 붙일지 확정 → ② 파싱 → ③ 청킹 → ④ 저장이다.
판을 먼저 찾는 이유는, 없는 판에 붙일 청크를 만들어 놓고 버리는 일을 피하려는 것이다.

### `from app.rag import ...` 를 함수 안에서 한다

`app.rag` 는 파서 라이브러리들을 끌고 온다. 모듈 맨 위에 두면 서버가 뜰 때마다
전부 읽어 기동이 느려진다. 업로드가 들어올 때만 필요한 것이라 함수 안에 뒀다.

## 같은 판을 다시 올리면 — 더하지 않고 갈아끼운다

```text
재적재 결과: {'chunks': 19, 'tables': 2, 'summary': '조항 단위 17 + 표 단위 2 = 19 청크'}
chunks 전체 행 수 : 19 → 19
늘지 않았다. 더한 게 아니라 갈아끼웠다.
```

지우지 않고 `add` 만 하면 같은 조항이 두 벌 남는다. 검색이 같은 근거를 중복으로
집어 오고, 둘 중 어느 것이 최신인지 구분할 방법이 없다.

```python
for old in list(dv.chunks):
    s.delete(old)
s.flush()   # DELETE 를 먼저 내보낸다
```

`flush()` 를 빼면 SQLAlchemy 가 INSERT 를 먼저 보낼 수 있다. 지금은 유일 제약이
없어 티가 안 나지만, `(version_id, ord)` 에 제약을 거는 순간 충돌한다.

`list(dv.chunks)` 로 복사하는 것도 이유가 있다. 순회하면서 원본 컬렉션을 지우면
도중에 목록이 바뀐다.

## `cascade="all, delete-orphan"`

```text
chunks 남은 행 수: 0 — 버전을 지우니 청크도 함께 지워졌다
```

버전을 지우면 청크도 함께 지워져야 한다. 안 걸면 `version_id` 가 가리킬 데가 없는
청크가 남고, 외래키 제약에서 삭제 자체가 실패한다.

## 짚어 둔 것 — 임베딩 없이 "완료"

```text
status=현행 index_status=완료 → is_searchable=True
임베딩 벡터는 한 건도 없다.
```

`ingest_document()` 가 `index_status = "완료"` 와 `index_progress = 100` 을 적는다.
`DocumentVersion.is_searchable` 은 그 값만 보므로, 벡터가 한 건도 없는 판이
검색 대상으로 판정된다. 지금은 검색 기능이 없어 드러나지 않는다.
④임베딩을 붙일 때 이 두 줄을 "임베딩까지 끝난 뒤" 로 옮겨야 한다.

## 짚어 둔 것 — 출처가 파일 이름에 끌려간다

```text
원본 파일명             DOC-FI-009_법인카드_사용_지침_v1.4.docx            → ['DOC-FI-009_법인카드_사용_지침_v1.4']
업로드가 바꾼 이름         DOC-FI-009_v9.9.docx                       → ['DOC-FI-009_v9.9']
```

조 제목이 없는 조각은 출처 자리에 파일 이름이 들어간다([[52_파서_진입점과_형식_확장]]에
적어 둔 locator 문제의 다른 얼굴이다). 업로드는 파일명을 `{doc_id}_{version}` 으로
갈아치우므로, 같은 문서인데도 노트북에서 본 출처와 DB 에 저장된 출처가 다르다.

어제까지는 화면에 찍고 지나가는 값이라 넘겼다. 오늘부터는 그 값이 DB 에 박히고
나중에 근거 인용으로 사용자에게 보인다. `ord=0` 과 `ord=2` 의 출처가
`DOC-FI-009_v9.9` 인데, 사용자에게 "이 답은 DOC-FI-009_v9.9 에서 나왔습니다" 는
아무것도 알려 주지 않는다.
