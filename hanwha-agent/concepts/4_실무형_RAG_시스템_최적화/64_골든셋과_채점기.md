# 골든셋과 채점기

[[63_검색_정책]]까지 만들고 나니 바꾼 것이 나아진 것인지 알 방법이 없었다.
질문 세 개를 눈으로 보고 "되는 것 같다"고 했을 뿐이다.

문항을 고정해 두고 점수를 매긴다. [[29_골든셋_회귀테스트]]에서 LLM 답변에 했던 일을
이번에는 검색에 한다.

## 다섯 유형 30문항

```yaml
meta:
  name: 사내 규정 골든셋 v1
  items: 30
  threshold: 0.55
```

| 유형 | 수 | 무엇을 보려는가 |
| --- | --- | --- |
| 단일 조항 | 10 | 조문 하나를 찾아오는 기본기 |
| 표 안의 조건 조합 | 6 | 표를 자르지 않은 것([[50_청킹_규칙]])이 값을 하는가 |
| 개정 전후 비교 | 4 | 과거 판을 열어 주는가([[63_검색_정책]]) |
| 타 부서 문서 참조 | 4 | 보안등급 필터가 제대로 막는가 |
| 규정에 없는 사항 | 6 | 없으면 없다고 하는가 |

유형을 나눈 것이 핵심이다. 총점만 보면 80% 가 좋은지 나쁜지 알 수 없지만,
유형별로 쪼개면 **무엇을 고쳐야 하는지가 나온다.** 다섯 유형이 각각 지금까지 만든
것 하나씩을 겨냥한다.

마지막 유형이 6문항으로 가장 많다. 답을 못 찾는 것보다 **없는 답을 지어내는 쪽이
더 나쁘다**고 보기 때문이다.

## 문항 하나의 모양

```yaml
- id: G11
  question: 4급 직원이 광역시로 출장 가면 일비와 숙박비는 각각 얼마인가요?
  type: 표 안의 조건 조합
  expect_doc: DOC-HR-014
  expect_version: v2.0
  expect_kind: 표
  expect_keywords: ["30,000", "70,000"]
```

기대값을 네 단계로 나눠 적는다. 문서 → 판 → 종류 → 본문 글자. 뒤로 갈수록 좁다.

`expect_keywords` 는 **금액 숫자**를 쓴다. 조문 번호나 제목이 아니라 값이다.
조문이 옮겨 가도 금액이 맞으면 맞는 근거를 찾은 것이다.

과거 판 문항에는 `needs_past_version: true`, 등급 문항에는
`requires_clearance: 대외비` 를 적어 둔다. 지금 채점기는 이 둘을 읽지 않는다.
문항이 무엇을 의도했는지 적어 두는 자리로만 쓰인다.

## 채점은 상위 3건만 본다

```python
DEFAULT_TOP_N = 3
```

검색은 12건을 가져오지만 채점은 상위 3건으로 한다. 실제로 LLM 에게 넘길 분량이
그쯤이기 때문이다. 12건 중 11위에 정답이 있으면 **답변에는 쓰이지 않는다.**
쓰이지 않을 것을 맞혔다고 세면 점수가 사실을 가린다.

## 못 찾는 것과 지어내는 것을 따로 센다

```python
def judge(item, hits, threshold) -> tuple[bool, str]:
    best = max((h["score"] for h in hits), default=0.0)
    if item.get("unanswerable"):
        ok = best < threshold
        return ok, "근거 부족 정상" if ok else f"임계값 초과({best:.2f}) - 지어낼 위험"
    if best < threshold:
        return False, f"임계값 미달({best:.2f})"
    ...
```

`unanswerable` 문항은 **채점 방향이 뒤집힌다.** 점수가 임계값보다 낮아야 맞는다.
규정에 없는 것을 물었을 때 아무것도 안 걸리는 것이 정답이다.

나머지 문항은 임계값을 넘은 다음에야 문서·판·종류·글자를 차례로 본다. 하나라도
어긋나면 다음 후보로 넘어가고, 셋 다 못 맞히면 「정답 문서가 상위에 없음」이다.

사유를 문자열로 함께 돌려주는 것이 중요하다. `False` 만 받으면 못 찾은 것인지
점수가 모자란 것인지 알 수 없다. 이유별로 고치는 방법이 다르다.

### 채점 판정을 먼저 확인했다

검색을 돌리지 않고 가짜 결과를 넣어 네 경우를 찍어 봤다.

| 넣은 것 | 판정 |
| --- | --- |
| 보통 문항 · 점수 0.31 | False — 임계값 미달 |
| unanswerable · 점수 0.31 | True — 근거 부족 정상 |
| unanswerable · 점수 0.82 | False — 지어낼 위험 |
| 보통 문항 · 정답 문서 상위 | True |

채점기가 틀리면 측정값 전체가 뜻을 잃는다. 검색을 붙이기 전에 채점 규칙부터
눌러 보는 순서다.

## 측정값을 테이블에 남긴다

```python
class EvalRun(Base, TimestampMixin):
    __tablename__ = "eval_runs"
    config: Mapped[str]      # '기본 검색'
    accuracy: Mapped[float]  # 0~100
    item_count: Mapped[int]
    measured_at: Mapped[datetime | None]
```

설정 하나를 한 번 측정한 결과가 한 줄이다. `config` 를 둔 이유는 나중에
「기본 검색」 / 「재순위 적용」 / 「청크 크기 변경」 같은 설정을 나란히 재기 위해서다.
지금은 `CONFIGS` 에 하나뿐이라 비교가 안 된다.

JSON 리포트도 `evals/reports/` 에 날짜를 붙여 쌓는다. 테이블에는 총점만 남고
문항별 결과는 파일에 남는다.

```python
session.query(EvalRun).delete()
```

저장할 때 기존 줄을 전부 지우고 다시 넣는다. 화면이 "현재 설정별 정확도"를 보여 주는
용도라 이력이 필요 없다는 전제다. 이력을 보고 싶으면 리포트 파일을 본다.

### 측정기가 쓰지 않는 테이블이 하나 있다

`EvalWeakType` 은 「정답률 낮은 질문 유형」 표에 쓰려고 만들었는데 **`run_eval.py` 가
건드리지 않는다.** 유형별 집계를 `by_type` 으로 계산해 JSON 에는 넣지만 이 테이블에는
넣지 않는다.

처음 측정한 뒤에도 0행이었다. 노트북으로 따로 채웠고([[67_오답_목록과_약한_유형]]),
그래서 두 테이블을 쓰는 사람이 갈렸다.

## 관리자 시각으로 잰다

```python
EVAL_USER = {"id": "2011-0003", "name": "한서영", "clearance": "대외비", "dept_id": "HR"}
```

채점할 때는 가장 높은 등급으로 검색한다. 등급 때문에 가려지면 검색이 못 찾은 것인지
정책이 막은 것인지 섞이기 때문이다.

이 선택이 값을 한다는 것은 [[65_측정값_뜯어보기]]에서 실제로 확인했다. 「타 부서 문서
참조」 4문항이 겨냥한 문서가 대외비라, 일반 등급으로 재면 1위가 엉뚱한 문서로 바뀐다.
그러면 검색이 못 찾은 것인지 등급이 가린 것인지 구분할 수 없다.

바꿔 말하면 **이 측정값은 보안등급 필터가 제대로 막는지를 재지 않는다.**
「타 부서 문서 참조」 유형이 그걸 재는 줄 알았는데, 관리자로 돌리는 한 그 유형도
그냥 검색 정확도를 잰다. 등급을 재려면 등급별로 따로 돌려 **달라지는 것**을 봐야 한다.
