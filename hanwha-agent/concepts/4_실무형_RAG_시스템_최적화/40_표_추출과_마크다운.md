# 표 추출과 마크다운

[[39_문서_파싱]]에서 표의 **자리**는 잡았다. 안을 무엇으로 채울지가 남았다.

## 이어 붙이면 안 되는 이유

표의 칸을 순서대로 이어 붙여 보면 이렇게 된다.

```python
flat = [cell.text.strip() for row in table.rows for cell in row.cells]
print(" ".join(flat))
```

```text
표 크기 : 4행 7열

버전 구분 시행일 주요 내용 작성 검토 승인 v2.0 개정 2025-07-01 일비 인상(25,000→30,000)
· 광역시 숙박비 상한 신설 · 별표1 전면 개정 김지원 박성호 대표이사 v1.1 개정 2024-09-01
교통비 정산 방식을 실비 정산으로 변경 김지원 박성호 대표이사 v1.0 제정 2024-01-01 최초 제정
이한별 박성호 대표이사
```

**어떤 값이 어떤 제목에 속하는지가 사라졌다.** `김지원` 이 작성자인지 검토자인지, `2025-07-01` 이 어느 버전의 시행일인지 글자만 봐서는 모른다. 모델도 모른다.

행과 열이 살아 있어야 한다. 그런데 `ParsedBlock.text` 는 **문자열 하나**다. 문자열인데 구조가 남아 있는 형식이 필요하다.

## 마크다운 표

```text
| 버전 | 구분 | 시행일 | 주요 내용 | 작성 | 검토 | 승인 |     ← 머리
|---|---|---|---|---|---|---|                                ← 구분선
| v2.0 | 개정 | 2025-07-01 | 일비 인상… | 김지원 | 박성호 | 대표이사 |   ← 본문
```

| 왜 마크다운인가 | |
| --- | --- |
| 문자열 하나 | `ParsedBlock.text` 에 그대로 들어간다 |
| 행과 열이 산다 | 모델이 "작성=김지원"을 읽어낼 수 있다 |
| 토큰을 적게 먹는다 | HTML 표보다 훨씬 짧다 |
| 언어 모델이 잘 읽는다 | 학습 데이터에 흔한 형식이다 |

```python
def _table_to_markdown(headers: list[str], rows: list[list[str]]) -> str:
    head = "| " + " | ".join(headers) + " |"
    sep = "|" + "---|" * len(headers)
    body = ["| " + " | ".join(str(c) for c in r) + " |" for r in rows]
    return "\n".join([head, sep, *body])
```

**첫 행을 무조건 머리로 쓴다.** 머리 행이 없는 표도 마찬가지다. 표의 첫 행이 제목인지 아닌지는 사람이 봐야 알 수 있는데, 틀렸을 때의 손해가 작다 — 첫 행이 본문이면 그 한 줄이 제목처럼 보일 뿐이다.

DOCX 표에 붙이면 이렇게 나온다.

```text
| 버전 | 구분 | 시행일 | 주요 내용 | 작성 | 검토 | 승인 |
|---|---|---|---|---|---|---|
| v2.0 | 개정 | 2025-07-01 | 일비 인상(25,000→30,000) · 광역시 숙박비 상한 신설 · 별표1 전면 개정 | 김지원 | 박성호 | 대표이사 |
| v1.1 | 개정 | 2024-09-01 | 교통비 정산 방식을 실비 정산으로 변경 | 김지원 | 박성호 | 대표이사 |
| v1.0 | 제정 | 2024-01-01 | 최초 제정 | 이한별 | 박성호 | 대표이사 |
```

`parse_docx` 의 표 자리를 이걸로 채운다.

```python
blocks.append(ParsedBlock("표", f"표{tables}", _table_to_markdown(rows[0], rows[1:])))
```

```text
블록 233 / table_count 7
```

## PDF 에서 같은 표를 꺼내면

같은 문서의 PDF 판에서 그 표가 있는 쪽을 `pypdf` 로 읽어 본다.

```text
 1 | 제·개정 이력
 2 | 버전
 3 | 구분
 4 | 시행일
 5 | 주요 내용
 6 | 작성
 7 | 검토
 8 | 승인
 9 | v2.0
10 | 개정
11 | 2025-07-01
12 | 일비
13 | 인상(25,000→30,000)
...
(문서 전체 434줄)
```

**표가 세로로 풀려 버렸다.** `pypdf` 는 글자를 꺼낼 뿐 선을 보지 않는다. [[39_문서_파싱]]에서 본 그대로 — PDF 에는 표라는 개념이 없고 좌표에 놓인 글자만 있다.

| | PDF | DOCX |
| --- | --- | --- |
| 나누는 단위 | **페이지** | **문단·표** |
| 출처 표시 | `p.6` | 문서 이름, `표2` |
| 페이지 수 | 있다 | **없다** (인쇄할 때 정해진다) |
| 표를 표로 아는가 | **모른다** | **안다** |

## pdfplumber — 선을 보고 표를 찾는다

```python
import pdfplumber

with pdfplumber.open(str(PDF)) as pdf:
    tables = pdf.pages[1].extract_tables()   # 표 → 행 → 칸 3중 리스트
```

```text
이 쪽의 표 : 1개
4행 7열
['버전', '구분', '시행일', '주요 내용', '작성', '검토', '승인']
['v2.0', '개정', '2025-07-01', '일비\n인상(25,000→30,000)\n· 광역시 숙박비 상한\n신설 · 별표1 전면 개정', '김지원', '박성호', '대표이사']
```

문서 전체에서 찾은 표 개수를 DOCX 와 맞춰 보면 검산이 된다.

```text
p. 2 : 1개    p.13 : 1개
p.11 : 1개    p.14 : 1개
p.12 : 1개    p.15 : 1개
              p.16 : 1개
─────────────
PDF 표 합계 : 7   ·   DOCX 표 : 7   ·   같다 : True
```

**같은 문서의 두 형식에서 같은 수가 나왔다.** 둘 다 틀렸을 수도 있지만, 서로 다른 방식으로 센 값이 맞는 것은 꽤 강한 신호다.

### 셀 안에 줄바꿈이 들어 있다

바로 마크다운으로 바꾸면 깨진다.

```text
| v2.0 | 개정 | 2025-07-01 | 일비
인상(25,000→30,000)
· 광역시 숙박비 상한
신설 · 별표1 전면 개정 | 김지원 | 박성호 | 대표이사 |
```

마크다운 표는 **한 행이 한 줄**이어야 한다. 셀 안의 `\n` 이 행을 갈라 버린다.

```text
줄바꿈이 든 셀 : 8개 (전체 220개 중)
```

220칸 중 8칸뿐이라 눈으로 훑으면 놓치기 쉽다. 줄바꿈을 공백으로 바꿔서 넣는다.

```python
flat = [[(c or "").replace("\n", " ").strip() for c in row] for row in t]
```

`(c or "")` 인 것은 `pdfplumber` 가 **빈 칸을 `None` 으로 돌려주기** 때문이다. 병합된 셀에서 나온다.

### 어느 라이브러리를 어디에 쓸 것인가

```text
글자 추출 줄 수 : pypdf 434줄 · pdfplumber 326줄
```

| | pypdf | pdfplumber |
| --- | --- | --- |
| 글자 추출 | 된다 (434줄, 표가 세로로 풀림) | 된다 (326줄) |
| **표 찾기** | **안 된다** | **된다** |
| 라이선스 | BSD | MIT |

무게가 갈린다. 설치된 용량을 재 보면 이렇다.

```text
pypdf         3.7 MB
pdfplumber    0.3 MB   ← 자기 자신은 가볍다
pdfminer      9.3 MB   ┐ pdfplumber 가 끌고 오는 것
PIL          16.0 MB   ┘
```

**`pdfplumber` 자체는 0.3MB 인데 딸려 오는 것이 25MB 다.** 글자를 배치대로 읽으려면 `pdfminer`, 선을 찾으려면 이미지 처리(`Pillow`)가 필요하기 때문이다.

그래서 앱에서는 나눠 쓴다.

```text
local_parsers.py 의 글자 추출   →  pypdf
표가 필요한 자리에서만          →  pdfplumber
```

## 두 형식의 조각 크기

같은 규정 문서를 두 형식으로 파싱해서 비교했다.

```text
형식        블록    표   page_count    글자(약)
───────────────────────────────────────────────
docx         233     7            1     8,300자
pdf           16     0           16     7,800자
```

```text
docx : 블록 233개 · 평균 약  35자 · 가장 짧은 블록   2자 · 가장 긴 블록  378자
pdf  : 블록  16개 · 평균 약 490자 · 가장 짧은 블록 108자 · 가장 긴 블록 1070자
```

**같은 문서인데 조각 수가 14배 차이 난다.** DOCX 는 문단 하나가 블록 하나라 잘고, PDF 는 페이지 하나가 블록 하나라 굵다.

| 조각이 크다 (PDF) | 조각이 작다 (DOCX) |
| --- | --- |
| 검색에 잘 걸린다 (단어가 많이 들어 있다) | 검색이 정확하다 |
| 관계없는 글자가 딸려 온다 | 앞뒤 맥락이 잘릴 수 있다 |
| 토큰 값이 늘어난다 | 조각 수가 늘어 관리할 것이 많아진다 |

### 열 건 전부로 넓혀 보면

재료에 든 규정 10건을 두 형식으로 전부 파싱했다([`02.문서파싱실습.ipynb`](../../sandbox/w5/day01/02.문서파싱실습.ipynb)).

```text
docx  1061개 · 평균  29자 · 중앙값  17자 · 최소  2자 · 최대  378자
pdf     81개 · 평균 360자 · 중앙값 224자 · 최소 38자 · 최대 1070자
```

한 건에서 본 것이 열 건에서도 같다. 블록 수는 문서마다 **10.0배에서 14.6배** 사이로 벌어진다.

표는 더 분명하다.

```text
표 합계 : docx 32개 / pdf 0개
```

`parse_pdf` 가 표를 찾지 않으니 당연한 결과인데, **당연한 것을 숫자로 본 값**이 있다. pdf 로 들어온 문서는 금액표·기한표가 전부 문장 사이에 녹아 있다는 뜻이고, 같은 규정을 어느 형식으로 올렸느냐에 따라 답의 품질이 갈린다는 뜻이다.

평균과 중앙값이 벌어지는 것도 눈여겨볼 만하다. docx 는 평균 29자인데 중앙값이 17자다. **절반이 17자 이하**이고 몇 개의 큰 표가 평균을 끌어올린다.

**어느 쪽도 그대로 쓰기엔 맞지 않다.** 평균 35자는 "제12조(숙박비)" 한 줄이라 그것만으로는 답이 안 나오고, 1,070자는 한 페이지 통째라 질문과 상관없는 조항이 절반이다. 다음 단계인 청킹이 이걸 다시 자르고 붙이는 일을 한다([[33_RAG_개요]] ③).

파싱은 **원문의 구조를 보존하는 데까지**이고, 검색에 맞는 크기로 만드는 것은 청킹의 몫이다. 여기서 미리 자르면 나중에 되돌릴 수 없다.

## 테스트

숫자를 고정해 둔다.

### `backend/tests/test_local_parsers.py`

```python
def test_parse_docx_keeps_tables_in_body_order() -> None:
    doc = parse_docx(DOCX)
    assert len(doc.blocks) == 233
    assert doc.table_count == 7
    assert doc.page_count == 1

    kinds = [block.kind for block in doc.blocks]
    assert kinds.count("표") == 7
    assert kinds[-1] == "조항"
    assert all(block.text.startswith("| ") for block in doc.blocks if block.kind == "표")
```

```bash
pytest -q backend/tests/test_local_parsers.py
```

```text
3 passed
```

`startswith("| ")` 한 줄이 **표가 마크다운으로 들어갔는지**를 지킨다. 표 블록이 생기는 것과 그 안이 채워지는 것은 다른 문제인데, 개수만 세면 빈 문자열이 들어가도 통과한다.

재료가 없는 환경을 위해 건너뛰는 길을 열어 뒀다.

```python
def _require(path: Path) -> None:
    if not path.is_file():
        pytest.skip(f"실습 재료가 없습니다: {path}")
```

샘플 문서는 저장소에 없을 수 있다. **실패가 아니라 skip 이어야** 다른 테스트가 묻힌다([[29_골든셋_회귀테스트]]).

## 짚어둘 것

숫자를 테스트에 박아 두면 **문서가 바뀔 때 같이 깨진다.** 233 과 7 은 `DOC-HR-014 v2.0` 한 건의 값이고, 규정이 개정되면 달라진다.

그래도 박아 둔 이유는 지금 확인하려는 것이 문서가 아니라 **파서**이기 때문이다. 파서를 고쳤을 때 숫자가 움직이면 그게 신호다. 문서가 바뀌어 깨지는 날에는 새 숫자로 갱신하면 된다 — 그때도 무엇이 왜 바뀌었는지는 보인다.
