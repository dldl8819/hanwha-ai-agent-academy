# 기법을 더했는데 떨어졌다

[[72_질의_재작성과_Multi_Query]]와 [[73_키워드_검색과_RRF]]를 붙이고 다시 측정했다.
설정 셋을 나란히 재는 구조는 [[64_골든셋과_채점기]]에서 `config` 칸을 둔 그 자리다.

```python
CONFIGS = [
    {"name": "기본 검색"},
    {"name": "+ Multi-Query", "multi_query": True},
    {"name": "+ 하이브리드", "multi_query": True, "hybrid": True},
]
```

## 결과

```text
문항 30개. 임계값 0.55. 상위 3건

 기본 검색             80.0% (24/30)
 + Multi-Query     76.7% (23/30)
 + 하이브리드           66.7% (20/30)
```

**더할수록 내려갔다.** 13.3%p 떨어졌다.

유형별로 보면 어디가 무너졌는지가 나온다.

| 유형 | 기본 | + Multi-Query | + 하이브리드 |
| --- | --- | --- | --- |
| 단일 조항 | 90.0 | 70.0 | 80.0 |
| 표 안의 조건 조합 | 83.3 | 83.3 | **33.3** |
| 개정 전후 비교 | 100.0 | 100.0 | 75.0 |
| 타 부서 문서 참조 | 50.0 | 50.0 | 50.0 |
| 규정에 없는 사항 | 66.7 | **83.3** | 83.3 |

「표 안의 조건 조합」이 5/6 에서 2/6 으로 떨어졌다. 그리고 「규정에 없는 사항」은
4/6 에서 5/6 으로 올랐다. 한 설정이 어떤 유형은 올리고 어떤 유형은 내린다.

[[64_골든셋과_채점기]]에서 유형을 나눈 이유가 여기서 값을 한다. 총점만 보면
「하이브리드는 나쁘다」로 끝나는데 쪼개 보면 그렇지 않다.

## 뒤집힌 문항은 일곱 개다

```text
  ID   유형            기본 검색   + Multi-Query   + 하이브리드
  G04  단일 조항         O         X              X
  G06  단일 조항         O         X              O
  G11  표 안의 조건 조합    O         O              X
  G12  표 안의 조건 조합    O         O              X
  G15  표 안의 조건 조합    O         O              X
  G19  개정 전후 비교      O         O              X
  G25  규정에 없는 사항     X         O              O
```

G11·G12·G15 가 한 묶음이다. 셋 다 `expect_kind: 표` 이고 하이브리드에서만 틀린다.
G06 은 Multi-Query 에서 틀렸다가 하이브리드에서 돌아온다.

## 고장 하나 — 표가 조항에 밀렸다

G11 의 상위 3건을 세 설정에서 뽑아 봤다.

```text
G11  4급 직원이 광역시로 출장 가면 일비와 숙박비는 각각 얼마인가요?
     기대 DOC-HR-014 v2.0  kind=표  kw=['30,000', '70,000']

--- 기본 검색  (best 0.7084)
    0.7084 [표 ] DOC-HR-014 v2.0 표2                          ← 정답
    0.6733 [조항] DOC-HR-014 v2.0 제3장 제1절 제11조(일비) · 별표1
    0.6658 [조항] DOC-HR-014 v2.0 제3장 제2절 제14조(숙박비) · 별표1

--- + Multi-Query  (best 0.7100)
    0.7100 [표 ] DOC-HR-014 v2.0 표2                          ← 정답
    0.6700 [조항] DOC-HR-014 v2.0 제3장 제1절 제11조(일비) · 별표1
    0.6700 [조항] DOC-HR-014 v2.0 제3장 제2절 제14조(숙박비) · 별표1

--- + 하이브리드  (best 0.6700)
    0.6700 [조항] DOC-HR-014 v2.0 제3장 제2절 제14조(숙박비) · 별표1
    0.6700 [조항] DOC-HR-014 v2.0 제3장 제1절 제11조(일비) · 별표1
    0.6600 [조항] DOC-HR-014 v1.1 제3장 제8조(일비) · 별표1      ← 만료본
```

**0.71 로 1위였던 `표2` 가 상위 3건에서 사라졌다.**

BM25 가 조항 쪽을 위로 올렸고 RRF 가 그걸 받았다. 표는 `| 직급 | 일비 | 숙박비 |`
같은 모양이라 질문의 낱말과 겹치는 글자가 적다. 조항은 문장이라 겹치는 낱말이 많다.
**BM25 는 표를 불리하게 본다.**

이유의 절반은 토크나이저다([[73_키워드_검색과_RRF]]). 쉼표가 금액을 가르는 탓에
표2 의 토큰이 `['2급', '40', '000', '100', '000', ...]` 이 되고, 질문과 겹치는 것이
`2급` 하나뿐이다. 표에는 문장이 없으니 금액이 부서지면 남는 것이 없다.

[[50_청킹_규칙]]에서 표를 자르지 않고 한 덩이로 둔 것이 벡터 검색에서는 값을 했는데
키워드 검색에서는 거꾸로 작용한다. 같은 청킹이 검색 방식에 따라 유리하고 불리하다.

그리고 3위에 `v1.1` 이 들어왔다. 이게 두 번째 고장이다.

### 파이프라인이 실제로 돌 때의 건수

```text
[1단계] 질의 재작성 · Multi-Query 2건 생성  (0.0s)   state=ok
[2단계] 벡터 + 키워드 하이브리드 검색 · 벡터 14건 · 키워드 12건 → 후보 18건  (0.4s)   state=ok
```

벡터 14건은 두 갈래가 각각 12건을 가져와 중복을 지운 결과다. 키워드 12건과 합쳐
후보가 18건이 된다. 그 18건이 `rerank_top_n = 3` 으로 좁혀지므로 15건이 버려진다.

후보를 넓히는 것과 3건만 남기는 것이 같이 있으면 넓힌 만큼 경쟁이 세진다.
정답이 밀려나는 자리가 여기다.

## 고장 둘 — 정책 필터를 지나치지 않는다

[[72_질의_재작성과_Multi_Query]]에 적은 일곱 단계 중 5번 정책 필터가 코드에 없다.
`LiveRetriever.search()` 가 `policy.filter_candidates` 를 부르지 않는다.

세 설정에서 상위 3건에 무엇이 섞이는지 세어 봤다.

```text
설정                만료(v1.1) 섞인 문항   대외비·3급 섞인 문항   순서≠점수
기본 검색                        3                 5          0
+ Multi-Query                 18                 6          4
+ 하이브리드                      18                10         11
```

**만료본이 3문항에서 18문항으로 늘었다.**

기본 검색의 3건은 정상이다. G17·G18·G20 이고 셋 다 「개정 전후 비교」 유형에
`wants_past_version=True` 다 — [[63_검색_정책]]의 정책이 과거를 묻는 질문에만 만료본을
열어 준 것이다. 나머지 18건은 정책을 아예 거치지 않아서 생겼다.

G19 가 「개정 전후 비교」인데 하이브리드에서 틀린 것도 여기서 설명된다. 만료본이
언제나 열려 있으면 과거 판을 열어 주는 일이 특별하지 않게 된다. 현행과 만료가
같은 후보 통에서 경쟁하고, 상위 3건에 어느 쪽이 들어올지는 점수가 정한다.

대외비·3급이 5 → 10 으로 늘어난 것은 지금은 문제가 안 된다. `EVAL_USER` 가 대외비라
전부 열람 권한이 있다([[64_골든셋과_채점기]]). 다만 일반 등급 사용자가 같은 경로로
검색하면 **열람 권한 없는 문서가 근거로 올라간다.** [[62_현행_판과_보안등급]]에 적은
"화면에서만 가리면 응답 본문에는 실려 나간다"가 이 자리다.

## 고장 셋 — 순서와 점수가 다른 자를 쓴다

`순서≠점수` 가 0 → 4 → 11 로 늘었다. 상위 3건의 점수가 내림차순이 아닌 문항 수다.

```text
G25  해외 출장 시 비즈니스석 탑승 기준이 어떻게 되나요?   (unanswerable)

--- + Multi-Query  (best 0.5000)
    0.4500 [조항] DOC-HR-014 v1.1 제3장 제11조(숙박비) · 별표1
    0.5000 [조항] DOC-HR-014 v1.1 DOC-HR-014_v1.1
    0.5000 [조항] DOC-HR-014 v2.0 제1장 제1조(목적)
```

1위가 0.45 이고 2·3위가 0.50 이다. [[73_키워드_검색과_RRF]]에 적은 설계의 부작용이다 —
순서는 RRF(또는 늘린 질의 중 최고점)가 정하고 점수는 원래 질문과의 코사인 유사도로
다시 재기 때문이다.

임계값 판정은 `max()` 를 쓰므로 틀리지 않는다. 다만 **근거를 화면에 보여 줄 때
첫 줄이 가장 가까운 조각이 아니다.** 사용자는 위에서부터 읽는다.

## G25 는 운으로 맞았다

G25 가 기본 검색에서 틀렸다가 Multi-Query 에서 맞았다. [[65_측정값_뜯어보기]]에서
0.5646 으로 임계값을 간신히 넘어 「지어낼 위험」으로 판정됐던 그 문항이다.

```text
기본 검색      best 0.5646   → 임계값 초과 → 오답
+ Multi-Query  best 0.5000   → 근거 부족 정상 → 정답
```

점수가 내려가서 맞았다. 그런데 상위 3건을 보면 `v1.1` 의 목차 조각과 `제1조(목적)` 이다.
[[65_측정값_뜯어보기]]에서 기본 검색이 2위로 가져왔던 「국외 지역으로의 출장에
대하여는 따로 정한다」가 사라졌다.

**근거가 나빠져서 점수가 내려갔고, 점수가 내려가서 정답이 됐다.** 채점은 맞았지만
검색은 나빠졌다. [[65_측정값_뜯어보기]]에 적은 「없다고 적힌 조항이 걸리는 것이 더 좋은
상태」가 여기서 사라졌는데 점수는 올라간다.

측정값 하나가 올라간 것을 개선으로 읽으면 안 되는 예다.

## 정리

| 고장 | 증상 | 고치는 곳 |
| --- | --- | --- |
| BM25 가 표를 불리하게 본다 | 표 유형 5/6 → 2/6 | 유형별 가중치, 또는 표 전용 경로 |
| 정책 필터를 건너뛴다 | 만료본 3 → 18문항 | `LiveRetriever` 에 5단계 추가 |
| 순서와 점수가 다른 자 | 순서≠점수 0 → 11문항 | 화면 표시 순서를 점수로 다시 정렬 |
| 리랭킹이 없다 | 6단계 미구현 | 크로스 인코더 |

세 고장 중 둘은 빠뜨린 단계 때문이고 하나는 설계의 부작용이다. 기법 자체가
나쁜 것이 아니라 파이프라인이 덜 끝난 상태로 측정했다.

### 측정 전에 같은 조건으로 맞춰야 한다

가장 크게 배운 것은 이쪽이다. 세 설정이 **거르는 단계가 서로 다르다.**
기본 검색은 정책을 거치고 나머지 둘은 안 거친다. 그 상태로 점수를 나란히 놓으면
무엇을 비교한 것인지 알 수 없다.

[[69_골든셋_점검기]]에서 측정 전에 골든셋이 데이터와 맞는지 보는 검사를 만들었는데,
설정끼리 같은 조건인지를 보는 검사도 필요하다. 지금 숫자 셋은 **기법 비교가 아니라
구현 완성도 비교**다.

### 그래도 남는 것

Multi-Query 가 「규정에 없는 사항」을 4/6 에서 5/6 으로 올린 것은 우연이 아닐 수 있다.
질문을 늘려 후보가 넓어지면 특정 조각 하나에 쏠린 점수가 평평해진다. 근거 부족을
감지하는 쪽에는 그게 유리하다.

다만 G25 가 운으로 맞은 것을 보면 이 한 건으로는 알 수 없다. 정책 필터를 붙이고 다시
재야 판단할 수 있다.
