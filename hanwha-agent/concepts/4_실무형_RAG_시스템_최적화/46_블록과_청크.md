# 블록과 청크

[[33_RAG_개요]] ③ Chunking 자리다. 파서가 이미 문서를 잘라 놓았는데([[39_문서_파싱]]) 그걸 그대로 쓰지 않는 이유부터 본다.

```text
문서 → 파싱 → [청킹 → 임베딩] → 적재 → 검색
```

## 파서가 준 것

`v2.0` 짜리 여비 규정 하나를 열었다.

```python
from app.rag.local_parsers import parse_local

TARGET = next(SAMPLES.glob('DOC-HR-014_*_v2.0.docx'))
doc = parse_local(TARGET)
print(f'블록 {len(doc.blocks)} · 표 {doc.table_count} · 쪽 {doc.page_count}')
```

```text
블록 233 · 표 7 · 쪽 1
```

블록 하나가 문단 하나 또는 표 하나다.

```text
[ 0] 조항 | DOC-HR-014_국내출장_여비_규정_v2.0 | 일반
[ 1] 조항 | DOC-HR-014_국내출장_여비_규정_v2.0 | 국내출장 여비 규정
[ 2] 조항 | DOC-HR-014_국내출장_여비_규정_v2.0 | v2.0
[ 3] 조항 | DOC-HR-014_국내출장_여비_규정_v2.0 | 문서번호  DOC-HR-014
[ 4] 조항 | DOC-HR-014_국내출장_여비_규정_v2.0 | 시행일    2025-07-01
```

## 통째로 넣으면

233개를 이어 붙이면 규정 한 편이 된다.

```python
joined = '\n'.join((b.text for b in doc.blocks))
print(joined[4000:4200])
```

```text
 기준으로 한다.
② 3급 이상의 직원은 업무 수행상 필요한 경우 특실을 이용할 수 있다.
③ 심야 이동으로 침대차를 이용한 경우에는 그 요금을 지급하고 숙박비를 지급하지 아니한다.
제19조(항공기)
...
```

4,000자 지점이 제19조다. 문서 한 편이 프롬프트 하나에 다 들어가면 [[32_사용량과_원가_기록]]에서 센 입력 토큰이 질문마다 그만큼 붙는다. 숙박비를 묻는데 항공기 조항까지 실려 간다.

## 블록 하나만 넣으면

반대쪽을 본다. 숙박비가 들어 있는 블록을 세어 보면 27개다.

```python
hits = [(i, b) for i, b in enumerate(doc.blocks) if '숙박비' in b.text]
```

```text
'숙박비' 가 들어 있는 블록 : 27개
  [  9] 291자 | | 버전 | 구분 | 시행일 | 주요 내용 | 작성 | 검토 | 승인 |
  [ 29]   7자 | 제2절 숙박비
  [ 30]   9자 | 제14조(숙박비)
  [ 32]  13자 | 제16조(숙박비의 예외)
  [ 68]  39자 | 3. "여비"란 출장에 소요되는 일비·식비·숙박비 및 교통비를 말한다.
```

"광역시 숙박비가 얼마까지 되나요?"에 답하는 블록을 골라 보면 이렇다.

```text
고른 블록 : ② 광역시 지역의 숙박비는 1박당 70,000원을 상한으로 한다.
  이 블록 안에 조 표시가 있나 : False
  30자도 안 되는 블록 : 131개 / 233개
```

**답은 맞는데 어느 조항인지가 블록 안에 없다.** 제14조라는 표시는 30번 블록에 9자짜리로 따로 떨어져 있다. 이 블록만 검색해서 넘기면 [[45_채팅_화면]]에서 비어 있던 ⑪ Citation 에 적을 것이 여전히 없다. 근거를 대려면 "제14조 ②항"이라고 말해야 하는데 그 정보가 다른 블록에 있다.

233개 중 131개가 30자도 안 된다. 절 제목, 조 제목, 문서번호 같은 것들이다. 이것들을 하나씩 검색 단위로 만들면 **뜻이 없는 조각이 검색 결과의 절반을 차지한다.**

## 그래서 둘이 다르다

| | 무엇 | 누가 정하나 |
| --- | --- | --- |
| 블록 | 파서가 보는 단위 — 문단 하나, 표 하나 | 문서와 파서 |
| 청크 | 검색이 쓸 단위 — 조 하나, 표 하나 | 우리 |

블록은 주어진 것이고 청크는 정하는 것이다. 파서를 고쳐서 블록을 크게 만드는 방법도 있지만 그렇게 하지 않는다. 파서는 문서 구조를 그대로 옮기는 일만 하고([[44_파일_형식_분기와_차단]]), 검색에 맞게 묶는 일은 다음 단계로 넘긴다. 같은 파서 출력으로 청킹 방식을 여러 개 시험해 볼 수 있어야 하기 때문이다.

이 문서에서 청크는 **조 단위**가 후보다. 제14조 제목과 그 아래 ①②③을 한 덩이로 묶으면 문맥과 출처가 같이 들어간다. 표는 표 하나가 이미 한 덩이다([[40_표_추출과_마크다운]]).

## 설치한 것

```bash
python -m pip install "sentence-transformers==6.0.1" "langchain-text-splitters==1.1.2"
```

| | 하는 일 |
| --- | --- |
| `sentence-transformers` | 문장을 벡터로 바꾼다 — ④ Embedding([[47_벡터와_코사인_유사도]]) |
| `langchain-text-splitters` | 긴 글을 정해진 길이로 자른다 — ③ Chunking |

**자르는 코드를 쓰기 전에 왜 자르는지를 먼저 봤다.** `langchain-text-splitters` 는 깔아 두고 아직 부르지 않았다. `sentence-transformers` 쪽은 같은 날 오후에 실제로 열었다([[48_임베딩_모델_비교]]).

## 짚어둘 것

청크 크기는 [[33_RAG_개요]]에 적어 둔 그 상충 관계를 그대로 만난다. 크면 관계없는 내용이 프롬프트에 실려 비싸지고, 작으면 문맥이 끊긴다. 위에서 본 두 극단이 그 양쪽 끝이다.

정답이 하나 있는 문제가 아니라 문서 구조에 맞춰 정하는 문제다. 여비 규정은 조 단위가 뚜렷해서 기준이 보이지만, 조가 없는 문서(`_formats` 안의 메모나 공지)는 글자 수로 자를 수밖에 없다.
