# 거리 연산자와 색인

[[58_임베딩_적재]]에서 1,024개짜리 숫자 묶음을 칼럼에 넣었다. 그 숫자들로
"가깝다"를 어떻게 재는지, 그리고 빨리 재려면 무엇이 더 필요한지를 본다.

## 셋 다 "작을수록 가깝다"

pgvector 가 주는 연산자는 셋이다.

| 연산자 | 이름 | 무엇을 재나 | 연산자 클래스 |
| --- | --- | --- | --- |
| `<=>` | 코사인 거리 | 두 벡터가 이루는 각도. `1 - 코사인유사도` | `vector_cosine_ops` |
| `<->` | L2 거리 | 두 점 사이의 직선 거리 | `vector_l2_ops` |
| `<#>` | 내적의 음수 | 곱해 더한 값에 마이너스 | `vector_ip_ops` |

내적만 부호가 뒤집혀 있다. 내적은 클수록 가까운데, 그대로 두면 정렬 방향이 혼자 반대가
된다. 마이너스를 붙여 셋을 "작을수록 가깝다"로 맞춰 두면 `ORDER BY ... ASC` 하나로
전부 쓸 수 있다.

## 정규화한 벡터에서는 셋이 같은 정보다

각도를 내가 정한 벡터를 넣고 예측값과 실측값을 맞춰 봤다.

```text
청크                 cos |    <=> 예측        실측 |    <-> 예측        실측 |    <#> 예측        실측
합성-같은 방향           1.0 |    0.0000    0.0000 |    0.0000    0.0000 |   -1.0000   -1.0000
합성-가까움             0.8 |    0.2000    0.2000 |    0.6325    0.6325 |   -0.8000   -0.8000
합성-중간              0.5 |    0.5000    0.5000 |    1.0000    1.0000 |   -0.5000   -0.5000
합성-직각              0.0 |    1.0000    1.0000 |    1.4142    1.4142 |   -0.0000   -0.0000
```

크기가 1 인 벡터끼리는 셋이 한 값에서 나온다.

```text
<=>  =  1 - cos
<->  =  sqrt(2 - 2cos)  =  sqrt(2 × <=>)
<#>  =  -cos            =  -(1 - <=>)
```

수업에서 나온 실제 값으로 맞춰 봐도 그대로다.

```text
<-> 는 sqrt(2 × 코사인거리) 인가 : sqrt(2×0.3074) = 0.7841  (수업 출력 0.7841)
<#> 는 -(1 - 코사인거리) 인가    : -(1-0.3074) = -0.6926  (수업 출력 -0.6926)
```

그래서 수업에서 세 연산자로 각각 정렬했을 때 **다섯 건의 순서가 똑같이 나왔다.**
값만 다르고 순위는 같다.

이게 되는 전제는 로컬 어댑터의 이 한 줄이다.

```python
vectors = self._model.encode(texts, normalize_embeddings=True)
```

정규화를 끄면 길이가 제각각이 되고, 그때는 L2 와 내적이 각도가 아니라 길이에 끌려간다.
긴 문서의 벡터가 길어져서 "내용이 비슷해서"가 아니라 "길어서" 위로 올라온다.
[[47_벡터와_코사인_유사도]]에 적어 둔 "정규화하면 내적이 곧 코사인"이 여기서 쓰인다.

## 거리를 점수로 뒤집는다

```python
_row(chunk, version, doc, 1.0 - float(dist))
```

DB 는 거리를 준다. 작을수록 가깝다. 화면에 그대로 내면 "0.3074 점" 이 좋은 건지 나쁜 건지
읽는 사람이 모른다. `1.0 - 거리` 로 뒤집으면 클수록 가까운 익숙한 점수가 된다.

순서는 뒤집어도 바뀌지 않는다.

```text
[ distance 오름차순 ]        [ score 내림차순 ]
  0.0     ...                1.0     ...
  0.3074  제1장 제3조(발급)      0.6926  제1장 제3조(발급)

두 표의 순서가 같은가 : True
```

단조 변환이라 당연한데, 당연한 것을 한 번 찍어 확인해 두면 나중에 점수 기준으로
자르는 코드를 쓸 때 안심하고 쓸 수 있다.

## HNSW 색인

```sql
CREATE INDEX chunks_embedding_hnsw ON chunks USING hnsw (embedding vector_cosine_ops);
```

연산자 클래스를 골라서 만든다. `vector_cosine_ops` 로 만든 색인은 `<=>` 로 정렬할 때만
쓰인다. `<->` 로 질의하면 같은 색인이 있어도 안 탄다. 쓰는 연산자와 만든 색인이 짝이어야 한다.

### 지금 규모에서는 색인이 테이블보다 크다

```text
chunks_pkey                16 kB
ix_chunks_version_id       16 kB
chunks_embedding_hnsw      40 kB
테이블 본체                8192 bytes
```

본문 8 kB 에 색인이 40 kB 다. HNSW 는 벡터 사이의 이웃 관계를 그래프로 따로 쌓기 때문에
행이 적을 때는 배보다 배꼽이 크다.

### 그리고 안 탄다

```text
[enable_seqscan=off]
  Limit  (cost=20.03..24.08 rows=4 width=12)
    ->  Index Scan using chunks_embedding_hnsw on chunks  (cost=20.03..24.08 ...
          Order By: (embedding <=> '[1,0,0,...
[enable_seqscan=on]
  Limit  (cost=1.09..1.10 rows=4 width=12)
    ->  Sort  (cost=1.09..1.10 rows=4 width=12)
          ->  Seq Scan on chunks  (cost=0.00..1.05 rows=4 width=12)
```

`enable_seqscan` 을 꺼야 색인을 탄다. 켜 두면 플래너가 전부 훑는 쪽을 고른다.
비용 추정이 24.08 대 1.10 이다. 네 줄짜리 테이블에서는 색인을 거쳐 가는 것보다
그냥 읽는 게 싸고, 플래너 판단이 맞다.

색인은 지금 필요해서가 아니라 **나중에 필요할 때 이미 있으라고** 만든다.
수만 건이 쌓인 뒤에 만들면 그동안 모든 질의가 전부 훑는다. 그 느려짐은
데이터가 적을 때는 티가 안 나고 쌓인 뒤에 온다([[49_임베딩_모델_고르기]]의 차원 문제와 같은 모양이다).

### 색인이 마이그레이션에 없다

```text
grep hnsw backend/app/db/migrations/versions/*.py → 어느 리비전에도 없음
```

`psql` 로 직접 만들었기 때문이다. 내 DB 에는 있지만 **새로 클론해서
`alembic upgrade head` 를 한 사람에게는 안 생긴다.** 스키마의 일부인데 스키마 이력에
없는 상태다.

확장 `vector` 도 같다. 둘 다 `op.execute()` 한 줄로 리비전에 넣을 수 있는 것이라,
넣어 두는 쪽이 맞다. 지금은 적어만 두고 넘어간다.
