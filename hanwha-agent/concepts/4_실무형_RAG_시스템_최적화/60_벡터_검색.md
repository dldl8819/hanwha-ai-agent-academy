# 벡터 검색

[[58_임베딩_적재]]에서 벡터를 넣고 [[59_거리_연산자와_색인]]에서 거리를 쟀다.
이제 질문 하나로 근거를 찾아온다. RAG 11단계 중 ⑥질의와 ⑦검색이다.

## 화면에 필요한 값이 테이블 셋에 흩어져 있다

| 테이블 | 거기서만 알 수 있는 것 |
| --- | --- |
| `chunks` | 본문, 출처(locator), 종류(조항·표) |
| `document_versions` | 어느 판인지, 현행인지 만료인지 |
| `documents` | 문서 제목, 소관 부서, 보안등급 |

검색 결과 한 줄을 사용자에게 보여주려면 셋을 다 붙여야 한다. "제14조(숙박비)"만 주면
어느 문서의 몇 판에서 나온 것인지 알 수 없고, 보안등급을 모르면 보여도 되는지 판단할 수 없다.

```python
stmt = (
    select(Chunk, DocumentVersion, Document, distance)
    .join(DocumentVersion, Chunk.version_id == DocumentVersion.id)
    .join(Document, DocumentVersion.doc_id == Document.id)
    .where(Chunk.embedding.is_not(None))
    .order_by("distance")
    .limit(limit)
)
```

한 번의 질의로 가져온다. 청크를 먼저 찾고 그 다음에 문서를 하나씩 조회하면
결과 12건에 질의가 25번 나간다.

```text
돌려준 칸: ['chunk_id', 'dept_id', 'doc_id', 'kind', 'locator', 'score',
           'security_level', 'text', 'title', 'version', 'version_status']
```

```text
score 0.9815  DOC-HR-014 v2.0 (현행) · 합성-가까움   · 국내출장 여비 규정 / HRGA / 일반
score 0.9     DOC-HR-014 v2.0 (현행) · 합성-같은 방향 · 국내출장 여비 규정 / HRGA / 일반
```

`version_status` 와 `security_level` 이 결과에 실려 나온다. 아직 아무도 쓰지 않지만
거를 재료는 갖춰진 셈이다.

### `embedding IS NOT NULL` 이 필요한 이유

칼럼을 `nullable=True` 로 더했기 때문이다([[58_임베딩_적재]]). 벡터가 없는 청크는
거리를 잴 수 없고, 빼지 않으면 `NULL` 이 섞여 정렬이 흐트러진다.

## 질문으로 찾아봤다

숙박비가 실제로 적힌 문서(`DOC-HR-014 국내출장 여비 규정`)를 올리고 물었다.

```text
'숙박'                         → 17줄
'숙박비'                        → 17줄
'출장 갈 때 숙박비 얼마?'             → 0줄
'출장 숙박비'                     → 0줄
```

```text

      제14조(숙박비) ① 숙박비는 실제 지출한 금액으로 지급하되, [별표1]의 상한을 …
  2. score 0.6507  DOC-HR-014 v9.9 (현행) · 표3
  3. score 0.649   DOC-HR-014 v9.9 (현행) · 표2
      | 직급 | 일비 | 숙박비(광역시) | 숙박비(그 밖의 지역) | 식비 | …
  4. score 0.6423  DOC-HR-014 v9.9 (현행) · 제3장 제1절 제12조(식비) · 별표1
```

1위가 `제14조(숙박비)` 이고 3위가 금액이 적힌 표다. `LIKE` 로 0줄이던 문장이
조문과 금액표를 같이 집어 온다. 출처도 `제3장 제2절 제14조(숙박비)` 로 나와
그대로 근거로 쓸 수 있다([[50_청킹_규칙]]에서 조 단위로 묶고 장·절을 붙인 결과다).

### 느린 쪽은 검색이 아니다

```text
회차           질문 임베딩       벡터 조회
1           11.145초      0.171초  ← 모델 여는 값 포함
2            0.096초      0.051초
3            0.095초      0.049초
4            0.090초      0.050초
```

질문 하나를 벡터로 바꾸는 데 0.09초, 5만 번 비교해 가까운 것을 찾는 데 0.05초다.
첫 회차의 11초는 임베딩이 아니라 모델을 처음 메모리에 올리는 값이고,
`factory` 의 `@lru_cache` 덕에 프로세스당 한 번만 든다([[58_임베딩_적재]]).

서버를 재시작한 뒤 첫 사용자만 그 11초를 기다린다. 뜰 때 미리 한 번 불러 두면
없앨 수 있는 비용이다.

## 문제 1 — 같은 내용이 여러 번 나온다

위 결과는 한 판만 올려서 깨끗하다. 수업에서는 같은 문서의 v1.4·v2.0·v2.1 을 다 올렸고
이렇게 나왔다.

```text
1. DOC-FI-009 v1.4 - 제2장 제11조(출장 중 사용)   score 0.557
2. DOC-FI-009 v2.0 - 제2장 제11조(출장 중 사용)   score 0.557
3. DOC-FI-009 v2.1 - 제2장 제11조(출장 중 사용)   score 0.557
```

1·2·3위가 같은 조항의 세 판본이고 점수까지 같다. 그 조항의 본문이 세 판에서 같기 때문이다.
`limit=3` 이면 사용자가 받는 근거 세 건이 한 문장이다. 수업에서 12로 늘렸지만
4·5·6위가 또 같은 표의 세 판본이라, 늘리는 것은 증상을 미루는 쪽이다.

[[55_청크_저장]]에서 청크를 문서가 아니라 버전에 매단 이유가 "판마다 본문이 다르므로"
였는데, 본문이 **같은** 판들이 섞이면 이번에는 중복이 된다. 검색은 현행 판만 봐야 한다.
`version_status` 가 이미 결과에 실려 있으니 거를 재료는 있다.

이게 작업 단계 목록의 마지막 한 칸이다.

```text
  ok    임베딩
  todo  검색 반영 및 현행 버전 지정
```

## 문제 2 — 근거가 없어도 답을 돌려준다

수업에서는 법인카드 지침만 올린 상태로 숙박비를 물었다. 숙박비가 적힌 문서는
올리지 않았는데도 열두 건이 모두 돌아왔고 1위 점수가 0.557 이었다.

위에서 맞는 문서를 올렸을 때 1위가 0.6795 다. 0.557 과 0.6795 의 차이로
"답이 있다"와 "없다"를 가를 수 있을까. 경계가 좁고, 문서가 바뀌면 또 달라진다.

**없는데도 빈손으로 돌아오지 않는다.** 벡터 검색은 "가장 가까운 k 개"를 돌려주는
기능이지 "맞는 답이 있는지"를 가려 주는 기능이 아니다. 점수 하한을 두거나,
근거가 약하면 모른다고 답하게 만드는 일은 ⑨프롬프트와 ⑩LLM 쪽에서 해야 한다.
[[28_가드와_재시도_폴백]]에서 만든 3단 방어와
[[29_골든셋_회귀테스트]]의 "근거 없으면 모른다고 답하는지" 검사가 쓰일 자리가 여기다.

## 모델이 있을 때와 없을 때

노트를 쓰는 동안은 임베딩 모델(2.29GB × 2)이 받아져 있지 않아 수업 출력을 봤다.
받은 뒤에 같은 것을 다시 돌려 위 수치로 바꿨다. 그 사이에 알게 된 것이 있다.

| | |
| --- | --- |
| 모델이 있어야 | 질문·문서의 벡터, 점수가 말이 되는지 |
| 없어도 되는 것 | 칼럼 왕복, 거리 연산자 셋의 관계, 색인이 타는지, 조인과 결과 모양 |

각도를 정해 만든 벡터를 넣으면 뒤쪽은 전부 눌러 볼 수 있다([[59_거리_연산자와_색인]]).
"모델이 좋은가"와 "배선이 맞는가"는 다른 질문이고 섞어 보면 어느 쪽이 틀렸는지 모른다.
모델이 없어서 어쩔 수 없이 나눴는데, 나누고 보니 나누는 쪽이 원래 맞았다.
