# 오답 목록과 약한 유형

[[65_측정값_뜯어보기]]는 손으로 뜯어본 것이다. 다음 측정에도 같은 일을 하려면
오답 목록이 코드로 나와야 한다. [[64_골든셋과_채점기]]에서 만들어 두고 비워 뒀던
`eval_weak_types` 테이블도 이번에 채웠다.

## 리포트에서 틀린 것만 뽑는다

```python
latest = sorted(REPORTS.glob('eval_*.json'))[-1]
results = json.loads(latest.read_text(encoding='utf-8'))['runs'][0]['results']
wrong = [r for r in results if not r['ok']]
```

`sorted(...)[-1]` 로 마지막 리포트를 집는다. 파일 이름이 `eval_20261012_112528.json`
이라 문자열 정렬이 시간 정렬과 같아서 통한다. 이름 규칙을 바꾸면 조용히 엉뚱한 파일을
집는다. 수정 시각으로 고르는 쪽이 더 안전하지만 지금은 이름이 그 역할을 겸한다.

```text
틀린 문항 6개

```

[[64_골든셋과_채점기]]에서 `judge()` 가 사유를 문자열로 함께 돌려준 것이 여기서
값을 한다. `ok` 만 있었으면 이 표를 만들 수 없다.

## 사유를 묶을 때 숫자를 지운다

```python
label = re.sub('\\(.*?\\)', '', r['why']).strip()
```

괄호 안을 지워 `임계값 초과(0.56)` 와 `임계값 초과(0.60)` 을 한 줄로 묶는다.

```text
사유별
  정답 문서가 상위에 없음           4
  임계값 초과 - 지어낼 위험         2
```

**이 두 줄이 [[65_측정값_뜯어보기]]의 출발점이다.** 그리고 함정이기도 하다.
위쪽 4건이 한 사유로 묶였지만 원인은 네 가지였다. 집계는 묶는 일이고 진단은 푸는
일이라 방향이 반대다. 집계표에서 멈추면 "검색이 문서를 못 찾는다"는 결론이 나온다.

## 약한 유형을 정답률 순으로 줄 세운다

```python
ranked = sorted(by_type.items(),
                key=lambda kv: (kv[1]['ok'] / kv[1]['n'], list(DIAGNOSIS).index(kv[0])))
```

정답률 오름차순이다. 약한 쪽이 위로 온다.

두 번째 키가 `list(DIAGNOSIS).index(kv[0])` 다. 동률일 때 `DIAGNOSIS` 딕셔너리에
선언한 순서를 따른다는 뜻이다. 진단 문구를 적어 둔 자리가 화면 순서까지 쥐고 있다.
문구를 보기 좋게 재배치하면 표의 줄 순서가 바뀐다.

```python
for i, (label, stat) in enumerate(ranked[:4]):
```

다섯 유형 중 넷만 남긴다. 100% 인 「개정 전후 비교」가 빠진다. 약한 쪽을 보는 표라
맞는 선택인데, 넷째와 다섯째가 동률이면 어느 것이 잘릴지가 위의 딕셔너리 순서에 달려 있다.

```text
 ord | label                | count | accuracy | diagnosis
-----+----------------------+-------+----------+------------------------------
   0 | 타 부서 문서 참조    |     4 | 50.0     | 보안등급 정상 차단 · 시험지 오류 2건
   1 | 규정에 없는 사항     |     6 | —        | 근거부족 정상
   2 | 표 안의 조건 조합    |     6 | 83.3     | 표가 조항 단위로 잘림
   3 | 단일 조항            |    10 | 90.0     | 정답 문서가 상위에 없음
```

### accuracy 가 숫자가 아니라 문자열인 이유

```python
accuracy: Mapped[str] = mapped_column(String(16), default="-")
```

`'—'` 를 넣기 때문이다. 「규정에 없는 사항」은 정답률을 가렸다.

가린 이유는 이 유형의 채점 방향이 뒤집혀 있어서다. 다른 유형의 66.7% 는 "셋 중 둘을
찾았다"는 뜻이고 이 유형의 66.7% 는 "여섯 중 넷을 안 지어냈다"는 뜻이다. 같은 칸에
나란히 두면 읽는 사람이 같은 뜻으로 받는다.

대신 가리면 비교도 못 한다. 다음 측정에서 4/6 이 5/6 으로 올라가도 표에는 `—` 다.
단위가 다른 숫자를 한 표에 담으려 한 데서 온 문제이고, 칸을 나누는 쪽이 맞다고 본다.

문자열로 두면 DB 에서 정렬도 비교도 못 한다. 그래서 줄 세우기를 파이썬이 하고
`ord` 로 결과만 적어 둔다([[66_측정_이력_내보내기]]).

## 진단 문구 셋이 사실과 다르다

```python
DIAGNOSIS = {
    '단일 조항': top_reason('단일 조항'),
    '표 안의 조건 조합': '표가 조항 단위로 잘림',
    '타 부서 문서 참조': '보안등급 정상 차단 · 시험지 오류 2건',
    ...
}
```

**「보안등급 정상 차단」은 일어나지 않았다.** `EVAL_USER` 가 대외비 등급이라
`DOC-PU-007`·`DOC-SE-003` 이 그대로 통과했다. [[65_측정값_뜯어보기]]에서 등급을
바꿔 재 보니 일반 등급에서만 차단이 생긴다. 이 유형의 오답 2건은 전부 시험지 오류이고
차단은 0건이다.

**「표가 조항 단위로 잘림」도 아니다.** 직급별 일비 표는 `표2` 로 온전히 남아 있고
`kind` 도 `표` 다. G16 이 틀린 이유는 그 표가 5위여서다 — 3·4위를 문서 표지와 목차
조각이 차지했다. 잘린 것이 아니라 밀린 것이다.

「단일 조항」 쪽은 `top_reason()` 이 사유 문자열을 그대로 가져온다.

```python
def top_reason(label: str) -> str:
    reasons = [re.sub('\\(.*?\\)', '', r['why']).strip() for r in wrong if r['type'] == label]
    return max(set(reasons), key=reasons.count) if reasons else '오답 없음'
```

그래서 진단 칸에 `정답 문서가 상위에 없음` 이 들어간다. 이건 증상이다. G07 의 원인은
`DOC-FI-009` 가 색인되지 않은 것이다. 손으로 적은 둘도 틀렸고 자동으로 채운 것도 틀렸다. **사유 칸과 진단 칸이 같은 말이면 진단 칸이
있을 이유가 없다.** 자동으로 채울 수 있는 것은 증상까지이고 원인은 사람이 적어야 한다.

## 두 테이블의 시점이 어긋날 수 있다

`eval_runs` 는 `run_eval.py` 의 `save()` 가 쓰고, `eval_weak_types` 는 이 노트북이 쓴다.
쓰는 사람이 다르다.

다음에 `run_eval.py` 만 돌리면 `eval_runs` 는 새 측정으로 갈리고 `eval_weak_types` 는
옛 측정의 집계를 그대로 들고 있다. 화면은 둘을 나란히 그리면서 서로 다른 측정을
보여 준다. 집계까지 `save()` 안으로 들어가야 맞다.

```python
for old in s.execute(select(EvalWeakType)).scalars().all():
    s.delete(old)
```

지우는 방식도 다르다. `save()` 는 `session.query(EvalRun).delete()` 로 한 번에 보내고
여기는 객체를 하나씩 지운다. 4행이라 차이가 없지만, 전수 삭제라면 묶어 보내는 쪽이다.

쓰고 나서 `session_scope()` 를 다시 열어 읽는 것은 둬도 될 일이다.
`expire_on_commit=False` 라 같은 세션에서 읽어도 되지만, 커밋이 실제로 들어갔는지
DB 에 다시 물어보는 쪽이 확인으로는 낫다.
