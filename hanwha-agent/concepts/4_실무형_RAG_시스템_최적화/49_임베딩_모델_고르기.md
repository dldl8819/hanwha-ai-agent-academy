# 임베딩 모델 고르기

[[48_임베딩_모델_비교]]에서 둘을 재 봤는데 6쌍으로는 결론이 안 났다. 점수 말고 **조건으로 후보를 좁히는** 쪽을 정리한다.

## 먼저 유형

표에 "Dense", "Dense + 멀티 벡터" 같은 말이 나온다. 검색용 벡터를 만드는 방식이 크게 둘이고 Dense 가 그중 하나다.

| | 희소(Sparse) | 밀집(Dense) |
| --- | --- | --- |
| 차원 | 어휘 사전 크기 (수만~수십만) | 1024 고정 |
| 값 | 대부분 0 | 거의 모든 칸이 0 이 아니다 |
| 한 칸의 뜻 | 특정 단어 하나 | 대응하는 단어가 없다 — 뜻이 흩어져 담긴다 |
| 예 | TF-IDF · BM25 · SQL `LIKE` | KURE-v1 · bge-m3 |

이름 그대로다. 희소는 0 이 대부분이라 성기고, 밀집은 값이 빽빽하다. [[47_벡터와_코사인_유사도]]에서 `LIKE '%잠자리%'` 가 0건이었던 것이 희소 방식의 한계였고, 같은 쌍이 코사인 0.6585 로 올라온 것이 밀집 방식이 한 일이다.

### 멀티 벡터

bge-m3 의 M3 는 Multi-Linguality · Multi-Functionality · Multi-Granularity 다. 가운데 것이 표의 "Dense + 멀티 벡터"로, 한 번 인코딩해서 검색 방식 셋을 낼 수 있다는 뜻이다.

| | 내놓는 것 | 맞춰보는 법 |
| --- | --- | --- |
| Dense | 문장당 벡터 1개 (1024) | 코사인 한 번 |
| Sparse | 토큰마다 가중치 | 어휘 매칭 |
| 멀티 벡터 | 토큰마다 벡터 1개씩 (N×1024) | 질문 토큰마다 문서 토큰 중 최적을 찾아 합산 |

멀티 벡터는 문장을 벡터 하나로 뭉개지 않으니 긴 글에서 세부가 덜 죽는다. 대가는 저장량이다. 여비 규정을 조 단위로 묶고 토큰을 세 봤다.

```text
조 단위 청크 73개 · 평균 65토큰 · 최대 1493토큰

청크 8,000개 기준 (1024차원 · 4바이트)
  Dense     벡터 1개/청크        :    31.25 MB
  멀티 벡터 토큰마다 1개 (65토큰) :     2.00 GB  ← 65배
```

[[47_벡터와_코사인_유사도]]에서 차원을 네 배로 올리면 4배라고 봤는데, 멀티 벡터는 65배다. 차원보다 **벡터 개수가 저장량을 더 크게 흔든다.**

## 세 후보

| | `nlpai-lab/KURE-v1` | `BAAI/bge-m3` | `upstage/solar-embedding` |
| --- | --- | --- | --- |
| 유형 | Dense | Dense + 멀티 벡터 | API |
| 차원 | 1024 | 1024 | 1024 |
| 최대 길이 | 8192 | 8192 | 8K |
| 베이스 | bge-m3 를 한국어로 파인튜닝 | 확장 XLM-R large | 비공개 |
| 가중치 | `model.safetensors` | `pytorch_model.bin` | 없음 |
| 라이선스 | MIT | MIT | 유료 약관 |
| 배포 형태 | 로컬 파일 | 로컬 파일 | 네트워크 호출 |
| 가격 | 0원 | 0원 | $0.02 / 1M 토큰 |

앞의 두 줄은 받아 둔 파일에서 확인된다.

```text
KURE-v1   model_type=xlm-roberta · hidden=1024 · max_pos=8194
bge-m3    model_type=xlm-roberta · hidden=1024 · max_pos=8194
```

`max_position_embeddings` 가 8194 인 것은 8192 에 특수 토큰 두 자리를 더한 값이다. 세 번째 열은 외부 서비스라 파일로 확인할 수 없고, 가격은 바뀔 수 있으니 도입 전에 다시 본다.

## 조건으로 좁힌다

점수를 매기기 전에 조건이 후보를 먼저 자른다.

| 조건 | 보는 칸 | 남는 것 |
| --- | --- | --- |
| 문서가 회사 밖으로 나가면 안 된다 | 배포 형태 | KURE-v1 · bge-m3 |
| 비용 0 으로 반복 실험해야 한다 | 가격 | KURE-v1 · bge-m3 |
| 한국어 규정 문서다 | 베이스 | KURE-v1 · solar |
| 색인이 걸려야 한다 | 차원 | 셋 다 (1024 < 2000) |
| 사내 배포에 라이선스 확인이 필요하다 | 라이선스 | KURE-v1 · bge-m3 |

첫 줄이 가장 세다. 대외비가 섞인 사내 규정을 다루므로 API 는 여기서 빠진다([[42_임베딩_모델_받기]]). 기술 비교가 아니라 보안 결정이라 점수로 뒤집지 않는다.

색인 조건은 [[47_벡터와_코사인_유사도]]에서 본 `pgvector` 의 2,000 한계다. 셋 다 1024 라 이 줄로는 아무도 안 걸린다. 차원이 큰 모델을 후보에 넣었다면 여기서 잘렸다.

남는 것은 로컬 둘이고, 그래서 48번에서 그 둘을 잰 것이다. **조건이 후보를 둘로 줄인 다음에 측정이 시작된다.** 순서가 반대면 쓸 수 없는 모델을 재느라 시간을 쓴다.

## 짚어둘 것

### 한국어 조건은 아직 근거가 없다

표의 세 번째 줄은 "한국어로 학습한 쪽이 낫다"는 가정이다. [[48_임베딩_모델_비교]]의 실측에서 KURE-v1 이 조금 나은 쪽으로 나오긴 했지만 6쌍짜리 결과였다. 가정을 표에 적어 두는 것과 확인한 것은 다르다.

### 멀티 벡터는 받았는데 안 쓴다

`bge-m3` 의 `modules.json` 을 보면 이렇다.

```text
Transformer → Pooling(CLS 토큰) → Normalize
```

Dense 경로 하나뿐이다. sentence-transformers 로 열면 1024 짜리 벡터 한 개가 나오고, sparse 와 멀티 벡터를 쓰려면 `FlagEmbedding` 으로 따로 불러야 한다. 표의 "Dense + 멀티 벡터"는 **모델의 능력**이지 우리가 쓰는 방식이 아니다.

지금 두 모델을 비교하는 조건이 같다는 뜻이기도 하다. 둘 다 Dense 로만 쓰고 있으니 48번의 비교는 공정하다.
