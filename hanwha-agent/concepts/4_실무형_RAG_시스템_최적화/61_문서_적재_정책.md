# 문서 적재 정책

[[58_임베딩_적재]]까지 만든 것으로 문서 한 건을 올리면 끝까지 돈다. 그런데 DB 에는
`seed.py` 가 만들어 둔 문서 아홉 줄이 이미 있었고, 그 줄들은 **파일도 청크도 없이
숫자만** 들고 있었다. 그 둘을 맞추는 일이다.

## 시드가 적어 둔 값은 전부 틀렸다

```text
문서           판      상태       시드    실제    벡터   표
DOC-FI-009   v2.1   현행        -     0     0   0  ←
DOC-HR-002   v3.1   현행      112    24    24   0  ←
DOC-HR-014   v1.1   만료       79    24    24   3  ←
DOC-HR-014   v2.0   현행       84    53    53   7  ←
DOC-HR-021   v1.2   현행       41    21    21   2  ←
DOC-PM-005   v2.0   현행       87    17    17   0  ←
DOC-PU-007   v4.0   현행      156    25    25   0  ←
DOC-SE-003   v2.2   현행       98    20    20   0  ←
DOC-SE-011   v1.0   현행       33    21    21   3  ←
합계                          690   205        15
```

**690 대 205.** 아홉 줄이 하나도 맞지 않는다.

`seed_data.py` 의 `chunk_count` 는 손으로 적어 둔 숫자였다. 화면은 그 값을 읽어
"690청크"라고 보여 주는데 `chunks` 테이블에는 한 줄도 없었다([[60_벡터_검색]]에
적어 둔 그대로다). 숫자를 만든 쪽과 숫자를 쓰는 쪽이 다르면 이런 일이 생긴다.

고치는 방향은 두 가지였다. 시드의 숫자를 0 으로 내리거나, 그 숫자가 가리키는 문서를
실제로 적재하거나. 뒤쪽을 골랐다. **숫자를 사실로 만드는 쪽이다.**

## 적재는 두 번 돌려도 안전해야 한다

```python
if dv is not None and real == 0 and dst.exists():
    document_service.ingest_document(doc_id=doc["id"], version=v["version"], path=str(dst))
```

조건이 셋이다.

| | 왜 |
| --- | --- |
| `dv is not None` | 시드에 있는 판이 DB 에 실제로 있어야 한다 |
| `real == 0` | **이미 청크가 있으면 건너뛴다** |
| `dst.exists()` | 파일이 실제로 있어야 한다 |

가운데가 핵심이다. `ingest_document` 는 안에서 기존 청크를 지우고 다시 넣으므로
([[55_청크_저장]]) 그냥 부르면 멀쩡한 205청크를 지우고 임베딩을 처음부터 다시 한다.
53청크에 1분 가까이 걸리는 일이라([[58_임베딩_적재]]) 아홉 줄이면 몇 분이 그냥 날아간다.

`real` 은 시드의 `chunk_count` 가 아니라 `chunks` 테이블을 세어 구한다. 거짓인 쪽을
기준으로 삼으면 조건 자체가 뜻이 없다.

재료 파일은 `samples/` 에서 `uploads/` 로 복사한 뒤 적재한다. 없으면 그 줄만 건너뛰고
나머지를 계속한다. 한 줄이 없다고 전체가 멈추면 어디까지 됐는지 알 수 없다.

## 청크가 0 인 판이 남는다

```text
청크가 0인 버전 ['DOC-FI-009 v2.1']
```

`DOC-FI-009 v2.1` 은 시드에 없다. 수업에서 화면으로 올려 본 문서다.
문서 버전 줄은 만들어졌는데 청크가 0 이다.

`document_versions` 와 `chunks` 는 따로 쓰인다. 업로드가 앞쪽을 만들고 배경 작업이
뒤쪽을 채우는데([[56_배경_작업과_작업_번호]]), 배경 작업이 실패하면 앞쪽만 남는다.
`is_searchable` 은 `index_status` 만 보므로 이런 판도 "검색 가능"으로 나온다.

## 반쯤 적재된 판을 찾는 질의

```sql
SELECT dv.id, dv.doc_id, dv."version",
       count(c.id) AS chunks, count(c.embedding) AS vectors
FROM document_versions dv
JOIN chunks c ON c.version_id = dv.id
GROUP BY dv.id, dv.doc_id, dv."version"
HAVING count(c.embedding) < count(c.id);
```

`count(컬럼)` 은 `NULL` 을 세지 않는다. 그래서 `count(c.id)` 는 청크 수,
`count(c.embedding)` 은 벡터가 든 청크 수가 되고, 둘이 다르면 임베딩이 중간에 끊긴 판이다.
`count(*)` 를 쓰면 둘 다 같은 값이 나와 아무것도 못 잡는다.

```text
없음 — 청크가 있는 버전은 전부 벡터가 차 있다
벡터 없는 청크 0개
```

지금은 깨끗하다. 질의 자체가 답이 아니라 **점검 수단**이다.

`JOIN` 이라 청크가 아예 없는 판은 이 질의에 안 잡힌다. 위의 `DOC-FI-009 v2.1` 이
그 경우다. 그건 `LEFT JOIN` 에 `HAVING count(c.id) = 0` 으로 따로 찾는다.
두 가지가 다른 고장이고 찾는 법도 다르다.

## 지울 때는 순서가 있다

```sql
BEGIN;
CREATE TEMP TABLE drop_ver AS
SELECT dv.id FROM document_versions dv JOIN chunks c ON c.version_id = dv.id
GROUP BY dv.id HAVING count(c.embedding) < count(c.id);

DELETE FROM chunks WHERE version_id IN (SELECT id FROM drop_ver);
DELETE FROM document_versions WHERE id IN (SELECT id FROM drop_ver);

SELECT count(*) FROM chunks WHERE embedding IS NULL;
COMMIT;
```

지울 id 를 **먼저 임시 테이블에 담는다.** 담지 않고 `DELETE ... WHERE id IN (SELECT ...)`
를 두 번 쓰면, 첫 번째 `DELETE` 가 청크를 지운 뒤 두 번째의 하위 질의가 다시 돌 때
그 판은 조건을 만족하지 않는다. 청크가 사라졌으니 `count` 가 둘 다 0 이 되어
`HAVING` 을 통과하지 못한다. **청크만 지워지고 판은 남는다.**

자식(`chunks`)을 먼저 지우고 부모(`document_versions`)를 나중에 지우는 것도 순서다.
반대로 하면 외래키에 걸린다.

`BEGIN` 과 `COMMIT` 사이에 확인 질의를 끼워 두면, 결과가 이상할 때 `ROLLBACK` 으로
되돌릴 수 있다.
