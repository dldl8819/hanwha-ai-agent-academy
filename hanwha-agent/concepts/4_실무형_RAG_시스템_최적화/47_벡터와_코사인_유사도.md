# 벡터와 코사인 유사도

[[33_RAG_개요]] ④ Embedding 자리다. 모델은 어제 받아 뒀고([[42_임베딩_모델_받기]]) 이번에는 **그 모델이 내놓는 숫자를 어떻게 비교하는지**를 손으로 계산해 봤다.

## 낱말 비교로는 안 되는 것

지금까지 문서를 찾는 방법은 글자가 겹치는지 보는 것이었다. 두 문구의 글자 겹침을 0~1 로 재 본다.

```python
def jaccard(x: str, y: str) -> float:
    sx, sy = (set(x.replace(' ', '')), set(y.replace(' ', '')))
    return len(sx & sy) / len(sx | sy)
```

```text
'광역시 숙박비 상한' vs '잠자리 비용 한도'    겹치는 글자 ['비', '한'] · 자카드 0.154
'광역시 숙박비 상한' vs '광역시 숙박비 상한액'  겹치는 글자 8개      · 자카드 0.889
```

뒤쪽은 글자 하나 차이라 0.889 가 나온다. 앞쪽은 뜻이 거의 같은데 0.154 다. 실제 문서에 SQL `LIKE` 를 걸어 보면 결과가 더 분명하다.

```python
def like(word: str) -> int:
    return sum((1 for b in doc.blocks if word in b.text))
```

```text
LIKE '%숙박비%' → 27건
LIKE '%잠자리%' → 0건
LIKE '%잠자리 비용%' → 0건
```

블록 233개 안에 숙박 규정이 분명히 있는데 "잠자리 비용"으로는 0건이다. 낱말 비교는 **쓴 사람과 찾는 사람이 같은 단어를 쓸 때만** 맞는다. 색인 검색으로는 여전히 유용하지만 이것만으로는 부족하다.

## 뜻을 좌표로

글자 대신 뜻을 숫자 배열로 바꾸면 겹치는 글자가 없어도 가까울 수 있다. 좌표를 두 개만 써서 흉내내 봤다.

```python
POINTS = {'광역시 숙박비 상한': [0.9, 0.2],
          '잠자리 비용 한도':   [0.86, 0.28],
          '출장 신청 절차':     [0.1, 0.95]}
```

```text
기준 : 광역시 숙박비 상한 [0.9, 0.2]
  잠자리 비용 한도  [0.86, 0.28] → 거리 0.089   ← 가깝다
  출장 신청 절차    [0.1, 0.95]  → 거리 1.097   ← 멀다
```

자카드로 0.154 였던 짝이 거리로는 0.089 로 붙는다. 다만 **이 좌표는 모델이 만든 것이 아니라 손으로 적은 것이다.** 원하는 결과가 나오도록 숫자를 정해 놓고 계산 방법을 확인한 것이라, 실제로 이렇게 나오는지는 모델을 열어 봐야 안다.

## 차원

벡터를 이루는 실수의 개수가 차원이다. 계산 방법은 개수가 늘어도 같다.

```python
v1024 = [round(math.sin(i), 4) for i in range(1024)]

def size(v: list[float]) -> float:
    return math.sqrt(sum(x * x for x in v))
```

```text
2차원      : 길이 2    앞 5개 [0.9, 0.2]
3차원      : 길이 3    앞 5개 [0.6, 0.8, 0.0]
1024차원   : 길이 1024 앞 5개 [0.0, 0.8415, 0.9093, 0.1411, -0.7568]

크기(‖v‖) : 0.9220 · 1.0000 · 22.6283
```

받아 둔 두 모델의 실제 차원은 `config.json` 에 적혀 있다.

```text
KURE-v1    hidden_size=1024 · max_position=8194 · xlm-roberta
bge-m3     hidden_size=1024 · max_position=8194 · xlm-roberta
```

**둘 다 1024 차원이고 구조도 같다.** KURE-v1 이 bge-m3 를 한국어로 미세조정한 것이라는 설명이 파일에서 확인된다. 그래서 이 두 모델을 맞바꿀 때는 Vector DB 를 다시 만들 필요가 없다 — 열이 1024개인 것은 그대로다. 차원이 다른 모델로 갈아타면 그때는 적재분을 전부 다시 만들어야 한다.

### 차원이 크면 더 좋은가

숫자가 많으면 뜻을 더 잘 담을 것 같지만 값이 붙는다. 실수 하나를 4바이트로 보고 재 봤다.

```python
BYTES_PER_NUMBER = 4

def mb(dim: int, n_chunks: int) -> float:
    return dim * n_chunks * BYTES_PER_NUMBER / 1024 / 1024
```

```text
1024차원 ×   70청크 × 4바이트 =   0.27 MB
1024차원 × 8000청크 × 4바이트 =  31.25 MB
4096차원 ×   70청크 × 4바이트 =   1.09 MB
4096차원 × 8000청크 × 4바이트 = 125.00 MB     ← 4배

4096차원은 1024차원의 4배다
```

문서 하나가 청크 70개쯤 된다고 보면 1024차원에서 0.27MB 다. 문서가 100건이 되어 8,000청크가 되면 31MB 이고, 차원을 네 배로 올리면 125MB 가 된다. 차원은 청크 수와 곱해지므로 문서가 늘면 같이 커진다.

용량만 문제가 아니다. 저장을 맡을 `pgvector`([[33_RAG_개요]] ⑤ · [[20_Docker와_PostgreSQL]])에 한계가 두 개 있다.

| | 차원 한계 |
| --- | --- |
| 벡터 열에 담기 | 16,000 |
| 빠른 검색용 색인(HNSW 등) 만들기 | 2,000 |

**담을 수 있는 차원과 색인을 만들 수 있는 차원이 다르다.** 2,000을 넘기면 저장은 되는데 색인이 안 걸려서 검색할 때마다 전부 훑는다. 데이터가 적을 때는 티가 안 나고 쌓인 뒤에 느려지므로, 차원은 적재를 시작하기 전에 정해야 한다.

## 거리가 아니라 각도

문장이 길면 벡터가 커진다. 크기가 비교에 끼어들면 곤란해진다. 코사인 유사도는 크기를 나눠서 없앤다.

```python
def dot(u, v):    return sum((a * b for a, b in zip(u, v)))   # 내적 — 같은 자리끼리 곱해 더한다
def norm(u):      return math.sqrt(dot(u, u))                 # 크기 — 제곱합의 제곱근
def cosine(u, v): return dot(u, v) / (norm(u) * norm(v))      # 내적을 두 크기로 나눈다
```

```text
u = [0.6, 0.8, 0]   v = [0, 1, 0]
  내적   : +0.8000
  크기   : 1.0000 × 1.0000
  코사인 : +0.8000
```

범위는 −1 에서 +1 이다.

```text
cos(u, u) = +1.0000    똑같다
cos(u, v) = +0.8000    닮았다
cos(u, ⊥) = +0.0000    아무 상관 없다
cos(u, w) = -1.0000    정반대
```

크기를 안 나누면 어떻게 되는지가 이유를 보여 준다. 질문 `q` 에 대해 뜻이 가깝지만 짧은 문서 `d1` 과, 뜻은 덜 가깝지만 긴 문서 `d2` 를 비교한다.

```python
q  = [1.0, 0.0]
d1 = [0.9, 0.1]     # 뜻이 가깝다. 짧아서 벡터가 작다
d2 = [3.0, 3.0]     # 뜻은 덜 가깝다. 길어서 벡터가 크다
```

```text
# 나쁜 예 — 내적만
  d1 0.900  vs  d2 3.000   → 이기는 쪽 = d2
# 좋은 예 — 코사인
  d1 0.994  vs  d2 0.707   → 이기는 쪽 = d1
```

내적만 쓰면 긴 문서가 이긴다. 그 결과가 프롬프트에 실리면 관계없는 긴 글에 토큰을 쓰게 된다. 각도만 보면 방향이 맞는 짧은 쪽이 이긴다.

## 정규화하면 내적이 곧 코사인

크기를 1 로 맞춰 두면 나눌 것이 없어진다.

```python
def unit(v: list[float]) -> list[float]:
    n = norm(v)
    return [x / n for x in v]
```

```text
‖û‖ = 1.0   ‖v̂‖ = 1.0
dot(û, v̂) = 0.960000   cosine(u, v) = 0.960000   차이 0.0
차이가 1e-12 보다 작은가 : True
```

같은 값이다. 그래서 적재할 때 정규화해 두면 검색할 때마다 크기를 다시 계산하지 않는다. 임베딩 라이브러리는 대개 정규화된 벡터를 바로 돌려주는 옵션을 갖고 있고, KURE-v1 은 `config_sentence_transformers.json` 에 기본 비교 방식을 `cosine` 으로 적어 두었다.

## 짚어둘 것

### 차원이 달라도 오류가 안 난다

`dot` 과 `distance` 는 `zip` 을 쓴다. `zip` 은 짧은 쪽에서 멈추므로 **차원이 다른 벡터를 넣어도 예외가 나지 않는다.** 원소가 1인 벡터 둘로 재 보면 이렇다.

```text
1024차원 vs 768차원 코사인 : 0.8660
```

같은 방향이니 1.0 이 나와야 하는데 0.8660 이다. 앞 768개만 곱한 뒤 크기는 각자 전체로 나눈 값이다. 계산이 멈추지 않으니 틀린 순위가 그대로 검색 결과가 된다. [[39_문서_파싱]]에서 본 "에러가 나지 않는 실패"와 같은 종류다.

노트북의 두 함수에 길이 검사를 넣어 두었다.

```python
if len(u) != len(v):
    raise ValueError(f'차원이 다르다: {len(u)} vs {len(v)}')
```

값이 나와 버리는 쪽보다 멈추는 쪽이 낫다. 모델을 바꿀 때 적재분을 같이 바꿔야 하는 이유가 여기에도 있다.
