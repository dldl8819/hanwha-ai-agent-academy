# 골든셋 점검기

[[68_골든셋_만드는_순서]]의 7단계는 만들 때 한 번 지키는 것이다. 문제는 그 뒤다.
문서가 개정되면 골든셋이 무너진다.

번호가 바뀌고, 판이 올라가고, 조항이 옮겨 간다. 그래도 측정은 그대로 돌아가고
숫자만 내려간다. **검색이 나빠진 것처럼 보인다.**

`evals/check_golden.py` 를 만들었다. 측정 전에 먼저 돌리는 자리다.

## 임베딩 모델을 부르지 않는다

여섯 항목 전부 DB 조회와 문자열 비교다. 모델도, 벡터도, API 호출도 없다.

| # | 확인 항목 | 걸리면 |
| --- | --- | --- |
| 1 | `expect_doc` 문서가 DB 에 있는가 | 문서 번호가 틀렸거나 문서가 폐기됐다 |
| 2 | `expect_version` 판이 있는가 | 개정으로 버전 번호가 바뀌었다 |
| 3 | 그 판이 현행인가 | 이전 버전으로 정답을 적어 뒀다 |
| 4 | 그 판에 청크가 있는가 | 적재되지 않았다 |
| 5 | `expect_kind` 종류의 청크가 있는가 | 표가 조항 단위로 잘렸다 |
| 6 | `expect_keywords` 가 한 청크에 모두 있는가 | 키워드가 사라졌다 |

모델을 안 쓰는 것이 핵심이다. 30문항 측정은 질문마다 임베딩을 한 번씩 부르고
1분 넘게 걸린다. 이 검사는 1초 안에 끝난다. **싸면 자주 돌릴 수 있고, 자주 돌리면
문서가 바뀐 날 바로 걸린다.**

## 돌려 본 결과

```text
골든셋 30문항 검사 — 오류 3 · 경고 0 (문항 3개에서)

  [오류] G07 (2) 버전 없음 — 개정으로 번호가 바뀌었다: v1.4 (DB: v2.1)
  [오류] G23 (1) 문서 없음 — 문서 번호가 틀렸거나 문서가 폐기됐다: DOC-PU-103
  [오류] G24 (1) 문서 없음 — 문서 번호가 틀렸거나 문서가 폐기됐다: DOC-SE-102

  항목별
    1 문서 없음              2건
    2 버전 없음              1건
```

[[65_측정값_뜯어보기]]에서 손으로 하루 걸려 찾은 셋을 그대로 잡았다.
**측정을 돌리기 전에 알 수 있던 것이었다.**

G07 의 메시지가 특히 쓸모 있다. `v1.4` 를 기대하는데 DB 에 `v2.1` 이 있다고 함께
적어 준다. 「없다」만 알려 주면 번호를 틀린 것인지 판이 올라간 것인지 모른다.

## 심각도를 둘로 나눈다

```python
오류, 경고 = "오류", "경고"
```

- **오류** — 그대로 측정하면 채점할 수 없는 문항이 된다. 고치거나 빼야 한다.
- **경고** — 채점은 되지만 기대값이 시스템 상태와 어긋나 있다.

③현행 여부가 경고다. 현행이 아닌 판을 가리켜도 그 판에 청크가 있으면 채점은 돌아간다.
답이 옛 금액이라는 것이 문제인데, 그건 사람이 보고 판단할 일이다.

```python
return 1 if 오류수 else 0
```

오류가 있으면 0 이 아닌 값으로 끝낸다. 측정을 자동으로 돌리는 자리에서 이 검사를
앞에 두면 **오류가 있는 골든셋으로는 측정이 시작되지 않는다.**

## 과거를 묻는 문항은 ③이 뒤집힌다

```python
과거를_묻는가 = bool(item.get("needs_past_version"))
if 과거를_묻는가 and dv.status == "현행":
    문제.append((경고, 3, f"과거 판을 묻는 문항인데 {기대판} 이 현행이다"))
elif not 과거를_묻는가 and dv.status != "현행":
    문제.append((경고, 3, f"현행이 아님({dv.status}) — 이전 버전으로 정답을 적어 뒀다"))
```

「개정 전후 비교」 문항은 **일부러** 만료된 판을 가리킨다. 그걸 오류로 세면 4문항이
늘 걸린다. 오히려 그 판이 현행이 되어 있으면 문항의 의도가 깨진 것이다 —
새 개정이 안 들어왔다는 뜻이다.

[[64_골든셋과_채점기]]에서 `needs_past_version` 을 "문항이 무엇을 의도했는지 적어 두는
자리로만 쓰인다"고 했는데, 여기서 처음 읽는 코드가 생겼다.

## 걸리면 멈추는 자리를 고른다

```python
if document is None:
    문제.append((오류, 1, ...))
    return 문제
```

①에서 문서가 없으면 ②~⑥을 묻지 않고 돌아간다. 없는 문서의 판을 찾고 청크를 세면
같은 원인으로 다섯 줄이 나온다. ④청크 0 도 같다 — 청크가 없으면 ⑤와 ⑥은 자동으로 걸린다.

한 원인에 한 줄만 나오게 하는 것이 목적이다. 사유가 다섯 줄이면 고칠 곳도 다섯 군데처럼
보인다([[65_측정값_뜯어보기]]에서 같은 사유 네 줄에 원인이 네 가지였던 것과 반대 방향의 문제다).

## ⑥은 "한 청크에" 가 조건이다

```python
한_청크에_다 = any(all(k in c.text for k in 키워드) for c in 청크)
```

키워드가 각각 어딘가 있는 것으로는 부족하다. `judge()` 가 청크 하나를 두고 키워드
전부를 보기 때문이다([[64_골든셋과_채점기]]). `30,000` 은 제11조에 있고 `70,000` 은
표2 에만 있으면 그 문항은 아무리 검색이 잘돼도 못 맞힌다.

그래서 메시지를 둘로 갈랐다.

- 어느 청크에도 없다 → `키워드 사라짐` (오류). 원문이 바뀌었다.
- 각각은 있는데 한 청크에 모이지 않는다 → `키워드 흩어짐` (경고). 청킹이 갈라놨다.

## 이 검사로 잡을 수 없는 것

지금 골든셋에서 ⑤가 걸리지 않는다. G16 이 `expect_kind: 표` 인데 통과한다.
`DOC-HR-014 v2.0` 에 `표` 종류 청크가 7개 있기 때문이다.

그리고 통과가 맞다. [[65_측정값_뜯어보기]]에서 확인한 대로 직급별 일비 표는 `표2` 로
온전히 들어가 있다. G16 이 틀린 이유는 그 표가 5위로 밀린 것이고, **순위는 모델을
불러야 알 수 있다.**

여섯 항목은 「기대값이 지금 데이터와 맞는가」만 본다. 「검색이 그걸 찾아오는가」는
못 본다. 둘은 다른 검사이고 둘 다 필요하다. 싼 쪽을 먼저 돌려 걸러 내고,
남은 것을 비싼 쪽으로 넘기는 순서다.
