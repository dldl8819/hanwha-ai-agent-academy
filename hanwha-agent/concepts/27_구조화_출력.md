# 구조화 출력

[[22_AI_Native_애플리케이션]]의 원칙 중 하나가 **"출력은 스키마로 강제하고 파싱·검증한다. 자연어를 그대로 다음 단계로 넘기지 않는다"**였다. 화면에 답변과 근거 목록, 근거 충분 여부를 따로 보여주려면 모델 응답이 문장이 아니라 **구조**여야 한다.

## 요청과 응답 모델 — `backend/app/schemas/chat.py`

| 모델 | 방향 | 무엇 |
| --- | --- | --- |
| `ChatRequest` | 들어오는 것 | 사용자가 보낸 질문 |
| `AnswerSource` | 나가는 데이터의 부품 | 인용한 근거 하나 |
| `AnswerOut` | 나가는 것 | 답변, 근거 목록, 근거가 충분했는가 |

```python
from typing import Literal
from pydantic import BaseModel, Field

DOC_ID = Literal["DOC-HR-014", "DOC-PU-007", "DOC-SE-003"]   # 임시

class ChatRequest(BaseModel):
    question: str = Field(min_length=2, max_length=2000,
                          description="사용자 질문. 두 글자 이상 2000자 이하")

class AnswerSource(BaseModel):
    doc_id: DOC_ID = Field(description="인용한 문서 번호. 등록된 세 건 중 하나")
    title: str = Field(description="문서 제목")
    version: str = Field(description="문서 버전. 예: v2.0")
    locator: str = Field(description="문서 안 위치. 예: 제12조 · p.6")

class AnswerOut(BaseModel):
    answer: str = Field(description="한국어 답변 본문")
    sources: list[AnswerSource] = Field(description="답변이 인용한 근거 목록")
    enough_evidence: bool = Field(description="근거가 충분했는가. 부족하면 False")
```

- **`doc_id`를 `Literal`로 막는다.** 모델이 목록에 없는 문서 번호를 지어내면 검증 단계에서 걸린다. 프롬프트로 "지어내지 마"라고 부탁하는 것에 더해, 코드가 한 번 더 확인하는 구조다
- `enough_evidence`를 별도 필드로 둔다. 근거가 부족한 답을 화면에서 다르게 보여줄 수 있다
- `description`은 주석이 아니라 `/docs`(OpenAPI) 화면에 그대로 보이는 설명이다. 오타가 나면 문서에 그대로 노출된다
- `max_length=2000`은 `.env`의 `MAX_INPUT_CHARS`와 **따로 관리되는 값**이다. 한쪽만 바꾸면 어긋난다

### 실습 중 만난 이슈: `Literal` 한 글자 오타

```python
DOC_ID = Literal["DOC-HR-014", "DOC-PU-007", "DOC_SE-003"]   # 하이픈 대신 밑줄
```

```text
수정 전 : 정상 번호 DOC-SE-003 인용이 검증 실패 -> literal_error
수정 후 : DOC-SE-003 통과
```

프롬프트에는 `DOC-SE-003`이라고 적어뒀으니 모델은 정확한 번호를 보낸다. 그런데 스키마 쪽이 틀려서 **모델이 맞게 답해도 검증이 실패한다.** `Literal`은 한 글자만 달라도 다른 값으로 보기 때문에, 막아야 할 오답이 아니라 정답을 막게 된다. 같은 값을 프롬프트와 스키마 두 곳에 적고 있어서 생긴 문제라, 나중에 문서 목록을 DB에서 가져오게 되면 한 곳에서 관리하게 된다.

## 프롬프트에 출력 형식을 못 박는다

```markdown
## 출력 형식

아래 세 필드를 가진 JSON 하나만 보냅니다.

| 필드 | 형 | 뜻 |
|---|---|---|
| `answer` | 문자열 | 한국어 답변 본문. 결론을 먼저 씁니다 |
| `sources` | 목록 | 인용한 근거. 항목마다 `doc_id` · `title` · `version` · `locator` |
| `enough_evidence` | 참/거짓 | 근거가 충분했으면 true, 부족하면 false |

- `doc_id` 는 `DOC-HR-014` · `DOC-PU-007` · `DOC-SE-003` 중 하나만 씁니다.
- 근거가 없으면 `sources` 를 빈 목록으로 두고 `enough_evidence` 를 false 로 둡니다.
- 설명 문장이나 코드펜스(```) 없이 **JSON 만** 보냅니다.
```

필드 이름과 형이 `AnswerOut`과 **정확히 같아야** 한다. 프롬프트가 요구하는 모양과 스키마가 검증하는 모양이 하나다.

## "JSON 만 보내라"고 해도 코드펜스로 온다

프롬프트에 분명히 적어도, 모델은 이렇게 감싸서 보낼 때가 있다.

````text
```json
{"answer":"1박 70,000원 이내", "sources":[...], "enough_evidence":true}
```
````

이걸 그대로 검증에 넣으면 첫 글자에서 멈춘다.

```text
① 그대로 넣으면 : Invalid JSON: expected value at line 1 column 1
```

첫 글자가 `` ` ``(백틱)이라 JSON 파서가 시작부터 실패한 것이다. 모델에게 부탁만 하는 것으로는 막을 수 없으니, **받는 쪽에서 벗겨낸다.**

### `_extract_json`

```python
def _extract_json(text: str) -> dict:
    # 1) 코드펜스가 있으면 안쪽 { ... } 만 꺼낸다
    fenced = re.search(r"```(?:json)?\s*(\{.*?\})\s*```", text, re.S)
    raw = fenced.group(1) if fenced else text

    # 2) 펜스가 없으면 앞뒤 설명 문장을 버리고 첫 { 부터 마지막 } 까지만 남긴다
    start, end = raw.find("{"), raw.rfind("}")
    if start == -1 or end == -1:
        return {}
    try:
        return json.loads(raw[start : end + 1])
    except json.JSONDecodeError:
        log.warning("응답 JSON 파싱 실패")
        return {}
```

정규식 조각별로 보면 이렇다.

| 조각 | 뜻 |
| --- | --- |
| ```` ``` ```` | 펜스 시작 |
| `(?:json)?` | `json` 표기는 있어도 없어도 된다. `(?:...)`는 캡처하지 않는 묶음 |
| `\s*` | 공백·줄바꿈 |
| `(\{.*?\})` | `{`부터 `}`까지 — **이 괄호만 캡처**해서 `group(1)`으로 꺼낸다 |
| `re.S` | `.`이 줄바꿈까지 포함하게 한다. JSON 이 여러 줄이어도 잡힌다 |

`.*?`는 최소한으로 잡는 방식이지만, 뒤에 `\s*```` ``` ````가 반드시 와야 해서 안쪽에 `{...}`가 중첩돼 있어도 **펜스 바로 앞의 마지막 `}`까지** 늘어난다. 근거 목록(`sources: [{...}]`)이 들어간 응답도 온전히 꺼내진다.

펜스가 없는 경우를 위해 `find("{")`·`rfind("}")`로 한 번 더 자른다. "다음은 답변입니다: {...} 참고하세요" 같은 응답에서도 JSON 부분만 남는다.

실행 결과다.

```text
① 그대로 넣으면 : Invalid JSON: expected value at line 1 column 1
② 벗기고 검증   : answer='1박 70,000원 이내' · 근거 1건 · 충분함 True
③ JSON 이 아니면 : {}
```

### 실패하면 빈 dict — 처리는 호출하는 쪽에서

JSON 을 못 꺼내면 예외 대신 `{}`를 돌려준다. 그대로 검증하면 이렇게 된다.

```text
④ 빈 dict 를 검증하면 : 3 개 필드 누락
```

`_extract_json`이 조용히 넘어가는 대신 **`AnswerOut` 검증에서 확실히 실패**하는 구조다. 그러니 이 둘을 쓰는 서비스 쪽에서 `ValidationError`를 잡아 "답변 형식이 올바르지 않습니다"처럼 처리하는 자리가 필요하다. 파싱과 검증을 두 단계로 나눠 두면, 실패했을 때 **형식이 깨진 것인지(파싱)** **내용이 규칙에 안 맞는 것인지(검증)** 구분할 수 있다.
