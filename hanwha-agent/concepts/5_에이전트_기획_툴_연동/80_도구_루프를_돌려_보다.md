# 도구 루프를 돌려 보다

수업 노트북은 두 질문(부산 숙박비, 법인카드 한도)으로 끝났다. 모델이 무엇을 정하는지 보려고
질문을 여섯으로 늘리고, 어댑터를 감싸 턴마다 기록했다. 실제 호출이다(claude-haiku-4-5,
`max_tokens=400`, 크로스 인코더).

## 결과 한눈에

| 질문 | 턴 | 모델이 고른 검색어 | 끝난 이유 | 원가 |
| --- | --- | --- | --- | --- |
| 부산 출장 숙박비 얼마까지 되나요? | 2 | `부산 출장 숙박비 한도` | end_turn | ₩7.1 |
| 법인카드 한도가 얼마인가요? | 3 | `법인카드 한도` → `법인카드 사용 지침 한도 금액` | end_turn | ₩13.4 |
| 안녕하세요 | 1 | (부르지 않음) | end_turn | ₩3.1 |
| 해외 출장 시 비즈니스석 탑승 기준이 어떻게 되나요? | 3 | 세 번 바꿔 검색 | **상한** | ₩13.0 |
| 개정 전 국내출장 숙박비는 얼마였나요? | 2 | `국내출장 숙박비 개정 전` | end_turn | ₩7.7 |
| 출장 일비와 재택근무 장비 지원 기준을 같이 알려주세요 | 3 | 한 턴에 **둘** + 하나 더 | **max_tokens** | ₩17.4 |

## 1. 모델이 검색어를 다시 쓴다

부산 질문에서 모델은 질문을 그대로 넣지 않고 `부산 출장 숙박비 한도` 로 줄였다.
[[72_질의_재작성과_Multi_Query]]에서 코드가 하던 일을 모델이 도구 인자로 하는 셈이다.
도구 안에서도 Multi-Query 가 다시 돈다. 재작성이 두 겹이 됐다.

검색어가 바뀌면 결과도 바뀐다. 같은 retriever 에 두 문장을 넣어 봤다.

```text
개정 전 국내출장 숙박비는 얼마였나요?   (사용자 질문)
   passed True  0.60   v2.0 제11조(일비) · v1.1 제8조(일비) · v2.0 제14조(숙박비)
국내출장 숙박비 개정 전                (모델이 고른 검색어)
   passed False 0.59   v2.0 제14조(숙박비) · v2.0 표1 · v2.0 제11조(일비)
```

사용자 질문으로 찾았으면 v1.1 이 하나 걸리고 임계값도 넘었다. 모델이 줄인 검색어로는
v1.1 이 빠지고 0.01 차이로 미달이다. [[77_점수를_재면서_쓰지_않는다]]의 「0.60 의 여유가
0.01」이 여기서 그대로 드러난다 — 검색어 몇 글자에 판정이 뒤집힌다.

## 2. 인사에는 도구를 부르지 않는다

「안녕하세요」에 도구 호출 없이 바로 답했다. `agent_system.md` 의 「인사말이면 부르지 않고
그대로 답합니다」가 지켜졌다. `ask()` 였다면 인사에도 검색을 돌리고 임계값 미달로 폴백했을
것이다.

다만 입력이 1,410 토큰이다. 시스템 프롬프트와 도구 정의가 매 호출에 실린다.
인사 한 마디에도 이 값은 고정이다. 답에 이모지(👋)가 붙었는데 프롬프트에 막는 줄이 없다.

## 3. 턴마다 입력이 쌓인다

```text
법인카드 한도
  턴1  in 1,420   out  84
  턴2  in 2,516   out 155
  턴3  in 3,606   out 171
```

한 턴에 약 1,100 토큰씩 는다. tool_result 하나가 그만큼이다. 앞 턴의 대화를 전부 다시
보내기 때문에 **세 번째 호출은 첫 번째 호출의 2.5 배를 낸다.** 턴을 늘리면 원가가 선형이
아니라 누적으로 는다.

tool_result 에는 `sources` 말고도 `steps`, `threshold`, `best_score` 가 들어간다. `steps` 는
화면용 진행 표시다. 모델이 답을 쓰는 데 필요 없는 글자가 매 턴 다시 실린다.

## 4. 한 턴에 도구를 둘 부른다

```text
출장 일비와 재택근무 장비 지원 기준을 같이 알려주세요
  턴1  calls=[search_documents(출장 일비), search_documents(재택근무 장비 지원)]
```

질문이 둘을 묻자 모델이 한 응답에 `tool_use` 블록을 둘 넣었다. 루프는 `for c in calls`
로 둘 다 실행하고 tool_result 둘을 한 메시지에 담는다. `tool_use_id` 로 짝을 맞춘다
([[79_도구_정의와_tool_result]]). 여기까지는 맞게 돈다. 출처가 어떻게 되는지는
[[81_출처와_판정이_답과_어긋난다]]에서 본다.

## 5. 잘린 답이 끝난 답이 된다

같은 질문 3턴째가 `stop_reason=max_tokens`, `out=400` 이었다. 답이 「30일을 초과」에서
끊겼다. 루프는 `tool_calls` 가 비었으니 끝났다고 보고 이 문장을 그대로 내보냈다.

[[78_에이전트_루프와_멈추는_조건]]에서 `stop_reason` 을 안 본다고 적은 결과다.
`max_tokens=400` 은 [[27_구조화_출력]] 때 JSON 한 덩어리에 맞춘 값이다. 문장으로 두 주제를
설명하기에는 짧다. 값을 올리거나, `max_tokens` 이면 잘렸다고 알리거나 둘 중 하나가 필요하다.

## 6. 상한에 닿으면 마지막 결과는 아무도 읽지 않는다

```text
해외 출장 시 비즈니스석 탑승 기준이 어떻게 되나요?
  턴1  해외 출장 비즈니스석 탑승 기준     → "국내 출장 규정만 나왔습니다"
  턴2  해외 출장 항공료 비즈니스 클래스   → "다시 검색해보겠습니다"
  턴3  해외 출장 규정 여비               → (상한)
  답 : (도구 호출 상한에 닿아 답을 마치지 못했습니다)
```

규정에 없는 질문이다. 모델은 「없다」고 말하지 않고 검색어를 바꿔 계속 찾았다.
`agent_system.md` 의 「부족하면 검색어를 바꿔 다시 부를 수 있습니다」가 이 방향으로 작용했다.

루프 구조도 봐야 한다. 3턴째에 모델이 도구를 요청하고, 루프는 그 도구를 **실행하고**
tool_result 를 붙인 뒤 `for` 가 끝난다. 모델을 다시 부르지 않으니 세 번째 검색 결과는
아무도 읽지 않는다. 검색 한 번(리랭커 포함 수 초)을 버리는 셈이다. 상한 턴에서는 도구를
실행하지 말고 「여기까지의 근거로 답하라」고 한 번 더 부르는 쪽이 맞다.

[[75_리랭킹_두_가지]]에서 같은 질문에 크로스 인코더가 0.0004 를 줬다. 근거가 없다는 신호를
가장 잘 내는 점수가 도구 결과에는 들어 있지 않다(`SOURCE_KEYS` 에 `rerank_score` 가 없다).
모델은 코사인 점수만 보고 「더 찾아보면 있을지도」를 반복했다.

backend/app/agent/prompts/agent_system.md
