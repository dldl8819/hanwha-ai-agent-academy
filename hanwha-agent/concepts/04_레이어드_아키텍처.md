# 레이어드 아키텍처

## main.py 하나에 다 몰아넣으면 안 되는 이유

로그인 확인, 권한 확인, 업무 규칙 처리, DB 조회/저장, 외부 API(LLM) 호출, 로그 기록, 응답 생성까지 한 요청 안에서 처리할 일이 많다. 이걸 `main.py` 한 파일에 순서대로 다 적으면, 코드가 길어질수록 어디를 고쳐야 할지 찾기 어렵고, 같은 로직(예: 권한 확인)을 다른 요청에서 재사용하기도 힘들다. 그래서 역할별로 파일/폴더를 나눈다.

## MVC 패턴

| 요소 | 역할 | hanwha-agent에서의 위치 |
| --- | --- | --- |
| Model | 데이터와 비즈니스 로직 | `backend/`, `models/`, `services/`, `repositories/` |
| View | 사용자에게 보여주는 화면 | `frontend/` |
| Controller | 요청을 받아 Model과 View를 연결 | `api/` |

## Layered Architecture (MVC를 더 세분화)

hanwha-agent의 폴더 구조는 MVC의 Model 부분을 역할별로 더 잘게 쪼갠 계층형(Layered) 구조다. 요청이 위에서 아래로 흐른다.

```text
frontend        Streamlit 화면
    | HTTP 요청
API             FastAPI Router — 요청을 받고 분배
    |
Schema          Pydantic — 요청/응답 데이터 형태 검증
    |
Service         비즈니스 로직 처리 (AI 기능도 여기)
    |
Repository      DB 접근
    |
Model           DB 테이블 정의
    |
PostgreSQL
```

각 계층은 자기 바로 아래 계층만 호출한다 (API가 DB를 직접 건드리지 않고 Service를 거치는 식). 계층을 나눠두면 예를 들어 DB를 SQLite에서 PostgreSQL로 바꿀 때 Repository 계층만 손보면 되고, 나머지 계층은 그대로 둘 수 있다.
