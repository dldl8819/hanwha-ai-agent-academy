# 리포지토리(Repository) 패턴

[[04_레이어드_아키텍처]]에서 나눈 계층 중 DB 접근을 전담하는 계층을 구체화한 것이다.

## 개념

쿼리(select, insert, delete 등 DB 처리 로직)만 모아두는 층이다. "DB에 어떻게 접근할지"를 이 계층에만 몰아두고, 나머지 계층은 DB의 세부 구현을 몰라도 되게 만든다.

## 클라이언트 요청 처리 흐름

```text
HTTP 문서 요청
    |
라우터 : documents.py           — 요청을 받아 분배
    |
서비스 : document_service.py    — 비즈니스 로직 처리
    |
리포지토리 : document_repo.py   — DB 처리 로직 (select 등)
    |
모델을 통해 DB 접속 : document.py
    |
DB
```

## 왜 필요한가 — 리포지토리 없이 라우터에서 바로 DB에 접속하면

```python
# 잘못된 예시 — 라우터에서 직접 SQL을 조립해서 실행
@router.get("/list")
def get_list(dept_id=None, security_level=None, status=None, q=None):
    sql = "SELECT * FROM documents WHERE 1=1"
    if dept_id:
        sql += f" AND dept_id = '{dept_id}'"
    if security_level:
        sql += f" AND security_level = '{security_level}'"
    # ...
    session.execute(sql)
    # DB 접속해서 쿼리문 실행 → 데이터 리턴
```

이 방식의 문제:

- **보안에 취약하다.** 쿼리 파라미터를 f-string으로 그대로 SQL 문자열에 꽂아 넣고 있다 — 전형적인 SQL 인젝션 패턴이다. `dept_id` 자리에 `' OR '1'='1`같은 값이 들어오면 조건 자체가 무력화된다. (SQLAlchemy의 `select().where(...)`나 `?`/`:name` 바인드 파라미터를 쓰면 값이 문자열로 안전하게 이스케이프된다.)
- **재사용·테스트·이관이 어렵다.** DB 접근 로직이 라우터 함수 안에 박혀 있으면, 같은 조회를 다른 곳(배치 작업, 다른 라우터)에서 또 써야 할 때 코드를 복붙하게 된다. 테스트할 때도 라우터 전체(HTTP 계층까지)를 띄워야 DB 로직을 검증할 수 있다. DB를 SQLite에서 PostgreSQL로 옮길 때도 이런 코드가 여기저기 흩어져 있으면 고칠 곳을 다 찾아야 한다.

리포지토리로 분리해두면, 라우터/서비스는 "무슨 조건으로 조회할지"만 알면 되고 "SQL을 어떻게 짤지"는 리포지토리 함수 하나만 보면 된다.

### 연습용 DB 준비

```python
from datetime import date
from app.db.session import get_sessionmaker, get_engine
from app.models import Department, Document, DocumentVersion
from app.db.init_db import init_db

연습DB = SANDBOX / "repo_practice.db"
연습DB.unlink(missing_ok=True)  # 파일이 없어도 오류 없이 지나감

연습엔진 = get_engine(f"sqlite:///{연습DB}")
init_db(연습엔진)
연습세션 = get_sessionmaker(연습엔진)

with 연습세션() as s:
    s.add_all([Department(id="HRGA", name="인사총무"), ...])
    s.flush()  # 다음 배치가 dept_id로 참조하므로 먼저 DB에 내보낸다
    s.add_all([Document(id="DOC-HR-014", dept_id="HRGA", ...), ...])
    s.flush()  # 다음 배치가 doc_id로 참조하므로 먼저 DB에 내보낸다
    s.add_all([DocumentVersion(doc_id="DOC-HR-014", version="v2.0", ...), ...])
    s.commit()  # commit()이 알아서 flush까지 하고 확정한다 — 마지막 배치는 따로 flush 불필요
```

`get_engine()`/`get_sessionmaker()`는 [[11_SQLAlchemy]]에서 만든 URL별 캐시 구조를 그대로 활용한 것이다. 연습용 DB URL(`repo_practice.db`)로 새 엔진을 만들면 실제 서비스용 `app.db`와 완전히 분리된 채로 실습할 수 있다.

`Department`→`Document`→`DocumentVersion` 순서로 `flush()`를 끼워 넣은 이유는, FK 컬럼을 `dept_id="HRGA"`처럼 문자열 값으로 채우고 있어서(관계 객체로 연결한 게 아니라) SQLAlchemy가 삽입 순서를 자동으로 못 맞추기 때문이다 — 부모 행을 먼저 실제로 DB에 내보내둬야 자식 행의 외래키 제약을 통과한다.

### `select()`로 조회

```python
from sqlalchemy import select

stmt = select(Document).where(Document.dept_id == "HRGA")

print(stmt)                              # 만들어진 SQL
print("바인딩된 값 :", stmt.compile().params)  # {"dept_id_1": "HRGA"} — 값이 SQL 문자열에 직접 안 들어간다
```

`stmt.compile().params`로 실제 바인딩되는 값을 따로 확인할 수 있다. 조건 값이 SQL 텍스트 안에 그대로 섞이지 않고 파라미터로 분리된다는 게, 위에서 본 "잘못된 예시"(f-string으로 SQL 조립)와의 핵심 차이다.

### Select 결과 꺼내는 방법 비교

| 방법 | 반환 | 결과 없을 때 | 2건 이상일 때 | 쓰는 상황 |
| --- | --- | --- | --- | --- |
| `session.scalars(stmt).all()` | 객체 리스트 | 빈 리스트 `[]` | 전부 반환 | 여러 건 조회 |
| `session.execute(stmt).scalar_one_or_none()` | 객체 1개 또는 `None` | `None` | `Error` (`MultipleResultsFound`) | 조건상 1건 또는 0건만 나와야 확신할 때 |
| `session.get(모델, 기본키)` | 객체 1개 또는 `None` | `None` | (기본키라 애초에 불가) | 기본키로 1건 조회 |

`scalar_one_or_none()`은 "결과가 정확히 1건이거나 0건이어야 한다"는 걸 전제로 하는 메서드라서, 실제로 2건 이상 나오면(예: unique 제약이 없는 조건으로 조회) 조용히 아무거나 하나 반환하는 게 아니라 명시적으로 에러를 낸다 — 여러 건이 나올 수 있는 조회에는 쓰면 안 되고, 그럴 땐 `scalars(stmt).all()`을 써야 한다.

## 실전 적용: `backend/app/repositories/document_repo.py`

```python
from __future__ import annotations
from sqlalchemy import Row, desc, or_, select
from sqlalchemy.orm import Session, joinedload
from app.models.document import Document, DocumentVersion

def list_documents(
    session: Session,
    *,
    dept_id: str | None = None,
    security_level: str | None = None,
    status: str | None = None,
    q: str | None = None,   # 문서명·문서번호 부분 검색
    limit: int = 50,
) -> list[Row]:
    stmt = select(DocumentVersion, Document).join(
        Document, DocumentVersion.doc_id == Document.id
    )
    if dept_id:
        stmt = stmt.where(Document.dept_id == dept_id)
    if security_level:
        stmt = stmt.where(Document.security_level == security_level)
    if status:
        stmt = stmt.where(DocumentVersion.status == status)
    if q:
        stmt = stmt.where(
            or_(Document.title.ilike(f"%{q}%"), Document.id.ilike(f"%{q}%"))
        )
    # 즉시 로딩(eager loading): Document.dept를 한 번의 JOIN 쿼리로 같이 가져온다
    stmt = stmt.options(joinedload(Document.dept))
    stmt = stmt.order_by(Document.id, desc(DocumentVersion.version)).limit(limit)
    return list(session.execute(stmt).all())

def get_document(session: Session, doc_id: str) -> Document | None:
    return session.get(Document, doc_id)

def add_version(session: Session, doc: Document, **fields) -> DocumentVersion:
    version = DocumentVersion(doc_id=doc.id, **fields)
    session.add(version)
    session.flush()
    return version
```

- `.join(Document, DocumentVersion.doc_id == Document.id)`처럼 대상 모델과 ON 조건을 직접 주는 조인 방식이다([[11_SQLAlchemy]]의 JOIN 절 참고). `select(DocumentVersion, Document)`로 두 모델을 같이 뽑았기 때문에, 결과의 각 행은 `(DocumentVersion, Document)` 튜플(`Row`)이 된다.
- `joinedload(Document.dept)`는 "즉시 로딩(eager loading)"이다. 붙이지 않으면 나중에 `document.dept`에 접근하는 순간(지연 로딩) 그때마다 추가 쿼리가 한 번씩 더 나간다 — 결과가 여러 건이면 N+1 쿼리 문제로 이어질 수 있다. `joinedload`를 붙이면 처음 조회할 때 JOIN으로 한 번에 다 가져온다.
- 조건 매개변수는 전부 `if dept_id:` 식으로 값이 있을 때만 `where()`를 이어붙인다. 이게 바로 위의 "잘못된 예시"가 f-string으로 하려던 것과 같은 목적이지만, SQL 인젝션 위험 없이 안전하게 구현한 버전이다.
- `add_version`은 `flush()`까지만 하고 `commit()`은 하지 않는다 — 커밋 시점은 리포지토리가 아니라 이걸 호출하는 서비스/`session_scope()` 쪽 책임으로 남겨둔 것이다. 리포지토리는 "쿼리"만 맡고, 트랜잭션을 언제 확정할지는 그 바깥(서비스 계층)이 결정한다.

**실습 중 겪은 이슈**: `stmt = select(...)` 줄만 탭(Tab)으로 들여쓰기가 되어 있고 나머지는 스페이스라서, `import`하는 순간 `IndentationError: unindent does not match any outer indentation level`가 났다. 에디터에서는 탭과 스페이스가 똑같이 보여도 파이썬은 서로 다른 들여쓰기로 구분하기 때문에, 같은 블록 안에서 섞어 쓰면 이런 에러가 난다. 탭을 스페이스로 바꿔서 해결했다.

## N+1 문제와 즉시 로딩(Eager Loading)

문서 목록을 조회한 뒤 각 문서의 부서 이름을 `document.dept.name`으로 화면에 보여준다고 하면, 관계(`relationship`)는 기본값이 **지연 로딩(lazy loading)**이라서 `document.dept`에 접근하는 그 순간마다 추가 쿼리가 하나씩 더 나간다. 문서가 10건이면 목록 조회 1번 + 부서 조회 10번 = 총 11번(N+1번) 쿼리가 나가는 식이다.

해결책은 처음 조회할 때 필요한 관계를 미리 같이 가져오는 **즉시 로딩(eager loading)**이다.

| 옵션 | 관계 방향 | 방식 |
| --- | --- | --- |
| `selectinload(Document.versions)` | 1:N (문서 하나에 버전 여러 개) | 연관된 행들을 `IN` 절로 따로 한 번 더 모아서 가져온다 |
| `joinedload(Document.dept)` | N:1 (여러 문서가 부서 하나에 속함) | 같은 `SELECT`에 `JOIN`으로 붙여서 한 번에 가져온다 |

```python
from sqlalchemy.orm import selectinload, joinedload

문서들 = session.scalars(
    select(Document).options(
        selectinload(Document.versions),
        joinedload(Document.dept),
    )
).unique().all()

for doc in 문서들:
    부서명 = doc.dept.name  # 추가 쿼리 없이 바로 접근됨
```

`selectinload`는 1:N처럼 결과 행이 늘어날 수 있는 관계에 쓰고, `joinedload`는 N:1처럼 결과 행이 늘어나지 않는(또는 `.unique()`로 중복만 제거하면 되는) 관계에 주로 쓴다. `document_repo.list_documents()`에서 `joinedload(Document.dept)`만 쓴 것도 이 조회에서 필요한 관계가 N:1(`Document.dept`)뿐이었기 때문이다.

## 시드(seed) 데이터

### `app/db/seed_data.py` — 테스트용 원본 데이터

`DEPARTMENTS`, `USERS`, `DOCUMENTS`(각 문서 안에 `versions` 리스트 포함) 세 개의 파이썬 리스트로 시드 데이터를 정의해둔다. 실제 DB 스키마와 무관하게 순수 딕셔너리로 적어두고, 적재할 때 모델 클래스에 그대로 풀어 넣는다(`Department(**row)`).

### `app/db/seed.py` — 적재 로직 (멱등성 보장)

```python
from sqlalchemy import func, select
from app.db.seed_data import DEPARTMENTS, DOCUMENTS, USERS
from app.db.session import session_scope
from app.models import Department, Document, DocumentVersion, User

def count_rows(session) -> dict[str, int]:
    return {
        "departments": session.scalar(select(func.count()).select_from(Department)) or 0,
        "users": session.scalar(select(func.count()).select_from(User)) or 0,
        "documents": session.scalar(select(func.count()).select_from(Document)) or 0,
        "versions": session.scalar(select(func.count()).select_from(DocumentVersion)) or 0,
    }

def seed_all(session=None) -> dict[str, int]:
    if session is not None:
        return _seed(session)
    with session_scope() as s:
        return _seed(s)

def _seed(session) -> dict[str, int]:
    # 이미 적재돼 있으면 다시 넣지 않고 현재 개수만 리턴
    if session.scalar(select(func.count()).select_from(Document)):
        return count_rows(session)

    session.add_all(Department(**row) for row in DEPARTMENTS)
    session.add_all(User(**row) for row in USERS)
    session.flush()

    for doc in DOCUMENTS:
        fields = {k: v for k, v in doc.items() if k != "versions"}
        session.add(Document(**fields))
        session.flush()
        session.add_all(DocumentVersion(doc_id=doc["id"], **ver) for ver in doc["versions"])
    session.flush()

    return count_rows(session)
```

"몇 번을 돌려도 결과가 같아야 한다(멱등, idempotent)"는 게 핵심이다. `_seed()` 맨 앞에서 `Document` 테이블에 이미 데이터가 있는지부터 확인해서, 있으면 새로 넣지 않고 현재 개수만 돌려준다. 그래서 `seed_all()`을 여러 번 호출해도 데이터가 중복으로 쌓이지 않는다 — 실제로 두 번 연달아 호출해서 두 번 다 같은 개수가 나오는 것으로 확인했다.
