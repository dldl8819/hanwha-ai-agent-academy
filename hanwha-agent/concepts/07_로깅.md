# 로깅

## 로그 레벨

| 레벨 | 언제 | 예 |
| --- | --- | --- |
| DEBUG | 개발 중에만 보고 싶은 상세 내용 | 로직 처리 과정을 상세히 보고 싶을 때 |
| INFO | 정상적으로 일어난 중요한 일(정보성) | 문서 업로드 완료, 승인 처리 완료 |
| WARNING | 지금은 실행되나 앞으로 문제가 될 수 있다 | 임계치에 가까움, 재시도 발생 |
| ERROR | 에러 발생 | LLM 요청 실패, 500 에러 |
| CRITICAL | 서비스 전체가 위험 | 서버 다운 |

## logging 모듈 기본 설정

파이썬 표준 라이브러리 `logging`을 사용한다. `basicConfig()`로 전역 설정을 한 번 잡아둔다.

- `level`: 지정한 레벨 이상만 출력 (예: `DEBUG`로 두면 DEBUG 이상 전부 출력)
- `format`: 로그 한 줄의 모양
- `datefmt`: 시간 표시 형식
- `force`: 노트북처럼 셀을 여러 번 실행해도 설정이 겹치지 않고 매번 새로 적용되게 함

```python
import logging

logging.basicConfig(
    level=logging.DEBUG,
    format="%(asctime)s %(levelname)-8s %(name)s: %(message)s",
    datefmt="%H:%M:%S",  # 시:분:초
    force=True,
)

# 이름을 붙여서 로거를 하나 가져온다.
log = logging.getLogger("demo")

log.debug("디버그 모드의 debug 입니다")
log.info("인포레벨 로그 입니다.")
log.warning("경고경고 주의하세요.")
log.error("에러발생~~~~~")

# 포맷 패턴
# %(asctime)s   : 시간
# %(levelname)s : 로그 레벨
# %(name)s      : 로거 이름
# %(message)s   : 메시지
```

`format`/`datefmt`는 둘 다 문자열이라는 걸 놓치기 쉽다. 실습 중 `datefmt=%H:%M:%S`처럼 따옴표 없이 적어서 `SyntaxError`가 났었고(`%H`를 대입식 일부로 해석), `format` 쪽도 `%(name)s`, `%(message)s`처럼 각 자리마다 타입 문자(`s`)를 꼭 붙여야 한다 — 하나라도 빠지면 정의할 때는 에러가 안 나다가, 실제로 로그를 찍는 순간 포맷 에러가 난다.

## agent-app에 로깅 추가 (backend/app/core/logging.py)

노트북에서 `basicConfig()`로 실험했던 것과 달리, 실제 프로젝트에서는 **로깅 설정을 앱 전체에서 딱 한 번만** 해야 한다. 여러 모듈이 각자 `basicConfig()`를 부르면 핸들러가 중복으로 쌓여서 로그 한 줄이 여러 번 찍히는 문제가 생기기 때문이다. `config.py`의 `Settings`/`get_settings()`처럼, 로깅도 한 파일에서만 설정하고 나머지는 `get_logger()`로 가져다 쓰는 구조로 만든다.

```python
import logging
import sys

# 이미 설정했는지 기억해두는 표식
_CONFIGURED = False

_FORMAT = "%(asctime)s %(levelname)-8s %(name)s: %(message)s"
_DATEFMT = "%H:%M:%S"

# 내 로그가 파묻히지 않게, 너무 시끄러운 라이브러리들은 레벨을 낮춰둔다
_NOISY = ("httpx", "httpcore", "urllib3", "asyncio")

def setup_logging(level: int = logging.INFO, stream=None) -> None:
    # global: 함수 안에서 모듈의 전역 변수를 수정할 수 있게 해주는 키워드
    global _CONFIGURED
    if _CONFIGURED:  # 이미 설정했으면 다시 하지 않고 바로 종료
        return

    handler = logging.StreamHandler(stream or sys.stdout)  # 로그를 어디로 내보낼지
    handler.setFormatter(logging.Formatter(_FORMAT, datefmt=_DATEFMT))  # 한 줄의 모양

    root = logging.getLogger()  # 이름 없는 최상위(root) 로거
    root.setLevel(level)
    root.handlers = [handler]   # 기존 핸들러를 밀어내고 하나만 남긴다

    for name in _NOISY:
        logging.getLogger(name).setLevel(logging.WARNING)

    _CONFIGURED = True

def get_logger(name: str) -> logging.Logger:
    setup_logging()
    return logging.getLogger(name)
    # name에는 관례적으로 __name__을 넣는다
    # -> 로그에 모듈 경로가 그대로 찍혀서 어느 파일에서 난 로그인지 바로 알 수 있다.
```

노트북에서 이 모듈을 다시 불러와 테스트할 때는, 이전 셀에서 건드려둔 루트 로거 핸들러와 캐시된 모듈을 정리하고 새로 얹는다.

```python
import sys, logging

if "backend" not in sys.path:
    sys.path.insert(0, "backend")

# 앞 셀에서 루트 로거를 건드렸으면, 깨끗이 하고 새로 얹는다.
logging.getLogger().handlers = []
for m in [k for k in list(sys.modules) if k.startswith("app.core.logging")]:
    del sys.modules[m]

from app.core.logging import get_logger

logger = get_logger("app.services.document")  # 임시 패키지명
logger.info("문서 적재 완료 : %s", "DOC-HR-001")  # f"" 보간 대신 %s 포맷 권장
```

`logger.info(f"...")`처럼 f-string으로 미리 문자열을 완성해서 넘기지 않고 `%s` 자리표시자 + 인자를 넘기는 이유는, 로그 레벨이 꺼져 있어서 실제로 출력되지 않을 때는 문자열 조합 자체를 건너뛰기 때문이다(약간의 성능 이점 + 지연 평가).

### 예외 처리와 로깅 함께 쓰기

[[06_예외_계층_설계]]에서 만든 `AgentError` 계열 예외와 로거를 같이 쓰면, "내부적으로는 원인을 자세히 기록하고, 사용자에게는 다듬어진 예외로 알려주는" 흐름을 만들 수 있다.

```python
def ingest(doc_id):
    logger.info("적재 시작: %s", doc_id)
    try:
        text = fake_parsing(doc_id)
    except ConnectionError as e:
        logger.exception("문서 파싱 실패 : %s", doc_id)  # 스택 트레이스까지 로그에 남긴다
        raise ExternalServiceError("문서 변환 서비스에 연결하지 못했습니다.", detail=str(e)) from e

    logger.info("적재 완료: %s", doc_id)
    return text

# 문제없는 상황
ingest("DOC-HR-001")

# 예외 발생 상황
try:
    ingest("DOC-BAD")
except AgentError as e:
    print(e.status_code, e.code, e.message)
```

`logger.exception()`은 `logger.error()`와 달리 현재 처리 중인 예외의 스택 트레이스까지 자동으로 로그에 포함시켜준다 — `except` 블록 안에서만 의미가 있다.

## 로그에 남기면 안 되는 것

- API 키
- 비밀번호
- 토큰
- 주민번호
- 문서 원문 전체
