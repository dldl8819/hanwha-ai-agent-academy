# 체인 합성

[[34_LangChain_기초]]에서 만든 체인은 전부 한 줄로 늘어서 있었다.

```python
chain = prompt | llm | parser
```

실제 RAG 는 이 모양이 안 된다. **갈래가 필요하다.**

## 왜 갈래가 필요한가

질문 하나를 두 군데에 써야 한다.

```text
                    "부산 출장 숙박비?"
                              │
                   ┌──────────┴──────────┐
                   ▼                     ▼
              Retriever        RunnablePassthrough
                   │                     │
                   ▼                     ▼
           출장비규정 제8조       "부산 출장 숙박비?"
                   │                     │
                   ▼                     ▼
                context               question
                   └──────────┬──────────┘
                              ▼
         dict {"context": [...], "question": "부산 출장 숙박비?"}
```

검색기에는 질문을 넣어야 답이 나온다. 그런데 프롬프트에도 질문 원문이 그대로 있어야 한다. `{context}`만 넘기면 모델은 **무엇을 묻는지 모른 채** 문서만 받는다.

한 값을 두 갈래로 보내고, 결과를 딕셔너리 하나로 모으는 것 — 이게 합성이다.

## 세 가지 도구

| 도구 | 하는 일 |
| --- | --- |
| `RunnablePassthrough()` | 받은 값을 **그대로** 흘려보낸다 |
| `RunnablePassthrough.assign(키=단계)` | 받은 딕셔너리는 두고 **키를 더한다** |
| `RunnableParallel(a=…, b=…)` | 갈래를 동시에 돌려 **딕셔너리로 모은다** |

이름이 비슷해서 헷갈리는데, 앞의 둘은 **다른 것**이다. `RunnablePassthrough()`는 값을 통과시키고, `.assign()`은 값을 불린다.

### assign — 원본을 잃지 않는다

```python
enrich = RunnablePassthrough.assign(
    doc_id=lambda d: "DOC-HR-011",
    grade=lambda d: "일반",
)

print(type(enrich).__name__)
print(enrich.invoke({"question": "부산 출장 일비는?"}))
```

```text
RunnableAssign
{'question': '부산 출장 일비는?', 'doc_id': 'DOC-HR-011', 'grade': '일반'}
```

넘긴 것은 `question` 하나뿐인데 결과에는 셋이 다 있다. **`question`이 살아 있다**는 게 핵심이다. 그래서 뒤에서 그대로 쓸 수 있다.

```python
line = enrich | RunnableLambda(lambda d: f"[{d['doc_id']}/{d['grade']}] {d['question']}")
print(line.invoke({"question": "부산 출장 일비는?"}))
```

```text
[DOC-HR-011/일반] 부산 출장 일비는?
```

RAG 에서 질문은 남겨두고 검색 결과만 붙일 때 이 모양이 된다. 타입이 `RunnablePassthrough`가 아니라 `RunnableAssign`으로 찍히는 것도 둘이 다른 물건이라는 표시다.

### RunnableParallel — 갈래를 모은다

```python
both = RunnableParallel(
    upper=RunnableLambda(lambda s: s.upper()),
    length=RunnableLambda(lambda s: len(s)),
)
print("RunnableParallel :", both.invoke("DOC-hr-002"))
```

```text
RunnableParallel : {'upper': 'DOC-HR-002', 'length': 10}
```

같은 입력(`"DOC-hr-002"`)이 두 갈래에 **각각** 들어가고, 결과가 키 이름대로 딕셔너리에 담긴다. 위 그림의 `context` · `question`이 만들어지는 방식이 이것이다.

### 파이프 안에서는 딕셔너리를 그냥 둬도 된다

```python
auto = RunnableLambda(lambda s: s) | {
    "upper": RunnableLambda(lambda s: s.upper()),
    "length": RunnableLambda(lambda s: len(s)),
}
print("dict 그대로      :", auto.invoke("DOC-hr-002"))
print("같은 결과인가    :", both.invoke("DOC-hr-002") == auto.invoke("DOC-hr-002"))
```

```text
dict 그대로      : {'upper': 'DOC-HR-002', 'length': 10}
같은 결과인가    : True
```

파이프 오른쪽에 딕셔너리를 두면 LangChain 이 `RunnableParallel`로 바꿔 준다. 34번 노트에서 `{"context": ..., "question": RunnablePassthrough()}`를 그냥 딕셔너리로 적었던 게 이래서 돌아간 것이다. 감싸도 되고 안 감싸도 되는데, **둘이 같은 것이라는 걸 알고 쓰는 것**과 모르고 쓰는 것은 다르다.

## 파이프의 규칙 — 맨 앞 하나만 Runnable 이면 된다

평범한 함수 세 개를 만들어 이어 봤다.

```python
def build_prompt(question: str) -> str: ...
def call_llm(prompt: str) -> str: ...
def parser(text: str) -> dict: ...
```

함수끼리는 이어지지 않는다.

```python
try:
    build_prompt | call_llm
except TypeError as e:
    print("함수끼리 :", e)
```

```text
함수끼리 : unsupported operand type(s) for |: 'function' and 'function'
```

`|`는 **왼쪽 객체의 `__or__`가 처리한다.** 평범한 함수에는 `__or__`가 없으니 파이썬이 할 수 있는 게 없다. 그런데 맨 앞 하나만 감싸면 나머지는 그대로 들어간다.

```python
pipeline = RunnableLambda(build_prompt) | call_llm | parser

print("파이프라인 :", type(pipeline).__name__)
print(pipeline.invoke("부산 출장 일비는?"))
```

```text
파이프라인 : RunnableSequence
{'answer': '출장 일비는 1일 3만원입니다.', 'doc_id': 'DOC-HR-012'}
```

`call_llm`과 `parser`는 감싸지 않았는데 들어갔다. 왼쪽이 Runnable 이면 `__or__`가 오른쪽을 받아 `RunnableLambda`로 감싸 주기 때문이다. **모든 함수를 감쌀 필요는 없고, 사슬의 첫 고리만 Runnable 이면 된다.**

## 여러 건을 한 번에 — batch 의 기본값

`batch`는 입력 여러 개를 한 번에 넣는다([[34_LangChain_기초]]). 그런데 **한 건이 실패하면 전체가 실패한다.**

```python
inputs = [
    {"doc_id": "DOC-HR-012"},
    {"doc_id": "DOC-XX-999"},   # 없는 doc_id — 여기서 터진다
    {"doc_id": "DOC-PU-007"},
    {"doc_id": "DOC-SE-002"},
]

try:
    lookup_chain.batch(inputs)
except ValueError as e:
    print("기본값 :", e, "→ 결과를 하나도 못 받는다")
```

```text
기본값 : 모르는 문서... → 결과를 하나도 못 받는다
```

4건 중 3건은 멀쩡한데 하나도 못 받는다. `return_exceptions=True`를 주면 실패한 자리에 예외 객체가 담긴 채로 전부 돌아온다.

```python
results = lookup_chain.batch(inputs, return_exceptions=True)

for one, sent in zip(results, inputs):
    mark = "실패" if isinstance(one, Exception) else "성공"
    print(f"  {mark}  {sent['doc_id']:<12} {one}")
```

```text
  성공  DOC-HR-012   DOC-HR-012 조회 완료
  실패  DOC-XX-999   모르는 문서...
  성공  DOC-PU-007   DOC-PU-007 조회 완료
  성공  DOC-SE-002   DOC-SE-002 조회 완료
```

순서가 유지되므로 몇 번째가 실패했는지 그대로 안다.

**여기가 돈 문제로 이어진다.** 이 예제는 사전 조회라 실패해도 잃는 게 없지만, 모델을 부르는 체인이었다면 터지기 전에 나간 호출은 **이미 과금된 뒤**다. 결과를 못 받는다고 돈이 돌아오지는 않는다. [[32_사용량과_원가_기록]]에서 검증 전에 사용량을 먼저 기록한 것과 같은 이야기다.

## 짚어둘 것

여기까지가 **틀**이다. `Retriever` 자리는 아직 비어 있고, 지금은 문자열을 만들어 내는 가짜 함수가 들어가 있다.

```python
retrieve = RunnableLambda(lambda q: f"[검색결과] {q} → 국내출장 여비 규정 제12조")
```

이 자리에 진짜 검색이 들어가려면 문서를 잘라 임베딩하고 벡터 DB 에 넣는 과정이 먼저다([[33_RAG_개요]]의 ①~⑤). 체인 모양은 그때도 바뀌지 않는다 — **갈아 끼우는 자리만 정해 둔 것**이다.
