# 동시 실행과 재시도·폴백

[[37_비동기와_스트리밍]]에서 `a-` 메서드를 봤다. 여기서는 그것으로 **여러 건을 한꺼번에** 돌리고, Runnable 이 기본으로 주는 재시도·폴백을 [[28_가드와_재시도_폴백]]에서 손으로 짠 것과 견준다.

## abatch 와 gather — 둘 다 동시에 돈다

0.3초 걸리는 가짜 조회 함수를 세 건 돌려 봤다.

```python
async def fetch_meta(payload: dict) -> str:
    await asyncio.sleep(0.3)
    return f"{payload['doc_id']} 조회 완료"
```

```text
순차 (for + await) : 0.92초
asyncio.gather     : 0.31초
abatch             : 0.31초
```

`for` 안에서 `await` 하면 **하나씩 끝나기를 기다린다.** 0.3초짜리 셋이 0.92초가 된 이유다. `await` 를 썼다고 동시에 도는 게 아니다.

| 방법 | 누가 동시 실행을 맡나 | 언제 쓰나 |
| --- | --- | --- |
| `await chain.abatch([...])` | LangChain 이 대신 해준다 | **같은 체인에 입력 여러 개** |
| `await asyncio.gather(*[...])` | 코루틴을 직접 모은다 | **서로 다른 일을 동시에** |

둘 다 0.31초로 같으니, 고르는 기준은 속도가 아니라 **입력 모양**이다.

```python
answer, meta = await asyncio.gather(
    answer_chain.ainvoke({"question": "부산 출장 일비는?"}),
    meta_chain.ainvoke({"doc_id": "DOC-HR-014"}),
)
```

```text
순차 : 0.61초
동시 : 0.30초
```

입력이 `{"question": ...}` 과 `{"doc_id": ...}` 로 달라서 `abatch` 로 묶을 수 없다. **`abatch` 는 같은 체인·같은 모양일 때만** 쓴다.

RAG 로 가면 이 모양이 그대로 필요해진다 — 질문에 답하는 일과 문서 메타를 읽어 오는 일은 서로 기다릴 이유가 없다([[35_체인_합성]]의 갈래와 같은 그림이다. 거기는 순서, 여기는 시간이다).

`abatch` 에는 `config={"max_concurrency": 3}` 으로 동시 실행 수를 조일 수 있다. 실제 모델을 부를 때는 이걸 안 주면 한도에 걸린다.

## with_retry — 예외에만 듣는다

두 번 실패하고 세 번째에 성공하는 함수로 확인했다.

```python
ok = RunnableLambda(flaky).with_retry(stop_after_attempt=3, wait_exponential_jitter=False)
```

```text
1. stop_after_attempt=3 : 부산 출장 일비는? 성공   (실제 호출 3회)
2. stop_after_attempt=2 : RuntimeError: 일시 오류 2   (실제 호출 2회)
```

`stop_after_attempt` 는 **재시도 횟수가 아니라 총 호출 횟수**다. 2를 주면 한 번 더 해보고 끝이다.

`wait_exponential_jitter=False` 는 실험용이다. 기본값은 실패할수록 간격을 늘려 기다리는데(지수 백오프), 연습에서는 그냥 시간만 잡아먹는다. 실제 운영에서는 켜 두는 쪽이 맞다 — 상대 서버가 힘들어서 실패하는 중에 바로 다시 때리면 더 나빠진다.

### 손으로 짠 재시도와 무엇이 다른가

| | `chat_service` 의 for 문 | `with_retry` |
| --- | --- | --- |
| 무엇에 반응하나 | **스키마 위반** (응답은 왔는데 모양이 틀림) | **예외** (응답 자체가 안 옴) |
| 다시 부를 때 | 힌트를 붙여 프롬프트를 바꾼다 | 똑같이 다시 부른다 |
| 기록 | `_record_usage` 로 호출마다 남긴다 | 남기지 않는다 |

**둘은 대체재가 아니다.** `with_retry` 는 네트워크·5xx 같은 일시 장애를, for 문은 "모델이 형식을 안 지킨 것"을 맡는다. 형식 위반은 예외가 아니라 정상 응답이라 `with_retry` 가 볼 수 없다.

## with_fallbacks — 먼저 나가버린 것은 못 거둔다

```python
safe = RunnableLambda(always_fail).with_fallbacks([RunnableLambda(fallback_notice)])
```

```text
[경고] 주 체인 실패 · 폴백 응답을 반환합니다
폴백 결과 : 지금은 답변할 수 없습니다. 총무팀 담당자에게 문의해 주세요.
   타입      : RunnableWithFallbacks
```

`invoke` 에서는 깔끔하다. **스트리밍에서는 다르다.**

```python
m = FakeListChatModel(responses=["부산 출장 일비는 2만원입니다"], error_on_chunk_number=n)
safe = (m | StrOutputParser()).with_fallbacks([RunnableLambda(폴백)])
```

```text
error_on_chunk_number=0 : 폴백 성공 → '지금은 답변할 수 없습니다.'
error_on_chunk_number=2 : 폴백 실패 → FakeListChatModelError
                          이미 나간 조각 2개 : '부산'
```

**첫 조각이 나가기 전에 터져야 폴백이 듣는다.** 중간에 터지면 사용자는 이미 `부산` 까지 읽은 상태이고, 폴백 문장으로 바꿔 치울 수가 없다. 예외가 그대로 올라간다.

`invoke` 에서는 "다 만들어진 다음에 넘긴다"라서 갈아 끼울 여지가 있었는데, 스트리밍은 **내보내면서 만든다.** 화면에 스트리밍을 붙이려면 중간 실패를 어떻게 보여줄지 따로 정해야 한다 — 그건 폴백이 해결해 주지 않는다.

## 앱에 넣기 — `chat_service` 가 체인을 부른다

`ask()` 에서 어댑터를 직접 부르던 줄이 체인 호출로 바뀌었다.

```python
chain = build_result_chain(llm, contexts=NO_CONTEXTS, user=DEFAULT_USER).with_retry(
    stop_after_attempt=2
)
...
# result = llm.answer(question=prompt, contexts=NO_CONTEXTS, user=DEFAULT_USER)
result = chain.invoke({"question": prompt})
```

바깥 구조는 그대로다. 가드 → Run INSERT → 트레이스 → for 재시도 → `_record_usage` → 검증 → 폴백 → Run UPDATE.

체인을 **for 문 밖에서 한 번만 만드는 것**이 맞다. 프롬프트는 매번 달라지지만 체인 구조는 같아서, 안에서 만들면 같은 객체를 세 번 조립하게 된다.

테스트는 그대로 통과한다.

```text
backend/tests/test_chat_golden.py    11 passed
backend/tests/test_layers.py          5 passed
전체                                 36 passed
```

골든셋이 안 깨졌다는 게 이 교체의 안전망이었다([[29_골든셋_회귀테스트]]). 어댑터를 `factory.get_llm` 으로 갈아 끼우는 방식이라, 안에서 체인을 쓰든 포트를 직접 쓰든 테스트는 상관하지 않는다. **경계를 잡아 두면 안쪽을 바꿀 수 있다**는 것이 여기서 값으로 돌아왔다.

## 짚어둘 것

### 재시도가 두 겹이 됐다

지금 한 번의 `ask()` 는 최대 **3회 × 2회 = 6번** 모델을 부를 수 있다. 바깥 for 문이 3회, 그 안의 `with_retry` 가 2회다.

의도한 것이면 괜찮다. 다만 `MAX_ATTEMPTS = 3` 만 보고 "최대 세 번"이라고 읽으면 틀린다. 두 숫자가 서로 다른 파일에 있어서 더 그렇다.

### with_retry 가 장부에 구멍을 낸다

[[32_사용량과_원가_기록]]에서 **검증 전에** 사용량을 기록하기로 한 이유는 "버려진 응답도 이미 과금됐다"였다. `with_retry` 는 그 구멍을 다시 만든다.

```text
포트가 실제로 불린 횟수 : 2 회
chat_service 가 받는 LLMResult : 1 개
장부에 안 남는 호출 : 1 건
```

`_record_usage` 는 `LLMResult` 를 받아야 행을 만든다. 그런데 예외로 끝난 호출은 `LLMResult` 자체가 없다. **토큰을 썼는지 안 썼는지조차 알 수 없다.**

- 연결이 끊겨 요청이 닿지 않았다면 과금은 없다
- 모델이 답을 다 만든 뒤 5xx·타임아웃이었다면 과금은 있다

지금 코드로는 둘을 구분할 방법이 없다. 어댑터가 실패한 호출에 대해서도 뭔가를 남기게 하거나(`ExternalServiceError` 에 토큰 수를 실어 보내는 식), 재시도를 한쪽으로 모으는 것이 다음에 볼 자리다.

### 스트리밍은 아직 안 된다

[[37_비동기와_스트리밍]]에서 본 그대로다. `build_answer_chain` 끝의 `RunnableLambda` 가 조각을 1개로 뭉치고, 그 앞의 `LLMPort.answer` 는 애초에 조각을 내놓지 않는다. 오늘 배운 `with_fallbacks` 의 스트리밍 함정도 **스트리밍을 실제로 켠 다음에야** 만나게 된다.
