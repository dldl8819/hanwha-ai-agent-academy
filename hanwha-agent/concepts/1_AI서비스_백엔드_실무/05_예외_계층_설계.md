# 예외 계층 설계

## 왜 예외를 계층으로 설계하는가

API에서 에러가 나면, 그 에러 메시지를 그대로 사용자에게 보여주기보다 데이터(상태 코드 + 코드 문자열 + 메시지)로 응답해줄 수 있어야 한다. 그러려면 예외 메시지에 아래 내용이 담겨 있어야 한다.

- 무엇이 잘못됐는가
- 무엇이어야 하는지
- 실제로 받은 값

이걸 예외가 발생할 때마다 즉흥적으로 만들지 않고, 프로젝트 전용 예외 클래스 계층으로 미리 설계해둔다.

## 예외 계층 구조

```text
Exception
    AgentError                 - 우리 앱의 모든 예외의 root, 기본 400
        NotFound                404
        PermissionDenied        403
        ValidationFailed        422
        GuardTripped            400   (입력 가드에 걸림 - 길이 초과, 인젝션 의심 등)
        RateLimited             429   (호출 한도 초과)
        ApprovalRequired        409   (승인 없이 외부 실행 시도)
        ModeNotAvailable        409   (모드 변경 불가)
        ExternalServiceError    502
```

모든 예외가 `AgentError`를 상속받기 때문에, 어디서 어떤 구체적인 예외가 나든 `isinstance(exc, AgentError)` 한 번으로 "우리가 의도한 상황"인지 구분할 수 있다.

처음엔 `ValidationFailed`를 `ValidationError`라고 이름 붙였는데, Pydantic이 이미 `pydantic.ValidationError`라는 예외를 쓰고 있어서 같은 이름으로 두면 나중에 `from pydantic import ValidationError`와 `from app.core.exceptions import ...`를 같은 파일에서 같이 쓸 때 이름이 충돌한다. 그래서 `ValidationFailed`로 바꿨다.

```python
class AgentError(Exception):
    status_code = 400
    code = "agent_error"

    def __init__(self, message: str, *, detail: str | None = None):
        # print(e) 했을 때 메시지가 나오게 Exception의 message를 그대로 넘긴다.
        super().__init__(message)
        self.message = message
        self.detail = detail

class NotFound(AgentError):          # 요청한 자원이 없다
    status_code = 404
    code = "not_found"

class PermissionDenied(AgentError):  # 자원은 있으나 이 사용자가 접근할 수 없다
    status_code = 403
    code = "permission_denied"

class ValidationFailed(AgentError):  # 입력값이 규칙에 맞지 않는다
    status_code = 422
    code = "validation_failed"

class ExternalServiceError(AgentError):  # 외부 서비스 호출 실패
    status_code = 502
    code = "external_service_error"
```

## 사용 예시

```python
def handle(exc):
    if isinstance(exc, AgentError):
        # 우리가 의도한 상황
        return {"message": exc.message, "status": exc.status_code, "code": exc.code, "detail": exc.detail}
    # 우리가 예상하지 못한 예외 (진짜 사고) — 내부 정보를 그대로 노출하지 않는다
    return {"message": "서버 오류가 발생했습니다.", "status": 500, "code": "internal_error"}

for exc in [
    NotFound("문서를 못 찾았습니다."),
    PermissionDenied("이 문서를 열람할 권한이 없습니다."),
    ExternalServiceError("문서 변환 서비스에 연결하지 못했습니다."),
    KeyError("doc_id"),  # 우리가 만든 예외가 아닌 경우
]:
    print(handle(exc))
```

`AgentError` 계열이 아닌 예외(`KeyError` 등)는 `isinstance` 검사에 걸리지 않아서 자동으로 500 처리로 빠진다 — 예상 못 한 에러가 사용자에게 내부 정보를 노출하지 않도록 막아주는 안전장치다.

## raise ... from ... — 예외 발생 원인을 잃어버리지 않기

다른 예외를 잡아서 우리 예외로 다시 던질 때, `from`을 안 붙이면 원래 무엇 때문에 터졌는지(원인)가 로그에서 사라진다.

```python
import json

def parse_bad(text):
    try:
        return json.loads(text)  # 문자열 → 파이썬 객체
    except json.JSONDecodeError as e:
        raise ValidationFailed(
            "데이터 형식이 올바르지 않습니다.",  # 사용자에게 보여줄 메시지
            detail=str(e),                    # 개발자가 볼 원래 에러 메시지
        ) from e  # 원인 연결

try:
    parse_bad("{json 형식이 아닌 input}")
except ValidationFailed as e:
    print("예외 메시지 :", e)
    print("원인 :", type(e.__cause__).__name__, e.__cause__)
```

`from e`로 연결해두면 `e.__cause__`로 원래 예외(`JSONDecodeError`)에 그대로 접근할 수 있다. 사용자에게는 다듬어진 메시지를 보여주고, 로그나 디버깅에는 원인이 되는 원본 에러를 그대로 남길 수 있다.
