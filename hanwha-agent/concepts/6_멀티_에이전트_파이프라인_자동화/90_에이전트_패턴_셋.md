# 에이전트 패턴 셋

[[78_에이전트_루프와_멈추는_조건]]의 루프는 다음 단계를 **모델이** 정했다. 이번에 만든 셋은 다음 단계를
**우리가** 정한다. 에이전트 패턴은 「LLM 이 다음 단계를 얼마나 스스로 정하는가」로 나뉜다는 것이 출발점이다
(Anthropic 엔지니어링 글 「Building effective agents」).

## 루프로 하면 생기는 일

수업 노트북이 먼저 이것을 셌다.

```text
루프(for turn in range) : 1개
MAX_TOOL_TURNS : 4
한 왕복에 1개씩 넷을 부르면 필요한 왕복 : 5 (> 4 — 최종 답 자리가 없다)
그때 남는 문구 : (도구 호출 상한에 닿아 답을 마치지 못했습니다)
```

도구가 넷이 됐다. 모델이 하나씩 차례로 부르면 마지막 답을 쓸 턴이 남지 않는다. 상한을 올리면 되지만
[[80_도구_루프를_돌려_보다]]에서 본 대로 턴마다 입력이 쌓여 비용이 누적으로 는다. 순서가 늘 같은 일이라면
모델에게 매번 고르게 할 이유가 없다.

## 셋

| 패턴 | 뜻 | 함수 |
| --- | --- | --- |
| 체이닝 | 일을 정해진 순서의 단계로 쪼개고, 앞 단계의 결과를 뒤 단계가 받는다 | `run_chain` |
| 라우팅 | 들어온 것을 우리가 분류해 서로 다른 처리로 보낸다 | `route` |
| 병렬 | 서로 기다릴 이유가 없는 일을 동시에 돌리고 결과를 모은다 | `run_parallel` |

```python
Step = Callable[[dict], dict]     # state 를 받아 바뀐 키만 돌려준다

def run_chain(steps, state):
    trace = state.setdefault("trace", [])
    for step in steps:
        changed = step(state)
        trace.append(step.__name__)
        state.update(changed)
        if "error" in changed:
            break
    return state

def route(state, pick, routes):
    name = pick(state)
    if name not in routes:
        raise KeyError(...)
    return {"route": name, **routes[name](state)}

def run_parallel(calls, max_workers=4):
    with ThreadPoolExecutor(max_workers=max_workers) as ex:
        futures = {name: ex.submit(fn, **kwargs) for name, (fn, kwargs) in calls.items()}
    for name, f in futures.items():
        try:    out[name] = f.result()
        except Exception as e:  out[name] = {"error": ...}
```

단계가 **바뀐 키만** 돌려주는 약속이 셋을 묶는다. 체이닝은 그걸 합치고, 라우팅은 고른 갈래의 결과에
`route` 를 얹고, 병렬은 이름별로 모은다. [[35_체인_합성]]의 LCEL `|` 와 같은 생각을 dict 로 한 것이다.

라우팅에서 표에 없는 이름이면 `KeyError` 다. 갈래를 하나 빼먹으면 조용히 넘어가지 않고 바로 터진다.
병렬은 반대로 하나가 터져도 나머지를 살린다. 둘 다 [[38_동시_실행과_재시도_폴백]]에서 본
「실패를 어디서 멈추고 어디서 흡수하나」의 답이다.

## 조립

```text
run_workflow(question)
   체이닝  ① _wf_search   검색 도구 → sources, passed
           ② _wf_route    라우팅
                 ├─ found        → _wf_found        병렬 : 근거 문서별 버전 이력 동시 조회
                 └─ insufficient → _wf_insufficient  버전 이력 조회 안 함, 안내 문구
```

```text
국내 출장 여비 규정은 지금 몇 버전 인가요?
  passed=True  route=found         versions={DOC-HR-014: v2.0/현행, v1.1/만료}
점심 메뉴 추천해 줘.
  passed=False route=insufficient  versions={}  note=있음
재택근무 장비 지원과 출장 숙박비 기준
  passed=True  route=found         versions={DOC-HR-014: ..., DOC-HR-021: v1.2/현행}
```

모델 호출이 없다(검색 안의 Multi-Query 를 빼면). 같은 질문이면 같은 길로 간다. 루프에서는 같은 질문에도
모델이 도구를 부르는 순서가 바뀔 수 있었다.

## 고르는 기준

| 물음 | 답 | 패턴 |
| --- | --- | --- |
| 단계가 서로 기다리나 | 뒤 단계가 앞 결과를 쓴다 | 체이닝 |
| | 상관없다 | 병렬 |
| 길이 여럿이고 입력을 보고 고르나 | 기준을 우리가 적을 수 있다 | 라우팅 |
| | 기준을 적을 수 없다 (처음 보는 질문) | 에이전트 루프 |
| 무엇을 바꾸려 하나 | 정확도 (느려도 된다) | 체이닝 |
| | 시간 (같은 결과를 빠르게) | 병렬 |
| 기다리는 일인가 | DB·네트워크·LLM | 병렬이 제값 한다 |
| | 순수 계산 | 병렬이 제값 못 한다 |
| 갈래·단계 규모 | 갈래 1, 단계 짧음 | 병렬이 오히려 느리다 |

## 병렬이 더 느렸다

마지막 줄을 직접 확인했다. 버전 이력 4건을 순차와 병렬로 불렀다.

```text
버전 이력 4건  순차 28ms · 병렬 40ms
```

로컬 PostgreSQL 조회 한 건이 7ms 남짓이다. 스레드 풀을 만들고 넷을 띄우고 모으는 비용이 그보다 크다.
병렬이 이기려면 한 건이 스레드 비용보다 충분히 오래 기다려야 한다 — 외부 API, LLM 호출 같은 것.
[[38_동시_실행과_재시도_폴백]]에서 `asyncio.gather` 로 호출을 묶어 빨라진 것과 같은 원리이고, 같은 원리로
여기서는 느려진다.

`ThreadPoolExecutor` 는 스레드다. 파이썬 GIL 때문에 순수 계산은 한 번에 하나만 돈다. 기다리는 동안에만
다른 스레드가 일한다. 표의 「순수 계산은 제값 못 한다」가 그 뜻이다.

## 라우팅이 검색 뒤에 있다

```text
점심 메뉴 추천해 줘.   7,115ms   passed=False → insufficient
```

규정과 상관없는 질문도 검색 파이프라인(Multi-Query 의 LLM 호출, 하이브리드, 크로스 인코더)을 다 거친 뒤에야
「없음」 갈래로 간다. 갈래를 고르는 기준이 검색 결과(`passed`)라서다. [[80_도구_루프를_돌려_보다]]에서 루프는
「안녕하세요」에 도구를 부르지 않았다. 모델이 앞에서 거른 셈이다. 워크플로우는 모델이 없으니 앞에서 거를
수단이 없다. 앞쪽에 값싼 분류(키워드, 작은 모델)를 하나 두면 라우팅이 둘이 된다.
