# 체크포인트

체크포인트는 그래프가 노드 하나를 끝낼 때마다 그때의 상태를 **실행 이름(thread_id)** 을 붙여 저장하는 지점이다.

```text
START -> search (저장) -> fix (저장) -> search (실패 — 저장 안 함)
                                          ↑ 다시 부르면 여기서부터
```

실패한 단계는 저장하지 않는다. 그래서 다시 실행하면 마지막으로 저장된 자리 다음부터 이어 간다.

## 붙이는 법

```python
def build_loop_graph(..., checkpointer=None):
    ...
    return g.compile(checkpointer=checkpointer)

config = {"configurable": {"thread_id": thread_id}, "recursion_limit": ...}
graph.invoke(inp, config)
```

- `compile(checkpointer=...)` — 저장소를 붙인다. 없으면([[92_순환_그래프와_재시도]]의 `run_loop_graph`) 저장하지 않는다.
- `thread_id` — 실행 이름. 같은 이름으로 부르면 같은 실행을 이어 간다. UUID 로 만든다.
- `invoke(None, config)` — 입력 없이 부르면 새로 시작하지 않고 저장된 자리에서 이어 간다.
  `run_resumable_graph(question=None, ...)` 이 이 길이다.

## 저장소 — PostgresSaver

```bash
python -m pip install "langgraph-checkpoint-postgres==3.1.2" "psycopg-pool==3.3.1"
```

```python
url = get_settings().database_url.replace("postgresql+psycopg://", "postgresql://", 1)
with PostgresSaver.from_conn_string(url) as saver:
    saver.setup()
```

- 주소에서 `+psycopg` 를 뺀다. SQLAlchemy 는 드라이버 이름을 주소에 적지만 PostgresSaver 는 psycopg 를 직접 쓴다.
- `setup()` 이 표 네 개를 만든다.

```text
DB 표 14 → 18 · checkpoint_blobs · checkpoint_migrations · checkpoint_writes · checkpoints
```

메모리 저장소(`InMemorySaver`)도 있다. 프로세스가 끝나면 사라지니 노트북 실험용이다. 서버가 재시작돼도
이어 가려면 DB 에 둬야 한다.

## 우리 DB 에 남이 만든 표가 생겼다 — alembic 제외

[[21_Alembic_마이그레이션]]의 autogenerate 는 우리 모델(`Base.metadata`)과 DB 를 비교한다. 체크포인트 표는
LangGraph 가 만들었고 우리 모델에는 없다. 그러면 autogenerate 는 「DB 에만 있는 표」로 보고 지우려 한다.

직접 비교해 봤다.

```text
include_name 없이 : remove_table checkpoints · checkpoint_migrations · checkpoint_writes · checkpoint_blobs
                    remove_index checkpoints_thread_id_idx · checkpoint_writes_thread_id_idx · checkpoint_blobs_thread_id_idx
include_name 있으면: []
```

```python
LANGGRAPH_TABLES = {"checkpoints", "checkpoint_blobs", "checkpoint_writes", "checkpoint_migrations"}

def include_name(name, type_, parent_names) -> bool:
    if type_ == "table":
        return name not in LANGGRAPH_TABLES
    return True

context.configure(connection=connection, target_metadata=target_metadata, include_name=include_name)
```

표를 비교 대상에서 빼면 그 표의 인덱스도 같이 빠진다. 다음 마이그레이션을 무심코 만들고 올렸다면 체크포인트 표
넷이 지워지고, 멈춰 있던 승인 요청([[94_HITL_승인]])이 전부 이어 갈 수 없게 된다.

강사님 코드는 온라인 모드에만 `include_name` 을 넣었다. 이 저장소는 오프라인 모드(`--sql`)에도 넣었다.
같은 비교를 두 길이 다르게 하면 한쪽에서만 drop 이 나온다.

수업 노트북은 마이그레이션을 만든 뒤 `upgrade()` 본문에 `drop_` 이 있으면 멈추게 했다. 테이블을 지우는
마이그레이션은 사람이 한 번 더 보게 하는 장치다.

## 실패한 자리에서 이어 가기

[[92_순환_그래프와_재시도]]의 순환 그래프를 체크포인트와 붙이고, 두 번째 검색에서 일부러 예외를 냈다.

```text
1차 실행 : 두 번째 검색에서 일부러 실패
           검색 ['기차표는 어떤 좌석까지 끊어도 돼?', '교통비는 어떤 좌석까지 끊어도 돼?']
저장된 상태 : 다음 노드 ('search',) · query 교통비는 어떤 좌석까지 끊어도 돼? · fixes 1
체크포인트 수 : 4
재개      : 검색 ['교통비는 어떤 좌석까지 끊어도 돼?']  → passed False · note
```

- 실패한 search 는 저장되지 않았고, 다음에 할 일이 `search` 로 남았다.
- 고친 질문(`query`)과 고친 횟수(`fixes=1`)가 남아 있다.
- 이어 가니 첫 검색과 고치기를 건너뛰고 두 번째 검색부터 돌았다.

`RuntimeError` 는 `retry_on`(ExternalServiceError)에 해당하지 않아 노드 재시도 없이 바로 그래프가 멈췄다.
재시도는 **같은 실행 안에서** 다시 부르는 것이고, 체크포인트는 **다른 실행에서** 이어 가는 것이다. 둘은 다른 층이다.

## 무엇에 쓰나

검색처럼 처음부터 다시 해도 되는 일에는 이득이 작다. 체크포인트가 반드시 있어야 하는 것은 **사람을 기다리는
그래프**다. 사람의 결정은 몇 초가 아니라 몇 시간 뒤에 온다. 그동안 프로세스를 붙잡고 있을 수 없으니 멈춘 자리를
DB 에 두고 나중에 이어 간다. 그게 [[94_HITL_승인]]이다.
