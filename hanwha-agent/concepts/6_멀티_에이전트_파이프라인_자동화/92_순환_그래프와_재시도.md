# 순환 그래프와 재시도

[[91_LangGraph]]에서 「LangGraph 가 값을 하는 것은 되돌아가는 선」이라고 적었다. 그 선을 처음 그었다.

```text
START -> search -> pick --- found        -> END
            ^         ├---- insufficient -> END
            └── fix <─┘ "fix"
```

검색이 모자라면 질문을 고쳐 다시 검색한다.

## 질문 고치기 노드

```python
FIX_WORDS = {"호텔비": "숙박비", "밥값": "식비", "기차표": "교통비"}
MAX_FIXES = 2

def fix_question(state: dict) -> dict:
    q = state.get("query") or state["question"]
    for old, new in FIX_WORDS.items():
        q = q.replace(old, new)
    return {"query": q, "fixes": state.get("fixes", 0) + 1}
```

입으로 하는 말을 규정 낱말로 바꾼다. 원 질문은 `question` 에 그대로 두고 고친 것을 `query` 에 둔다.
상태가 `LoopState(WorkflowState)` 로 두 칸(`query`, `fixes`)을 더 갖는다. 검색 노드도 `query` 가 있으면
그걸로 찾도록 `_wf_search_query` 가 새로 생겼다.

## 되돌아가는 선과 멈추는 장치 둘

```python
g.add_conditional_edges("search", pick, {"fix": "fix", "found": "found", "insufficient": "insufficient"})
g.add_edge("fix", "search")
```

`fix → search` 한 줄이 순환이다. 순환에는 멈추는 장치가 있어야 한다. [[78_에이전트_루프와_멈추는_조건]]의
`MAX_TOOL_TURNS` 와 같은 자리이고 여기는 둘이다.

| 장치 | 누가 | 넘으면 |
| --- | --- | --- |
| `MAX_FIXES = 2` | 갈래 함수가 센다 | `insufficient` 로 정상 종료 |
| `recursion_limit = 2*MAX_FIXES+3` | LangGraph 가 센다 | `GraphRecursionError` 예외 |

앞의 것이 정상적인 끝이고 뒤의 것은 안전판이다. search·fix 를 두 번 오가고 마지막 갈래까지 가면
search, fix, search, fix, search, insufficient 로 여섯 단계라 7 이면 넉넉하다.

## 재시도 정책

```python
retry = RetryPolicy(max_attempts=MAX_ATTEMPTS, retry_on=ExternalServiceError)
g.add_node("search", search, retry_policy=retry)
```

| 필드 | 뜻 |
| --- | --- |
| `max_attempts` | 첫 시도를 포함해 몇 번까지 |
| `retry_on` | 이 예외일 때만 다시 부른다 |
| `initial_interval`, `jitter` | 기다리는 간격. 테스트에서는 0, False 로 |

**노드 단위**로 다시 부른다. [[38_동시_실행과_재시도_폴백]]의 `with_retry()` 가 체인 전체를 다시 돌린 것과
다르다. 검색 안의 LLM 호출(Multi-Query)이나 임베딩이 일시적으로 실패하면 그 노드만 다시 돈다.
`retry_on` 을 좁게 잡은 것이 중요하다. 코드 오타(`KeyError` 등)까지 다시 부르면 같은 오류를 세 번 보고 끝난다.

`MAX_ATTEMPTS` 는 [[28_가드와_재시도_폴백]]의 스키마 재시도 상수(3)를 그대로 가져다 썼다. 값은 같지만 뜻이 다른
두 재시도가 한 상수를 공유한다.

## 실제로 돌려 보니 고치기가 거의 안 돌았다

같은 retriever(크로스 인코더 판정, [[83_어휘_점수가_늘_0이었다]])로 질문 넷을 넣었다.

```text
출장 가서 호텔비는 얼마까지 되나요?      검색 1회  rerank 0.309  → found   (고치기 안 함)
출장 가면 밥값은 하루에 얼마 나와?       검색 1회  rerank 0.88   → found   (고치기 안 함)
기차표는 어떤 좌석까지 끊어도 돼?        검색 3회  0.002 → 0.03 → 0.03 → insufficient
점심 메뉴 추천해 줘                      검색 3회  0.0   → 0.0  → 0.0  → insufficient
```

- **호텔비·밥값은 고칠 필요가 없었다.** 크로스 인코더가 질문과 조각을 같이 읽고 「호텔비」가 숙박비를 묻는 것을
  알아봤다([[75_리랭킹_두_가지]]). 사전으로 바꾸기 전에 모델이 이미 바꿔 읽은 셈이다.
- **기차표는 고쳐도 안 됐다.** 「교통비」로 바꾸니 0.002 → 0.03. 규정 본문은 「철도(KTX·SRT)」라고 적는다.
  기차표를 더 넓은 말로 바꿔 오히려 멀어졌다.
- **고쳐도 질문이 그대로인데 다시 검색했다.** 점심 메뉴에는 바꿀 낱말이 없다. 그래도 `fixes < MAX_FIXES` 라
  fix 로 가고, 같은 질문으로 다시 검색했다. 검색 한 번이 18초 남짓이라 54.8초가 걸렸다. 기차표도 두 번째 고치기는
  바뀐 것이 없어 세 번째 검색은 두 번째와 같았다.

## 보완 — 고쳐도 같으면 고치러 가지 않는다

```python
def route_with_fixes(state: dict) -> str:
    if route_after_search(state) == "found":
        return "found"
    if state.get("fixes", 0) >= MAX_FIXES:
        return "insufficient"
    current = state.get("query") or state["question"]
    return "fix" if fix_question(state)["query"] != current else "insufficient"
```

갈래를 고르는 자리에서 「고치면 달라지는가」를 미리 본다. `fix_question` 이 순수 함수(상태만 받아 값을 돌려준다)라
갈래 함수 안에서 불러도 부작용이 없다. 상태 칸을 늘리지 않았다.

```text
                         수정 전            수정 후
점심 메뉴 추천해 줘       검색 3회 · 54.8s    검색 1회 · 17.7s
기차표는 어떤 좌석…      검색 3회            검색 2회
```

순환을 만들 때 상한만 걸면 「상한까지는 돈다」가 된다. 상한은 최악을 막고, **도는 것이 의미가 있는지**는 따로
물어야 한다.
