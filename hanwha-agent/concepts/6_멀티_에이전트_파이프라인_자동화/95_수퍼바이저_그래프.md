# 수퍼바이저 그래프

[[90_에이전트_패턴_셋]]의 라우팅은 「검색 뒤 한 번」 갈래를 골랐다. [[91_LangGraph]]에서 그 고르기가 함수에서
선(conditional edge)으로 바뀌었다. 이번에는 **고르기만 하는 노드**가 따로 생겼다. 멀티 에이전트의 가장 흔한 모양이다.

```text
START → supervisor ──(고른 이름)──→ search / draft ──┐
            ↑                                         │
            └─────────── 끝나면 돌아온다 ─────────────┘
            └── "finish" → END
```

## 구조

```python
def build_supervisor_graph(workers, pick):
    def supervisor(state: dict) -> dict:
        return {"next": pick(state), "turns": state.get("turns", 0) + 1}

    g = StateGraph(SupervisorState)
    g.add_node("supervisor", supervisor)
    for name, step in workers.items():
        g.add_node(name, step)
        g.add_edge(name, "supervisor")
    g.add_edge(START, "supervisor")
    g.add_conditional_edges("supervisor", lambda s: s["next"], {**{n: n for n in workers}, "finish": END})
    return g.compile()
```

| 노드 | 하는 일 |
| --- | --- |
| supervisor | 상태를 보고 다음 담당 이름을 `next` 에 적는다. 몇 번 골랐는지(`turns`) 센다. **일은 하지 않는다** |
| 담당(search, draft) | 일을 하고 supervisor 로 돌아간다 |

[[92_순환_그래프와_재시도]]의 순환은 `fix → search` 한 줄이었다. 여기서는 모든 담당이 supervisor 로 돌아오는
별 모양 순환이다. 담당을 늘려도 선 긋는 코드는 그대로이고 `workers` 에 이름 하나가 더해질 뿐이다.

## 고르는 규칙

```python
MAX_TURNS = 4
DRAFT_WORDS = ("신청서", "초안")

def pick_worker(state: dict) -> str:
    if state.get("turns", 0) >= MAX_TURNS:
        return "finish"
    if "sources" not in state:
        return "search"
    if any(w in state["question"] for w in DRAFT_WORDS) and state.get("passed") and "draft" not in state:
        return "draft"
    return "finish"
```

지금은 코드가 고른다. 이 함수 자리를 모델 호출로 바꾸면 「모델이 담당을 고르는 수퍼바이저」가 된다.
[[90_에이전트_패턴_셋]]의 기준표로 보면, 지금 규칙은 우리가 적을 수 있는 기준이라 라우팅이고 모델로 바꾸면
에이전트 루프에 가까워진다. 그래프 모양은 같고 **고르는 주체만 바뀐다.**

멈추는 장치도 둘이다. `MAX_TURNS`(규칙이 「finish」를 고른다)와 `recursion_limit = 2*MAX_TURNS+2`(LangGraph 의 안전판).
[[92_순환_그래프와_재시도]]와 같은 짝이다.

## 규칙이 후보를 보고 있었다

강사님 규칙의 셋째 줄은 `state.get("sources")` 였다.

```text
출장 숙박비 상한은 얼마인가요?   turns 2  passed True   초안 없음
부산 출장 신청서를 써 줘         turns 3  passed True   초안 있음
점심 메뉴 신청서 써 줘           turns 3  passed False  초안 있음   ← 문제
```

검색은 임계값을 못 넘어도 후보 목록을 돌려준다([[76_정책_필터를_되돌리고_다시_재다]]). 목록이 비어 있지 않으니
근거가 있는 것처럼 보여 점심 메뉴 신청서가 만들어졌다. [[90_에이전트_패턴_셋]]의 라우팅은 같은 판단을 `passed` 로 했다.
**「근거가 있나」를 묻는 자리마다 같은 값을 보는지** 확인해야 한다. `passed` 로 고친 뒤 같은 상태에서 `finish` 를 골랐다.

## 초안 담당

```python
def _sv_draft(state: dict) -> dict:
    with session_scope() as s:
        run_id = next_run_id(s)
        s.add(Run(id=run_id, user_id=1, question=state["question"], status="진행중", ...))
    docs = ", ".join(sorted({x["doc_id"] for x in state.get("sources", [])}))
    made = registry.get("create_draft").run(run_id=run_id, doc_type="국내출장 신청서",
                                            fields={"요청": state["question"], "근거문서": docs}, user=state["user"])
    ...
    return {"draft": made, "run_id": run_id}
```

- 초안을 쓰기 전에 실행 기록(Run)을 연다. `drafts.run_id` 가 외래키라 Run 이 먼저 있어야 한다([[84_초안_도구와_쓰기_등급]]).
- 칸은 「요청」(질문 그대로)과 「근거문서」(문서 번호)뿐이다. 출장지·기간 칸이 없다. 흐름을 잇는 것이 목적이라 양식은 비어 있다.
- `user_id=1` 이 박혀 있다. 누가 물었든 1번 사용자의 실행 기록이 된다.

## 승인 그래프로 이어진다

수업 노트북은 수퍼바이저가 만든 초안의 `run_id` 를 승인 요청에 실었다.

```python
sv = chat_service.run_supervisor_graph(question=GOLDEN)
text = f"{sv['draft']['doc_type']} 승인 요청 ({sv['run_id']})"
req = chat_service.run_approval_graph(text=text, ..., run_id=sv.get("run_id"))
```

검색 → 초안 → 승인 요청 → (사람) → 전송이 그래프 둘로 나뉘어 이어진다. 수퍼바이저 그래프는 사람을 기다리지 않으니
체크포인트가 없고, 승인 그래프는 사람을 기다리니 체크포인트가 있다([[93_체크포인트]]). 둘을 하나로 합치지 않은 이유다.
