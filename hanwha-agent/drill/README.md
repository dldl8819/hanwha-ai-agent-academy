# drill — 스스로 코드를 쓰게 하는 연습 도구

**상태 : 설계만. 아직 구현하지 않았다.**

## 왜 만드는가

수업이 강사님 코드를 따라치는 형태라, 다 적고 나면 돌아가는 코드는 남는데 "내가 저걸 백지에서 쓸 수 있나"는 확인이 안 된다. 따라치기와 스스로 쓰기를 가르는 건 **답을 모르는 상태에서 맞았는지 알 수 있느냐**다.

그 조건이 이 저장소엔 이미 있다.

| 파일 | 줄 | 무엇을 보는가 |
| --- | --- | --- |
| [test_layers.py](../backend/tests/test_layers.py) | 119 | 계층 구조가 무너졌는지 |
| [test_chat_golden.py](../backend/tests/test_chat_golden.py) | 129 | 응답이 조건을 만족하는지 (11문항) |
| [test_guards.py](../backend/tests/test_guards.py) | 29 | 가드가 막아야 할 걸 막는지 |

## 원칙 세 가지

**1. 채점은 pytest 가 한다. LLM 이 아니다.**
LLM 채점은 돈이 들고, 채팅에서 물어보는 것과 같고, 무엇보다 애매하게 맞았다고 해준다. pytest 는 안 봐준다.

**2. 통과한 뒤 원본과 대보는 게 핵심이다.**
통과 ≠ 잘 쓴 코드. `_record_usage` 를 검증 **뒤에** 두고도 테스트는 통과한다. 재시도로 나간 비용이 장부에서 빠진다는 건 원본과 대보기 전엔 안 보인다([[32_사용량과_원가_기록]]). 이 diff 단계가 없으면 그냥 문제 푸는 사이트다.

**3. 화면은 마지막이다.**
값은 어느 코드를 비우고 요구사항을 어떻게 쓸지 정하는 데 있고, UI 가 그걸 대신 해주지 않는다. 화면부터 만들면 문제 0개짜리 껍데기가 남는다.

## 채점기를 어떻게 붙이는가 — 설계의 전부

`backend/tests` 의 테스트는 `from app.services import chat_service` 로 **진짜 패키지**를 부른다. 그대로 가져오면 내가 쓴 코드가 아니라 원본을 채점한다.

| 방법 | 결과 |
| --- | --- |
| 원본 파일을 내 답안으로 덮어쓴다 | 원본이 날아간다. 안 된다 |
| `app` 을 임시 폴더에 복사하고 한 파일만 갈아끼운다 | 되긴 한다. 느리고 DB 설정·상대 import 까지 딸려온다 |
| **문제를 파일 하나로 좁힌다** | 제약이 생긴다 — 그리고 그 제약이 맞다 |

세 번째를 고른다. 문제는 `시작.py` 한 파일이고 `test_문제.py` 가 **같은 폴더의 그 파일을 직접 import** 한다. `backend/app` 은 건드리지 않는다.

그래서 문제를 "chat_service 를 짜라"가 아니라 "재시도 루프를 짜라"로 좁혀야 한다. `ask()` 는 가드·팩토리·관측·DB·재시도가 한 자리에 모인 함수라 통째로는 연습 문제가 안 된다. 좁히는 게 손해 같지만 이득이다 — 한 번에 하나만 생각한다.

원본이 `app` 에서 끌어오는 것(`LLMResult`, `AskOut` 등)은 `시작.py` 맨 위에 필요한 만큼만 베껴 넣는다.

## 문제 하나의 모양

```text
drill/problems/28_재시도/
├── 문제.json        메타 — 개념 노트, 유형, 정답 위치
├── 요구사항.md      무엇을 만족해야 하는가
├── 시작.py          import 와 시그니처만
└── test_문제.py     채점기
```

## 정답 파일은 두지 않는다

폴더에 `정답.py` 를 두면 편집기 탭에서 그냥 보인다. 따로 저장하지 않고 **원본 위치만 적어둔다.**

```json
{
  "id": "28_재시도",
  "개념": "concepts/2_AI-Native_아키텍처_테스트/28_가드와_재시도_폴백.md",
  "유형": "코드",
  "정답": {
    "파일": "backend/app/services/chat_service.py",
    "함수": ["_hint_from", "_fallback"]
  }
}
```

- 같은 코드가 두 곳에 있지 않다. 원본을 고치면 정답도 따라 바뀐다
- 편집기에서 눈에 안 띈다
- 줄 번호가 아니라 **함수 이름**이라, 위쪽 코드가 밀려도 안 깨진다

함수만 잘라내는 건 `ast` 로 한다. [test_layers.py](../backend/tests/test_layers.py) 가 이미 쓰는 기법이라 새로 배울 게 없다.

## 요구사항.md 쓰는 법

여기가 진짜 일이고, 도구가 대신 못 해준다.

| 적는다 | 안 적는다 |
| --- | --- |
| 무엇을 만족해야 하는가 | 어떤 함수를 어떤 순서로 부를지 |
| 판정 기준 (테스트가 뭘 보는지) | 원본 코드 조각 |
| 왜 이게 필요한가 한 줄 | 힌트 |

**테스트 코드는 보여준다.** 숨기면 추측 게임이 된다. 실무에서도 요구사항은 주어진다 — 모르는 건 구현이지 조건이 아니다.

## run.py — 화면이 얇아지는 이유

```bash
python drill/run.py 목록
python drill/run.py 풀기 28_재시도    # 작업 폴더에 시작.py 를 복사
python drill/run.py 채점 28_재시도    # pytest → 통과하면 diff
```

CLI 가 핵심이 아니다. **함수**가 핵심이다.

```python
def 채점(문제id: str) -> dict:
    # {"통과": bool, "실패": [사유...], "diff": str | None}
```

CLI 는 이 dict 를 출력만 한다. Streamlit 도 같은 함수를 부르고 `st.write` 만 한다. 그래서 화면이 100줄이다. **화면에 판정 로직이 들어가는 순간 이 설계는 깨진다.**

## 골든형 — 4과목부터

RAG·에이전트는 pytest 로 못 잡는다. 정답이 문자열 하나가 아니라서. 그건 [[29_골든셋_회귀테스트]]에서 이미 푼 문제다 — 조건으로 판정하면 된다. `유형: "골든"` 인 문제는 `test_문제.py` 대신 `golden.json` 을 두고 `check()` 같은 판정 함수를 쓴다.

형식은 **4과목 수업을 듣고 확정한다.** 지금 추측으로 적어두면 어차피 다시 고친다.
